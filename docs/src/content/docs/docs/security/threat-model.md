---
title: "Threat model: secrets held by the server"
---
This page describes what the Lodestore server stores, what protects it, and what an attacker gets in each realistic compromise. It does not cover the repository format itself; see [ADR 0002](/docs/adr/0002-key-model-and-envelope/) for the key hierarchy.

## What the server stores

The server keeps a catalog in SQLite or PostgreSQL. Some of its rows are secrets:

- the repository master key of every repository the server manages
- the server's own key slot password for each repository (the slot that lets the server reopen the repository without an administrator)
- the S3 credentials the server uses, including the write-only credentials it hands to agents
- the private key of the built-in certificate authority and of the gRPC server certificate

Every one of these values is wrapped with XChaCha20-Poly1305 under a 32-byte **unlock key** before it is written to the database. The associated data holds the kind and the id of the secret, each with its length in front, so a wrapped value cannot be moved to another row and no pair of names can be read as another pair. The wrap format carries a version number. On the first start of 0.2 the server checks the unlock key and then re-seals, in one transaction, every secret that 0.1 sealed with the earlier associated data; if anything fails, every row stays as it was. A 0.1 server cannot read the re-sealed secrets, so back up the database before updating to 0.2.

The server also keeps a search cache in `<data_dir>/find-cache/`: the list of file paths of every snapshot that a fleet-wide find has walked. Each frame of a cache file is compressed and sealed with the same AEAD under the unlock key, with the snapshot id, the frame position and the end of the file bound in as associated data, so the file holds no path in the clear and a reordered or truncated file is rejected. A file is deleted together with its snapshot and whenever it fails to open (a different unlock key included); the server rebuilds it from the bucket on the next search. The cache is only an accelerator: restoring needs nothing from it.

The unlock key comes from `LODESTORE_UNLOCK_KEY` or `LODESTORE_UNLOCK_KEY_FILE`. If neither is set, the server generates one on first start in `<data_dir>/unlock.key` (mode 0600, created exclusively), logs a warning that the key sits next to the database, and shows a banner in the UI until the key is moved. The server then unlocks the secrets by itself on every start: there is no prompt.

## What an attacker gets

| The attacker has | Master secrets of the repositories | Notes |
| --- | --- | --- |
| Only the database (a leaked backup of the catalog, a stolen SQL dump) | Not exposed | Secrets are ciphertext. Host names, schedules and snapshot metadata are visible. A copy of `data_dir` does not reveal file names either as long as the unlock key is not in it (see the auto-generated `unlock.key` above): the search cache is sealed under that key. |
| Only the unlock key | Not exposed | The key opens nothing without the wrapped values. |
| The database and the unlock key | **Exposed, for every repository** | This combination yields the master secrets, the S3 credentials and the CA key. Auto-unlock does not protect against it. |
| The server host with a running process | **Exposed** | Unlocked secrets live in the process memory. Signed updates keep this attacker from installing a binary through the update path. A restore job still runs as root, but the agent writes only under its restore folders, so this attacker has root on an enrolled host only where in-place restore is on, where the agent is from 0.1 or where the restore folders include system directories. Hooks from the allowlist, and inline commands where `allow_inline` is on, stay in this attacker's hands (see [Agent updates](#agent-updates)). |
| The bucket only | Not exposed | Data is encrypted under keys derived from the master key, which is never stored in the bucket in the clear. |

The auto-unlock model defends against exactly one thing: a leak of the database on its own. It is not a defence against anyone who can read both the database and the unlock key, and it should not be described or relied on as one.

## Where to keep the unlock key

- **Default (key file next to the database).** Protects only against a leak of the database alone. A backup of the whole data directory contains both, so it gives the attacker everything. Move the key elsewhere as soon as the server runs.
- **`LODESTORE_UNLOCK_KEY_FILE` on a separate volume or a secrets mount.** The database and the key then leave the host through different paths.
- **Helm.** The chart stores the unlock key in a Kubernetes `Secret`. Anyone who can read that `Secret` and the PVC has both. Copy the key out of the cluster (the chart's notes print the command) and keep it in a password manager or vault.
- **Never** put the key in the same backup set, repository or ticket as the database.

## Losing the unlock key

Losing the unlock key loses the server's access to the repositories, not the data. The key slots in the bucket still open with the repository password or the recovery key, and a restore needs only the bucket and one of them. To bring the server back, reconnect the existing repository in the setup wizard with the password or the recovery key.

## A repository that does not match the server's record

When the server adds a repository it records the hash of the repository's `config` object. Every later open reads `config` again and compares it with the record: the hash, the format version, the `incompat_features`, the cipher suite and the repository id. A `config` larger than 1 MiB counts as a difference and is not read further. `lode check` and the server's checks report it as the finding `unreadable_config` and go on with the other checks. If any of them differs, the server does not open the repository for anything, not for reading and not for writing. It hands no writer keys and no storage key to agents, signs no URLs for reading packs, and answers `503` `repository_unavailable` to the API that browses, searches and downloads. Restore jobs and backup jobs the server queues for the repository, manual, scheduled and catch-up alike, fail with the error code `repository_unavailable` and are not sent to the agent. A backup started on the host itself (`lode backup`) does not pass through the server first; the agent compares `config` with its own record before it writes. The reason is stored, shown on the repository page in Storage checks, and raises the alert `repository_unavailable` (see [Alerts](/docs/guides/alerts/)). The other repositories and the start of the server are not affected. The status clears by itself when the next open matches again, and **Check storage again** on the repository page opens the repository again at once. The catalog sync (`POST /api/v1/repositories/{id}/catalog/sync`) answers `503` `repository_unavailable` too, and enrolling a host or planning a restore for a repository in this state fails with `failed_precondition` ("the repository is unavailable") instead of an internal error. Replacing the agent key of such a repository stores the new key and sends it to no agent; agents get the current credentials at their next hello after the repository opens again, and online agents on their next reconnect, so rotated credentials reach the hosts late, not never.

- A failure to reach the storage (network, access, a missing `config`) is not a mismatch. It is not recorded and does not raise this alert; those failures show up in the checks and in the jobs that need the storage.
- **A host that can overwrite `config` can make the repository unavailable.** The check above compares `config` with the record, so a `config` that was replaced makes the server refuse the repository, for every host, until the object is restored. This needs an agent key that can overwrite objects. The generated AWS policy refuses that; MinIO, a bucket with a wider policy and a folder repository do not (see the first bullet of [Agent credentials](#agent-credentials)). Versioning or Object Lock keeps the earlier version of `config` for the repair but does not stop the replacement from being read. It is a stated limit of the model: no data is read or lost, the server shows the reason and raises `repository_unavailable`, and backups through the server stop on every host until `config` is back.
- A build that does not know a feature listed in `incompat_features` refuses to read the repository as well as to write it, so a repository that needs a feature this build lacks fails to open instead of being read wrongly.
- Opening with a password has a budget. The key slots are tried cheapest first, and the Argon2 work (memory in KiB times passes) of the slots that the secret in hand actually tries, summed over one opening, may not exceed 16777216, the work of one slot with the largest parameters allowed. Only Argon2id slots for a password count. Opening with a recovery key starts no Argon2, and a slot of another kind, or one whose parameters are outside the allowed range, costs nothing and is skipped. A key slot larger than 64 KiB is not read. One opening also reads at most 1024 key slots, in the order of the listing, and keeps none of them in memory; a slot past the 1024th is not tried, with a password or with a recovery key. When the budget or the count stops the opening, the error says that the secret is wrong or that the slot it opens was not tried, names both limits and says how many slots were left; `lode` exits with code 12 and the setup wizard answers `422`. A host with the writer keys can add valid password slots that cost less than the real one and so use up the budget first. Opening with the password then fails until the extra slots are removed. Whoever can write under `keys/` can also plant more than 1024 slots that are listed before the real one, which blocks the recovery key for that opening as well; an agent key has no write access to `keys/`, so this needs more than an agent holds. The server, which opens the repository with the master key in its database, is not affected by either. See [ADR 0002](/docs/adr/0002-key-model-and-envelope/) and [How we test data safety](/docs/security/how-we-test/#what-we-have-not-verified).

## Agent credentials

An agent holds a writer keyset and a write-only S3 key. It can add data to the repository and it cannot read it back. The key carries no delete permission, and deletion and garbage collection run only on the server.

- **Write-only means no delete, not no overwrite.** In S3 a `PutObject` on an existing key replaces the object. The generated AWS policy therefore ends with a `Deny` on `s3:PutObject` for requests without `If-None-Match` (the `s3:if-none-match` condition key), and Lodestore itself writes every object with `If-None-Match: *`. Overwrite is refused only where the provider enforces that condition. MinIO rejects the condition key, so the policy it receives (`mc admin policy` commands in the wizard) leaves it out, and a stolen agent key can replace any pack, index or snapshot object there. The checks try this with a throwaway object: the agent key shows as **Write-only verified** only when the overwrite is refused, and as **Can overwrite** (a warning) otherwise. A compromised host can destroy data this way without ever deleting it. Enable bucket versioning or Object Lock on the bucket: with either, a replaced object keeps its earlier version and the data can be recovered.
- **A key that can delete or overwrite is accepted.** The repository wizard and **Replace agent key** show **Can delete** or **Can overwrite** as a warning and carry on; the state is stored on the repository and stays visible. Nothing blocks it, so check the badge after every key change.
- **A local folder gives the agent delete rights.** There is no separate key: the agent writes with file permissions and can delete and overwrite. It is for trying Lodestore, not for real backups.
- **Only S3-compatible storage has these properties.** A separate agent key without delete rights and Object Lock exist only there, which is why 0.1 offers S3-compatible storage and a local folder and nothing else. The agent and `lode` of 0.1 are built without Azure Blob, GCS, SFTP and WebDAV. Those are on the v0.2 roadmap, and they would hand agents full credentials unless that changes first.

- The S3 key is **shared by all agents of a repository**. Revoking a host cuts its gRPC stream at once and the server rejects it with the code `revoked`, but the revoked host still holds the S3 key and can keep writing to the bucket until the key is replaced. Use **Replace agent key** in the repository settings: you enter a new write-only key, the server pushes it to every connected agent, and offline agents receive it when they reconnect. The revocation dialog repeats this warning.
- Revocation is a denylist on the server, checked on the connection and on every message; there is no CRL or OCSP. The agent logs the error and exits with code 77. The systemd unit lists `RestartPreventExitStatus=77`, so the service stays `failed` and is not restarted. The agent touches no local files. A revoked `agent_id` is never accepted again; the host returns only through `install.sh --force` with a new join token.
- Agent client certificates are issued by the built-in CA, last 90 days and renew automatically. The agent generates its private key locally and it never leaves the host.
- **A certificate that the server has replaced stops working.** The server records the serial of the certificate it issued at enrolment and at every renewal, and every agent call (the session, the renewal, the plan of a restore, a refresh of pack links, a read of pack ranges and the download of an agent update) accepts only that serial. The serial before it is accepted until the first session with the new certificate, and for at most 24 hours, so a renewal whose answer was lost does not lock the agent out; a renewal made with the previous certificate does not extend that window. This ends the use of a copy of an old certificate. It is not protection against a copy of the current certificate and its key, which is the credential. A restore that was started before a renewal runs on to its end.
- **The refusal is `certificate_stale`, not `revoked`.** The agent logs that the host has to be enrolled again (`install.sh --force` with a new join token) and keeps retrying with backoff; it does not exit with 77 and the service is not stopped. An agent that the catalog does not know gets the same answer and raises no alert; the server counts those refusals in `lodestore_unknown_agent_refusals`. A revoked agent still gets `revoked`.
- **Two alerts report it.** A refusal raises the critical alert `agent_certificate_rejected` for the host, with the serial and the address of the caller. A live session of an agent that is replaced by a session from another address (for IPv6, another /56), or five such replacements within ten minutes, raise the warning `agent_session_conflict`, which points at a cloned host. Both are built from events that the server keeps in memory for 24 hours. After a restart an alert that was open stays open until 24 hours after it first opened, and a refusal that had not raised one yet is not remembered: the alert comes back at the next attempt of the agent. Behind a load balancer that replaces the address of the agent (SNAT, or TLS passthrough that does not keep it), the server sees the address of the balancer, so the rule of another address does not fire and only the count of replacements remains. An agent whose traffic leaves through a pool of addresses can raise `agent_session_conflict` without a clone.
- **A server database restored from a backup.** The restored database knows the serial from the time of the backup. An agent that renewed its certificate after that is refused with `certificate_stale` and raises `agent_certificate_rejected`; an agent enrolled after the backup is unknown to the database and is refused without an alert. Neither comes back by itself: enrol the host again with `install.sh --force` and a new join token. There is no switch that trusts a serial, because the server cannot tell a restored database from a stolen certificate. Backed-up data is not affected; see [Cleanup](/docs/guides/gc/#lost-server-database).

## Agent updates

An agent update replaces the binary of a process that runs as root on the host. The server cannot use this path to hand an agent code, because the agent decides what it runs.

**What the agent trusts.**

- The public key of the project, built into the agent binary, and the `*.pub` files in `/etc/lodestore/trusted-keys` on the host. Nothing else counts as a signer, and the server has no message that adds, replaces or removes a key.
- A key file counts only when it passes the same ownership test as a hook: the file and the directory belong to the agent's user (root in the systemd unit), are not writable by group or others, and the file is not a symlink and is at most 4 KiB. `install.sh --trust-key` installs a key that way, as `root:root` with mode 0644 in a 0755 directory.
- The signature covers the binary and a trusted comment, `lodestore-agent <version> <arch>`, under a global signature. The agent checks the SHA-256 the server announced, the signature, that the signed version is the requested one, that the architecture is its own, that the version is newer than the running one, and that the new binary prints its version when started with `version`. It refuses anything else and reports the reason.

**What the server can and cannot do.**

- It can hold updates back by never starting them, or roll out a newer version that a trusted key signed. A rollout of an older signed binary is refused by the agent, so a downgrade is not possible.
- Through an update it cannot give an agent a key to trust, a binary for another architecture, a binary signed by an unknown key, or a binary of its own making.
- Only a token or session with the scope `agents:update` starts, pauses, resumes or cancels a rollout. `hosts:write` is not enough.

**A server that is taken over.**

The signature checks stop a compromised server from installing a binary through the update path, and that is the limit of what they do. A server that is taken over holds the repository keys, reads every backup and can start a restore job on any enrolled host. The agent checks the destination of every job itself, whoever started it, so the job writes only under the restore folders of that host, by default `/var/lib/lodestore/restore`. The attacker can put files of their choosing there. The REST gates do not apply to a server that bypasses REST, so the attacker can also restore owners, setuid/setgid bits and file capabilities inside the folders. The default folder belongs to root and has mode 0700, so no other user on the host can reach it; a restore folder that an administrator opened to other users brings that risk back.

Three kinds of host stay fully exposed, and a restore job is root there, able to replace the agent binary, `/etc/lodestore/trusted-keys`, `/etc/lodestore/hooks.d` and `agent.yaml`:

- a host whose `agent.yaml` has `restore: { allow_in_place: true }`;
- a host whose agent is from 0.1, which does not check restore folders;
- a host whose `allowed_restore_roots` include a system directory such as `/etc` or `/usr`.

On every other host the attacker still starts the scripts of `hooks.d` through a policy with arguments of their choosing, and runs inline commands where `allow_inline` is on. Treat a server compromise as access to all backed-up data and as root on every host of those kinds.

**The installer.**

`install.sh` carries the project's minisign public key. What it checks depends on how it is run:

- With `--from-github` it requires `minisign`, verifies `SHA256SUMS.minisig` with the project key (or a key from `--trust-key`), requires the trusted comment to name the release version, and then checks the agent against the checksum in `SHA256SUMS`.
- Through the server, when `minisign` is installed, it verifies the agent's signature. The trusted comment must name the product and the architecture. The version is not compared, so a compromised server or an attacker on the path can hand out an older signed agent of the same architecture. This rollback risk is left open on this path.
- Through the server, without `minisign`, it checks only the SHA-256 served by the same server and prints a `note:`. That shows the download is intact, not who built it.
- Over plain HTTP the script itself can be replaced, together with the key inside it. `--insecure` means anyone on the network can get root on the host.

The installer trusts the server it was downloaded from. The script, the key inside it and the key shown in Add host all come from that server, so a compromised server can substitute its own key and an agent signed with it. `--from-github` does not change this, because the script that carries the key still comes from the server. This residual risk is accepted. Whoever does not trust the server compares the key and its id `8CA38864EEA52F78` with the ones published on [Binary](/docs/install/binary/#check-the-files) and in `project.pub` of the release tag, and verifies the agent with `minisign -V` using that key before installing it.

**Rollback guard.**

The old agent keeps its binary as `lodestore-agent.prev`, writes a record of the update, and arms a transient systemd timer for 120 seconds before the process restarts. If the new version does not connect and report itself in that time, the timer runs the previous binary's `update-rollback`, which puts it back. A new binary that crashes or never connects is therefore rolled back by the timer. The report of the new version and the timer exclude each other: whichever takes the record of the update first decides, so an update confirmed to the server stays in place. If the previous binary has disappeared there is nothing to put back, and the host reports that instead of a rollback.

Running `install.sh` by hand ends the update: it stops the timer and removes the record of the update and `lodestore-agent.prev`. An agent that starts with a version other than the target of the update drops the record as well, so the guard does not replace a binary installed by hand.

**Residual risk.**

If the host reboots inside the two-minute window, the transient timer is lost. The agent that starts afterwards puts the guard back for the rest of the window, or rolls back at once when the window has already run out. The only gap is a reboot in the window combined with a new binary that dies before its start-up code (`on_start`) has run: then nothing re-arms the guard and nothing rolls back. The server still notices. It shows the update as failed once its deadline passes (`rolled_back`, the alert `agent_update_failed`), or, if the report of the switch never reached it, the host appears offline (`agent_offline`). Run `install.sh` on the host to repair it.

## Join tokens and the setup link

- A join token carries 256 bits of randomness. The database stores only its SHA-256. It works once and expires after one hour by default.
- The install command passes the token in the arguments of `sh`, so it is briefly visible to local users in the process list on the host being enrolled. Treat it as a short-lived secret and do not paste it into shared channels.
- The first-run setup link is printed to the server log once. Whoever reads the log before the administrator is created can create the administrator, so restrict access to the log or use the Helm `Secret` to set the administrator password up front.
- The server has no TLS on the REST and UI port. Terminate TLS on a reverse proxy, otherwise sign-in cookies and tokens cross the network in clear text. See [networking](/docs/reference/networking/).

## Signing in and sensitive actions

The administrator signs in with a password and gets a session cookie. The sign-in is the target of guessing, and a session that someone else holds is the way to a token, a join token or a restore, so these have limits of their own.

**Limits on sign-in.**

- Only failed attempts count. Per client address and user name the limit is 5 a minute, and per client address 30 a minute. A client address is the address of the TCP connection, or, behind `trusted_proxies`, the address from `X-Forwarded-For`; IPv6 clients are grouped by their /56 prefix. Without `trusted_proxies` behind a reverse proxy every client has the address of the proxy and shares these limits.
- A user has a limit of its own: 60 failed attempts an hour, counted for a user that exists, so names that do not exist cost nothing there. It does not lock out an address from which the administrator has signed in (the server keeps up to 16 of them per user in memory, and a request that carries the user's live session counts as one). An address the server has not seen can be refused while a guess is going on, and also right after a restart, because the list of known addresses is in memory only and starts empty. Behind a reverse proxy without `trusted_proxies` the limit for a name does not hold: all clients have the address of the proxy, which becomes a known address after the first successful sign-in.
- The hashing of passwords (Argon2) runs through a gate: at most twice the number of CPU cores (between 2 and 32) at once, and a request that waits more than 2 seconds gets `503` `busy` with `Retry-After`. A refused request spends none of the attempts above, so a flood of sign-ins cannot lock the administrator out by itself, and it cannot make the server hash without bound.
- A new password may have at most 1024 bytes, and a password over 4096 bytes is refused before it is hashed or counted. A longer password that was set earlier still works up to that size.

**Entering the password again (step-up).** A session can create an API token, create a join token and start a restore that writes in place, restores owners or targets an agent without the capability `restore_roots_v1` only if its password was entered in the last 15 minutes. Signing in counts. Otherwise the answer is `403` `step_up_required` before anything is created, and `POST /api/v1/auth/step-up` opens the next 15 minutes. A wrong password there counts against the per-address limits of a sign-in (not the limit for a user name), and five wrong ones in a row end the session; that counter is in memory. A wrong current password when changing the password, and a failed sign-in that carries the cookie of a live session of that user, count into the same counter, so a stolen cookie cannot guess the password through those either. A session of the demo and a session that was open before the update has no such time, so it is asked at its first dangerous action. This limits what a stolen session cookie does without the password; it does not stop someone who also knows the password. An API token never needs a step-up, and it cannot create tokens or join tokens at all (see [API tokens](#api-tokens)).

**Changing the password.** It ends every other session of the administrator, and the request may ask to revoke all API tokens too (`revoke_tokens`); the join tokens that nobody has used yet then expire in the same step. Without that choice the tokens stay valid, because a script that uses one would stop without warning.

## Notifications and outbound requests

Webhook, Slack and Telegram deliveries are requests from the server to an address that the administrator, or whoever holds the interface, typed in. They are filtered so that a channel cannot be used to reach what the server can reach and the administrator cannot.

- The server resolves the name itself and refuses an answer in a blocked range. Always blocked: link-local addresses (`169.254.0.0/16`, `fe80::/10`, which holds the metadata service of AWS, Google Cloud and Azure), `100.100.100.200` (Alibaba Cloud), `fd00:ec2::254` (AWS over IPv6), the unspecified, multicast and broadcast addresses, `0.0.0.0/8` and `240.0.0.0/4`. Blocked unless `notifications.allow_private_targets` is `true`: loopback, the private ranges of RFC 1918, `100.64.0.0/10`, `192.0.0.0/24`, `198.18.0.0/15`, `::1`, `fc00::/7`, `fec0::/10` and `64:ff9b:1::/48`. An IPv6 address that holds an IPv4 address (mapped, compatible, NAT64 `64:ff9b::/96`, 6to4 and Teredo) is judged by the IPv4 address in it, so it cannot be used to get around the table.
- Requests do not follow redirects and time out after 10 seconds. The client ignores `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` of the server's environment: an address filter that a proxy can bypass is no filter.
- Email resolves the SMTP host once, applies the same table and connects to the address it checked, and checks the TLS certificate against the host name.
- `notifications.proxy` in `server.yaml` (an `http://` or `https://` URL, which may carry a user name and password that are kept out of debug output and of the error text of a delivery) sends webhook, Slack and Telegram requests through that proxy. The server then no longer resolves the name of the target: the proxy does, so the filter checks only addresses written as numbers in the URL, and the filtering of names is the proxy's job. Email does not use the proxy and still connects directly.

## Limits against a flood

- REST and the metrics port close a connection that does not send a complete request head within 10 seconds, the pause between two requests on one connection included. Bodies and responses are not timed, so a long download or the stream of a log is not cut.
- gRPC: the TLS handshake of an agent has 10 seconds, a connection holds at most 32 streams at once, the server accepts at most 4096 connections and drops the next ones at once, and an agent that opens a session and sends no `Hello` within 10 seconds is disconnected.
- A host has at most 8 open CLI jobs, the jobs that the agent reports from its local socket. A job over the limit is refused and the agent is told to forget it; results of jobs that the agent finished while offline are always recorded. This keeps a local user, or a compromised agent, from filling the job table.

## Helm defaults

The chart's pod runs with a read-only root filesystem (the server writes only to its data volume and to a 64 MiB `/tmp`), as user 65532 with the seccomp profile `RuntimeDefault`, no privilege escalation and no capabilities. It has a ServiceAccount of its own with no token mounted, since the server never talks to the Kubernetes API. A NetworkPolicy restricts ingress: the web and agent ports are open to every source, and the metrics port, which has its own Service, only to the sources in `networkPolicy.metricsFrom`. The metrics port answers without a token, so keep it off ingress. Egress is open unless you set `networkPolicy.egress`. See [Deploying with Helm](/docs/install/helm/#pod-security-defaults).

## What an agent sees during a restore

A restore job runs on the target agent, and the server decides what that agent receives. The master secret never leaves the server. The decision is recorded in [ADR 0004](/docs/adr/0004-restore-data-path/).

**What the agent receives for a job.**

- **A plan of the selection only.** The server opens the snapshot, walks the selected subtrees with its own keys and streams the entries it finds: names, modes, owners, times, links, extents and, for each file, the list of chunks as pack, offset and frame length. Directory trees are not sent as blobs, and snapshot keys and the master secret are not sent at all. The agent learns the paths and metadata of what it restores and nothing about the rest of the snapshot.
- **The keys of the packs the plan uses.** Each pack key opens the frames of that pack and no other pack. The set of packs issued to a job is kept by the server, and a refresh or a ciphertext read for a pack outside that set is refused. The set is dropped when the job finishes or is interrupted.
- **Presigned URLs.** On S3 the server signs a `GET` for each issued pack, valid for one hour, and the agent reads the frames it needs with `Range` requests. The agent asks for fresh URLs through `RefreshPackAccess` when a link is close to expiry or refused, and only for packs already issued to the job. A URL grants read access to that one object until it expires, so it is kept in memory, never logged and left out of error messages.
- **The identity of the source repository: `repo_id` and `k_id`.** To check a chunk against its keyed hash and to compare files with what is already on disk, the agent needs the chunk-hash key of the repository the snapshot came from. `k_id` is a derived key, not the master secret, and without access to the bucket and the index it opens nothing. It is handed over only to the agent that the administrator chose as the target of a restore, including an agent of another repository (a new machine replacing a dead one). It lives in the job assignment, is wiped from the agent's memory after the run and is never written to disk.

**What the agent still holds after a restore.**

- **Neighbouring chunks of a pack.** A pack key opens every frame in its pack, not only the chunks the plan names. An agent that keeps the key can decrypt the other chunks of those packs if it can also read the pack, which its own S3 key cannot do (below). This residue is accepted: packs are 32 MiB, the key is held in memory only for the job, and the agent has no read access to the bucket.
- **The target's own S3 key still cannot read packs.** The key an agent holds is write-only, and a restore does not change that: the test `restore_s3_agent_key_cannot_read_packs` tries a direct `GET` of pack objects with it and expects a refusal. Data reaches the agent only through presigned URLs for the packs of its job.
- **Storage without presigning.** The local folder cannot sign URLs, so the server reads the requested pack ranges and relays the ciphertext to the agent over gRPC, `ReadPackRange`, in parts of at most 1 MiB, for packs issued to the job only. It does not decrypt anything for the agent. The path is the same when the repository sits on the agent's own machine.

**Where the agent writes.**

- The agent runs as root and confines every restore itself. A restore into a new folder must lie under one of the restore folders, the list `restore.allowed_restore_roots` in the host's local `/etc/lodestore/agent.yaml`. Without the key the only folder is `/var/lib/lodestore/restore`, which the agent creates with mode `0700`. A restore **in place** runs only where `restore.allow_in_place: true` is set, which an administrator does in `agent.yaml` or with `install.sh --allow-in-place-restore`; it is off by default. The server cannot change either setting and no message does: only someone who can write `agent.yaml` on the host, who is root already, can. The interface asks for explicit confirmation before it sends a restore in place. The default is a new folder, and files that exist in the target but not in the snapshot are never deleted.
- The agent makes this check for every job, whether a session, an API token or a server that is taken over started it. The server answers early with 400 `restore_outside_roots` or `restore_in_place_disabled` from the folders and the flag the agent reported, and an API token cannot queue a restore on an agent that does not report the capability `restore_roots_v1` (400 `restore_agent_outdated`). The server checks the capability again when it hands a token's job to the agent, and fails the job with `restore_agent_outdated` if the agent no longer reports it, for example after a rollback to 0.1. These answers are hints; the agent decides. The agent opens the restore folder and then the rest of the path without following a symlink below the folder, so a link planted inside a folder cannot lead a write out of it.
- Restoring file owners, setuid/setgid bits, file capabilities, POSIX ACLs and the extended attributes `security.*` and `trusted.*` (`restore_owners`) is the way a restore can leave a root-owned setuid file or a label that a security module acts on. Without `restore_owners`, whoever started the job, the agent and `lode server restore --no-owners` skip every attribute in `system.*` (all ACL kinds), `security.*` and `trusted.*` without a message, and restore `user.*` as before. The local `lode restore`, run by whoever holds the bucket, always restores them. Through the REST API a token needs `restore:in-place` for it: a token that holds only `restore:host` (or `restore:download`) gets 403 and can restore files without those bits and capabilities only. Sessions are not affected. The agent adds its own rule, whoever started the job: a restore into a new folder never keeps setuid, setgid or file capabilities, even with `restore_owners`; the owners are restored and the bits and capabilities are dropped. Only a restore in place, which the host allows with `allow_in_place`, keeps them. A server that is taken over therefore cannot leave a setuid-root file in a restore folder that other users can reach. `lode server restore` asks for owners by default, so a token with only `restore:host` must add `--no-owners`. A server that is taken over bypasses REST and is limited by the restore folders only, as described under [Agent updates](#agent-updates).
- What is not limited: a restore in place on a host with `allow_in_place: true` writes any path of the host as root, and the restore folders do not apply to it. An agent from 0.1 has no restore folders: a session restores anywhere through it, and a token cannot restore to it. A restore folder is only as safe as the folder chosen: a system directory or a folder that other users can write to gives back the risk it was meant to remove.
- Names in the plan are validated again on the agent and every write goes through directory descriptors with `*at` calls, so a hostile plan cannot reach outside the target through `..` or a symlink.
- The target path itself is opened one component at a time. Missing folders are created `0700`. A component that a local user other than root could swap is refused: a symlink that user owns, or a folder that user owns when others can write to it or to the folder it sits in. The default location `/var/lib/lodestore/restore` sits under root-owned folders, so a local user can neither plant nor redirect it; a custom target under a world-writable folder can at most be made to fail.

**Re-enrolment and the previous agent id.**

- A host that is enrolled again may claim its earlier `agent_id`, and the server then binds the snapshots of that id to it. This only changes which host the interface offers as the original one. The agent is write-only and cannot read snapshots, so claiming an id gives it no data. A host that took over another id could, however, be offered "restore to the original host" in the interface, a social-engineering risk. Join tokens are issued by the administrator only.

**How much of a tree an operation walks.** A snapshot from a host with the writer keys can have directories that share subdirectories, so a few kilobytes of trees describe a path count that nobody could finish. Every operation that walks a snapshot (a restore, a listing, an archive download, the plan of a restore for an agent, a search) has a budget of 2^30 entries and 512 GiB of directory data, and every visit counts, also a visit to a subdirectory it has already seen through another parent. Four more limits apply to what a single directory and a single operation hold in memory: one directory may have at most 2^23 entries and 1 GiB of tree data, and an operation may hold at most 2^24 entries and 2 GiB of tree data at once across the directories it has open. Tree data is the decoded length of the pieces of a directory, with the lists of pieces of its subdirectories; every open directory is counted at its full length and not at what is left to hand out. A directory of a few nodes can carry huge lists of chunks, so the bytes are limited as well as the entries. A directory whose pieces already add up, by the sizes in the index, to more than the limit is refused before any piece is read, and the number of entries of a piece is counted before the piece is decoded. The writer of a backup refuses a directory above these limits and a path whose open directories together pass them, and writes no snapshot, so what a backup finishes can be restored with these four limits; the whole-walk budget is checked only by the operations that walk, so a tree above 2^30 entries still backs up and then stops a restore. The same limits of a directory and a path apply to the parent snapshot that `lode backup` reads to skip unchanged files, counting the directories of the parent it holds along a path; a parent that passes one is dropped, the backup reads the remaining files whole and records an issue. The limits count tree data as it is stored, by the decoded length of the pieces, not the memory the decoded entries take; a restore checks the tree before it writes and then holds the top directory twice, so at its peak it holds up to one directory more than the limit of a path. When a limit is reached the operation stops with an error that names it (`entries in one directory`, `bytes in one directory`, `entries held at once`, `bytes held at once`, `entries`, `bytes of directory data`). `lode restore` and `lode ls` print that error. Only `lode restore` adds, for the four limits of a directory and a path, the flag `--allow-large-directories`. A restore job for an agent fails with that text, and a search ends as incomplete with `stop_reason` `walk_limit`. The integrity check, `lode check` and the server's scheduled check alike, applies the four limits to every directory it reads, counting the directories above it at their full length the way a restore does. A snapshot that passes one is reported as the finding `unreadable_tree` with the limit named, and the check goes on with the other snapshots. The check sizes directories and files by all index shards, a restore by the shards its snapshot names until a blob is missing from them. A shard planted by a holder of the writer keys can copy the real records with other sizes, and a snapshot that names only it would then stop a restore at a limit, or make it read and charge chunks, that the check over all shards passes. So where the copies of a blob disagree on its size, the check keeps the length it read for each such tree and the size it used for each such chunk of a file that added up, and after the walk reports every snapshot that names a shard listing a tree larger than that, or such a chunk at another size, as `unreadable_index`; for this it holds the blobs whose copies disagree, those lengths and the index shards each snapshot names until the run ends, none of it in a repository no planted shard has touched. This is a finding whatever the limits, so a planted shard can make the check report a snapshot whose restore would succeed, never the reverse. When several snapshots share a directory, every one that reaches it gets a finding in or below it, not only the first one the check reads, except for findings below a directory whose subtree alone passes a limit of a path (see below). A snapshot that would pass the walk budget of a restore is reported as `unreadable_tree` with the text of one of the errors a restore gives (for a snapshot over both counts, entries and bytes, a restore may stop on the other one first), and its tree is not expanded, so trees that describe 2^40 visits are read once for each directory they are a piece of, also when a directory lists the same piece many times; the bytes of such a piece count every time it is listed, as in a restore. The check reads each directory at most once, however many paths lead to it, and for each remembers how many entries and bytes a path holds from it down and how deeply it is nested, so a snapshot is judged by its own path in whichever order the snapshots are read. A directory whose subtree alone passes a limit of a path (entries or bytes held at once, or nesting) is a finding for every snapshot that reaches it, and the check may not walk the rest of that directory. Besides what it remembers about each directory it has read, the check keeps the members of hardlink groups in those directories until the run ends. It also keeps, until the run ends, the id of every distinct chunk the directories it read name, and for every chunk or tree it found unknown or unreadable the text of that finding, so that each later snapshot that reaches it gets the finding too. Neither is bounded by the limits of a path: a planted directory of 1 GiB of tree data that names random chunk ids no shard describes holds about 30 million ids and as many findings, roughly 5 to 7 GB. For the directories it is still walking it holds up to the limit of a path plus one directory: a directory is decoded before its path is compared with the limit. For the directories on the way down whose subtree alone takes the path over a limit it holds a fixed amount for each directory. Each directory is read once, so there are no more of these amounts than directories read, as with what the check remembers about them; this part is not bounded by the limits of a path, nor by the depth. The members of a hardlink group are compared within one snapshot, so a snapshot that shares a directory with a planted one, and does not have the other member, gets no finding and restores, while the snapshot that has both members gets the finding and a restore of it fails. The check never lifts these limits. The API answers `400` `tree_too_large` for a listing, a summary and the preparation of an archive, which all stop before the response starts. A download of an archive that reaches a limit after the stream has begun cannot change the status any more: it ends without the end of the archive, so the file is incomplete and does not open as a whole. `lode restore --allow-large-directories` lifts the four limits of a directory and a path for that process only, for snapshots written before backups refused such trees; each such directory is then held in memory whole, and the budget of the whole walk stays. The server never lifts them. Two operations in a row each get the whole budget. Cleanup does not use the budget: its marking step visits every tree once. The numbers are estimates, not measurements.

**Download as an archive is the exception.** Downloading a selection as `tar.gz`, `tar.zst` or `zip` is the one place where the server decrypts data for a person. The server streams the archive to the browser without temporary files, and no agent is involved. A `tar` archive (`tar.gz`, `tar.zst`) carries every extended attribute of the snapshot, ACLs and `security.*` and `trusted.*` included, as `SCHILY.xattr.*` records, whatever the owner switch of a restore says. What happens to them is decided by whoever unpacks it: GNU `tar` applies them only when it is given `--xattrs` (and `--acls` for ACLs), so do not pass those options for an archive you do not trust to carry only what you expect.

## Backup hooks

A backup policy can run a script on the host before and after a backup. The server chooses which hook runs and with which arguments, and the agent decides whether it may run.

**What the boundary guarantees.**

- The agent runs only a regular file in `/etc/lodestore/hooks.d` that the administrator installed. The file must be owned by the agent's user (root in the systemd unit), must not be a symlink, and must not be writable by group or others. The directory has to meet the same rules. Anything else is refused with `hook_rejected`, and a missing script is `hook_missing`.
- A policy cannot create a script: it only names one, and `hooks.d` is writable only by root on the host. Through a policy a compromised server can only pick among the scripts that are already there. A restore job is a different path, but `hooks.d` and `agent.yaml` lie outside the restore folders by default, so the agent refuses to write them. If an administrator puts `/etc` (or a folder that contains it) into `allowed_restore_roots`, or turns on `allow_in_place`, a server that is taken over can write them again and this boundary does not hold against it (see [Agent updates](#agent-updates)).
- An inline `command` runs only when `/etc/lodestore/agent.yaml` contains `hooks: { allow_inline: true }`. A policy cannot set this flag, and a restore job cannot write the file unless `/etc/lodestore` lies inside a restore folder or in-place restore is on, as with `hooks.d`. The file counts only when it is owned by the agent's user and is not writable by group or others; otherwise the flag is off. `agent.yaml` is separate from `agent.json`, so `install.sh --force` keeps it.
- Arguments reach the script through `execve`, never through a shell. The hook gets an empty environment except `PATH`, `LODESTORE_POLICY`, `LODESTORE_JOB_ID`, `LODESTORE_HOOK_PHASE` and, for the post hook, `LODESTORE_BACKUP_STATUS`. S3 keys, writer keys and proxy settings are not passed. Standard input is `/dev/null`.
- Through an API token, changing hooks needs `hooks:write` as well as the scope of the route: creating a policy with hooks, and adding, changing or removing hooks of one. So does widening a policy that has hooks: any change of the repository, and any change of the selector that is not provably narrower, whichever hosts are enrolled at that moment. Only two selector changes count as narrower: a shorter list of `hosts`, or the same `matchLabels` with more labels added. An empty selector, a label that is removed or changed, a host id that is not enrolled yet and a switch between a host list and labels all need `hooks:write`. New host labels that bring a host under such a policy need it too (this one is judged against the policies as they are now). `lode apply` is gated the same way, dry runs included. The 403 reads "The token needs the hooks:write scope to change hooks or the hosts they run on (policies: a, b)." and names the policies. Deleting a policy needs only `policies:write`, and hooks that a policy already has are not touched by an upgrade. Sessions are not restricted.
- A hook runs in its own process group. On timeout (one hour by default, set in the policy) or cancel, the group gets SIGTERM and, after 10 seconds, SIGKILL, so child processes end as well.

**What it does not guarantee.**

- A compromised server can still pass hostile arguments to a powerful installed script. Write scripts to validate `$@`, and prefer scripts that take no arguments.
- The hook runs as the agent's user, which is root. Anyone who can write `hooks.d` or `agent.yaml` already owns the host.

**Writing hooks.**

- Hooks inherit the agent's systemd sandbox: `NoNewPrivileges`, `PrivateTmp`, `ProtectKernelTunables`, `ProtectKernelModules`, `ProtectControlGroups`, `RestrictAddressFamilies`, `LockPersonality`, `RestrictRealtime`, `ProtectClock`, `ProtectHostname`, `ProtectKernelLogs` and `SystemCallArchitectures=native`. Namespace restrictions and a read-only file system are not applied, so mount and `unshare` based hooks still work.
- `NoNewPrivileges` makes `sudo` fail. To run a step as another user, use `runuser -u <user> --` or `setpriv`.
- `PrivateTmp` gives the agent and its hooks a private `/tmp` that is not the host's `/tmp`. A dump written there is invisible to the database process, and a policy path under `/tmp` backs up the private tree. Write dumps to `/var/lib/lodestore/staging` or `/var/backups`.

## API tokens

An API token lets a script or CI job reach the REST API without a browser session. It is the boundary between the CI environment and the server, and the token is the only credential that crosses it.

- **Scopes.** A token carries a list of scopes chosen by the administrator. Each token-enabled route names one scope through the `Scoped<S>` extractor and rejects a token without it with `403`; the 403 names the missing scope. A route that does not use the extractor accepts sessions only, so a new route is closed to tokens until someone opts it in. A test lists the session-only routes (token management, join tokens, repositories, catalog, server settings, the administrator account) and checks that a token holding every scope still gets `401` there. Some actions need a second scope on top of the one the route names; the table lists them.

| Scope | What it allows | What it does not allow |
| --- | --- | --- |
| `hosts:read` | Read hosts, the fleet overview, alerts and the state of agent updates. | Change anything. It shows no file names and no snapshot contents. |
| `hosts:write` | Set the labels of a host, revoke a host. A host that carries a label is picked up by every policy that selects that label. | Change a label that brings a host under a policy with hooks, unless the token also has `hooks:write` (policies are named in the 403). Issue join tokens (session only). Update agents, which is `agents:update`. Run jobs. |
| `alerts:write` | Silence and unsilence the alerts of a host. A silenced host raises no notification. | Change thresholds or notification channels (session only). |
| `agents:update` | Start, pause, resume, cancel and dismiss an agent update. A started update makes hosts, at the moment the token picks, install a newer agent binary from the server's agent directory that the project key or a key in `/etc/lodestore/trusted-keys` has signed; the agent restarts. The token can also hold updates back by never starting them or by pausing one. | Install a binary the server built or one signed by an unknown key, roll an agent back (an agent refuses an older version), install a binary for another architecture, or add a trusted key to a host. The agent decides on every one of these, not the server. `hosts:write` does not include `agents:update`. |
| `policies:read` | Read policies, validate a policy, preview what a retention rule would forget. | Change anything. |
| `policies:write` | Create, change and delete policies, `POST /api/v1/policies/apply`, change the check settings of a repository. A change of paths, selector or schedule decides what is backed up and when, and deleting or narrowing a policy stops backups. | Set or change retention, make a policy with retention run more often, or change `includeStdin` without `snapshots:delete`. Change hooks, or the hosts a policy with hooks runs on, without `hooks:write`. A token that holds only `policies:write` therefore cannot make the server delete snapshots or run a command on a host. |
| `hooks:write` | Second scope only: together with `policies:write` or `hosts:write`, change `spec.hooks` of a policy (add, change, remove) and widen the hosts of a policy with hooks (selector, repository, host labels). A hook runs as the agent's user, which is root. | Do anything by itself: every route that it unlocks needs the scope of the route as well. Install a script into `hooks.d` or turn on `allow_inline` on a host: the agent runs only scripts that the administrator installed, and inline commands only where `agent.yaml` allows them. |
| `jobs:read` | Read jobs, their events and the results of integrity checks and cleanup. | Start or stop anything. |
| `jobs:run` | Run a policy or a host now, rerun and cancel a job, start and cancel an integrity check, dry-run or abort cleanup. A token starts a policy on a host at most 6 times in an hour (see [Retention and forgetting snapshots](#retention-and-forgetting-snapshots)). | Change what a policy backs up. Restore, download, delete a snapshot or start a cleanup that deletes. |
| `metrics:read` | Read `/metrics`: host names, policy names, sizes and times. | Anything else. |
| `snapshots:read` | List snapshots and browse their file trees, search for a file across hosts. This shows paths and metadata. | Read file contents, which is `restore:download`, or write them to a host, which is `restore:host`. Delete or mark a snapshot. |
| `snapshots:delete` | Delete a snapshot, mark or unmark it as suspicious, run cleanup and change its settings, and as a second scope: set or change retention, make a policy with retention run more often, and change `includeStdin`. A new schedule with no two runs in the next 366 days, or one the server cannot scan within 100000 runs, counts as more often than a schedule that has them. These are the ways to make the server forget snapshots. | Delete a version that Object Lock still protects. Make a retention rule forget the two newest good snapshots of a pair: that floor holds, while `DELETE /api/v1/snapshots/{id}` removes any snapshot. Read file contents. |
| `restore:download` | Read backed-up data through the server: prepare an archive download and fetch the archive (`tar.gz`, `tar.zst`, `zip`). The server decrypts the data for the caller. | Write to any host. |
| `restore:host` | Start a restore into a new folder on an enrolled host, under a folder in that agent's `allowed_restore_roots` (by default `/var/lib/lodestore/restore`). The agent refuses any other path. Any snapshot can be written to any enrolled host, so the token reads data too, for whoever can read that folder (by default only root). | Restore in place. Restore file owners, setuid/setgid bits or file capabilities (`restore_owners` needs `restore:in-place`; the 403 names it). Write outside the restore folders. Restore to an agent that does not report `restore_roots_v1` (400 `restore_agent_outdated`). It does not include `restore:download`. |
| `restore:in-place` | Restore in place, writing the original paths of the host, and restore file owners, setuid/setgid bits and file capabilities. It works only on a host whose `agent.yaml` has `restore: { allow_in_place: true }`; elsewhere the agent refuses (`restore_in_place_disabled`). The agent runs as root, so on such a host this scope writes any path as root. | Restore into a new folder (that is `restore:host`). Restore an unsigned snapshot in place (`restore_unverified_in_place`). |

A restore into a new folder is `restore:host` and a restore in place is `restore:in-place`; neither includes the other, and neither includes `restore:download`. A token issued before the upgrade that held `restore` was changed to `restore:download` only.

- **Storage.** Only the SHA-256 hash and the first characters of the token are stored. The secret is shown once, so the database and its backups do not hold a usable token.
- **Revocation.** Every request looks the token up in the database, so a revoked or expired token stops working at once. There is no cache to wait out.
- **No CSRF with Bearer.** The browser does not attach an `Authorization` header by itself, so a Bearer request cannot be forged from another site. Session requests keep their CSRF check. A request with a Bearer header is never mixed with the cookie: the token alone decides.
- **Audit.** A restore or download started by a token records `token:<name>` as who started it.
- **Plain HTTP.** A token sent over HTTP without TLS can be read on the network. Serving the API over TLS, or keeping CI and server on a trusted network, is the operator's job. `lode` warns when it sends a token to a non-loopback `http://` address.
- **What a stolen token gives.** Everything its scopes allow and nothing else; read the table for the scope in question. The scopes that read backed-up data are `restore:download` (through the server) and `restore:host` (written to a host), so give them to few jobs and use short expiry. The scopes that can lead to commands as root on hosts are `restore:in-place` on a host that allows it, `hooks:write` together with `policies:write`, `hosts:write` or both (hooks run as root and an inline command runs wherever `allow_inline` is on), and `agents:update`, which can make hosts install a newer agent binary that a trusted key signed. The scopes that can make the server delete are `snapshots:delete` and, together with it, `policies:write`. A token cannot create other tokens, change the password or touch repositories.

## Retention and forgetting snapshots

After every backup that ends as succeeded or with warnings, the server applies the retention rules of the policy to one pair: the policy and the host. It deletes the `snapshots/<id>` object with its own credentials and removes the catalog row. Packs are never touched here; unreferenced data is the business of garbage collection.

**What the boundary guarantees.**

- Only the server forgets. The agent key is write-only and cannot delete, so a compromised agent cannot forget anything, its own snapshots included.
- A pass looks only at snapshots that carry the tag of its policy, sit in the repository of the policy and were bound to their host by the server: the host is recorded when the agent reports a finished job on its own authenticated session. A snapshot that the catalog sync merely found in the bucket gets its host from fields the agent wrote into the manifest (`agent_id`, `hostname`), so it is kept in the catalog but never counts toward any rule or the floor and is never forgotten by retention. Snapshots of other policies, manual `lode` snapshots, stdin snapshots (with or without `--policy`, unless the policy opts in below) and snapshots of a deleted policy are never counted and never forgotten.
- The object key comes from `snapshot_object_key` for a 64-character hex id that is already in the catalog. No path from a user or an agent is used.
- A compromised agent can flood its own pair with fresh snapshots to push good ones out of the retention window. The damage is limited to that pair and host, because only snapshots linked to a finished job of that host count, so a compromised agent cannot plant manifests that claim another host and displace its history. A snapshot marked suspicious (by the anomaly detector or by an administrator) counts toward no rule and is never forgotten, and the two newest good complete snapshots of a pair are always kept, even with `keepLast: 1`.
- Receive time, not the time written by the agent, orders the snapshots, so an agent cannot move a snapshot in or out of a window with a forged clock. If the receive time of any snapshot in a pair is not yet confirmed by the storage (a catalog rebuilt from a database that predates the receive-time column, or a backend that reports no modification time), the pass is postponed and a warning is written to the job log, because buckets computed from estimated times could collapse and drop history.
- Only snapshots the server has signed count (see [Snapshot provenance and `latest`](#snapshot-provenance-and-latest)). A snapshot that nothing signed takes no slot in any rule, does not push a signed one out of a window and is never forgotten by retention; an administrator can still delete it. A host that plants a hundred snapshots with the writer keys therefore cannot displace its real history. Its real backups are another matter: they are signed, and a compromised host can still make enough of them to push its own older history out of the window.
- Incomplete snapshots take no slot in any rule, and no rule forgets them; they are neither counted nor deleted by retention.
- **Two pools per pair.** The snapshots of a pair are counted in two pools: scheduled (`schedule` and `catchup` jobs) and manual (run-now). The rules and the floor apply to each pool on its own, so the two newest good complete snapshots of each pool are always kept. A stream of manual runs rotates only manual snapshots and never touches the scheduled history. A run-now that is queued or running when a slot comes does not take the slot: the scheduled backup runs after it, so a run-now cannot stand in for the scheduled snapshot. The pool is stored with the snapshot (`snapshots.origin`), so it survives the removal of old job records.
- **stdin snapshots stay outside retention.** A snapshot from `lode backup --stdin --policy X` takes no slot and is never forgotten by retention, and it is not the policy's last successful backup for the alert on a missed backup, the metrics or the anomaly baseline. The policy opts in with `spec.retention.includeStdin: true`; stdin snapshots then join the manual pool. Changing `includeStdin` through a token needs `snapshots:delete`. This agrees with [the local socket reference](/docs/reference/local-socket/#jobs).
- **A token needs `snapshots:delete` to change what the server forgets.** Creating a policy with `spec.retention` or changing it (`includeStdin` included) needs the scope in addition to `policies:write`, since a tighter rule makes the next backup delete older snapshots. So does making the schedule of a policy with retention run more often: the server compares the smallest gap between two runs over the next 366 days, in the time zone of the policy, before and after the change, and a smaller gap needs the scope. A new schedule with no two runs in that year (such as `* * 29 2 *`) or one too dense to scan within 100000 runs counts as smaller, since the server cannot show it is not. A cron limited to some months, such as `0 3 * 12 *` (daily in December), is caught in any month. A rarer schedule or a shifted time needs only `policies:write`, and a schedule that is not changed is not scanned. `lode apply` applies the same rules, dry runs included. Sessions are not affected.
- **Run-now limit.** A token starts a policy on a host (run a policy, run a host, rerun a job) at most 6 times in an hour per pair of policy and host; the seventh request gets 429 `rate_limited` with a `Retry-After` header. Sessions are not limited, but their runs count in the same hour. The count is read before the jobs are created, so two parallel requests can get a seventh run through: the limit is exact for sequential requests and allows at most 7 under a race. The limit is a constant and is not configurable, and the scheduler is not subject to it.

**When the storage refuses the delete.**

- With Object Lock or versioning, a plain delete succeeds by adding a delete marker; the earlier version stays in the bucket. The catalog and `lode` no longer see the snapshot, and no tombstone is needed.
- If the storage answers "access denied" (a server key without `s3:DeleteObject`, a lock rule that forbids it), the server writes a tombstone, removes the row from the catalog and adds a warning, `Could not delete snapshot <id>: <reason>`, to the log of the backup job. The job stays succeeded. The tombstone stops later catalog syncs from bringing the row back while the object is still in the bucket; it is dropped when the object disappears. A catalog sync retries the delete at most once a day for a tombstoned object that is still listed, and drops the tombstone when the delete goes through.
- A temporary backend error leaves the row in place and the next pass retries.

**What the markers do not protect against.**

- Suspicious marks and the anomaly details live in the database only. If the database is lost and the catalog is rebuilt from the bucket, the marks are gone; the rebuilt snapshots are not bound to a job, so retention neither counts nor forgets them, and old history simply stops being rotated. The mark "signed" comes back from the bucket during the rebuild, but the host and the job of a snapshot do not.
- Retention can still be steered within the limits above. A stream of manual runs, up to 6 an hour per pair, pushes older manual snapshots out of the manual pool, for example a manual backup taken before a risky change; the scheduled history is not touched. A session or a script with `jobs:run` that runs every hour for days does the same.
- Snapshots whose job record the server had already deleted when the pool column was added (older than 90 days) count as scheduled, because nothing says otherwise; a run-now snapshot of that age is therefore rotated with the scheduled pool.
- A forgotten snapshot cannot be brought back without bucket versioning. The interface shows a preview of what a rule change would forget and asks for confirmation before it saves a tighter rule, to guard against an accidental change.

## Garbage collection and storage keys

Forgetting a snapshot only removes its manifest. Space comes back when the server runs garbage collection, which deletes packs and index shards that no remaining snapshot references. Deletion is a server-only act.

**What an agent key can do around `locks/`.**

- Read: the agent key may list and read `locks/`. Garbage collection publishes the candidate packs of a cycle there, and a running backup checks them before it reuses an existing pack.
- Not write: the agent key has no `PutObject` on `locks/`, so a compromised host cannot plant a candidate list or block a collection cycle with markers that never close.
- Not delete: no `Delete*` action is granted on any prefix. On a bucket with versioning or Object Lock this covers deleting a version by its version id as well.
- `locks/attest-*`: the objects that carry the server's signature over index shards, and the signed record of who made each snapshot, are written only by the server (and, for provenance, by `lode backup` with the repository password). A compromised host can neither write one nor make one verify. See [Index metadata from a compromised agent](#index-metadata-from-a-compromised-agent) and [Snapshot provenance and `latest`](#snapshot-provenance-and-latest).

**A snapshot that cleanup cannot follow.** An agent with the writer keys can put an object under `snapshots/` that does not open, or a snapshot whose root tree is not in the repository. Cleanup cannot tell what such a snapshot references, so it deletes nothing on a guess. In 0.1 one such object stopped every later cycle until someone removed it from the bucket by hand. Now the cycle puts every snapshot it cannot follow into **quarantine**, continues reading the others, stops before it publishes a list of packs to delete, and raises the alert `snapshot_quarantined`. Nothing is deleted while the quarantine holds a snapshot nobody has confirmed.

- To carry on, an administrator with `snapshots:delete` confirms each quarantined snapshot with `POST /api/v1/repositories/{id}/gc/quarantine/{snapshot_id}/exclude` or **Exclude from cleanup** in the interface. A confirmed snapshot is no longer protected: the next cycle may delete the data that only this snapshot uses. The confirmation is a decision to stop protecting it, not a statement that it is safe or that the data can be recovered.
- A snapshot that belongs to a backup job cannot be confirmed. That is a snapshot whose catalog row names a host and a job, or one that a server-signed record names (see [Snapshot provenance and `latest`](#snapshot-provenance-and-latest) and [ADR 0006](/docs/adr/0006-snapshot-provenance/)). A real backup that no longer opens is damage to repair with a check, or to delete as a snapshot, not to ignore. A snapshot that retention has already forgotten, but that the storage still keeps (for example under Object Lock), is bound to no job and can be confirmed.
- A confirmation made while a cycle is running is kept. It is removed by itself when the snapshot reads again or is gone from the bucket; if it breaks again later, the snapshot is back in the quarantine and needs a new confirmation.
- The confirmation lives only in the server database. After a lost database the quarantine returns with the next cycle and each snapshot has to be confirmed again.
- A planted snapshot therefore costs the repository its cleanup until an administrator looks at it, and it cannot cause a deletion by itself. A compromised host that keeps planting new unopenable snapshots keeps the cleanup waiting; that is a denial of cleanup, not of backups or restores.

**What the server key needs.** The server deletes with its own key, never the agent key, and never asks the storage to bypass a lock. On AWS S3 versioned deletion takes `s3:DeleteObject`, `s3:DeleteObjectVersion`, `s3:ListBucketVersions` and `s3:GetObjectVersion` in addition to the rights it already uses. MinIO does not tell these apart: a key with `s3:DeleteObject` alone removed a version in testing, so a MinIO setup that works does not prove the AWS policy is complete.

**Locked versions.** When the storage refuses to delete a version because Object Lock still protects it (MinIO answers 400 `InvalidRequest`, AWS answers 403 `AccessDenied`), the version is reported as retained, not as a failure. Its delete marker is kept until the last real version is gone, otherwise the object would reappear in listings. A later cycle frees the version once the lock has run out.

## Index metadata from a compromised agent

An agent holds the key that seals index shards ([ADR 0002](/docs/adr/0002-key-model-and-envelope/)). Whoever controls an agent can therefore write a shard that lists any blob at any place and declares that it supersedes any other shard, and can put a pack of their own choosing in the bucket. This section says what Lodestore does about that. The signature objects are described in [ADR 0005](/docs/adr/0005-server-attestations/).

**What the server signs.** The server writes create-only objects `locks/attest-*` that list the index shards it vouches for, with a MAC under a key derived from the repository master key. Agents do not have that key. They can read the objects and cannot forge or alter one. The server and `lode` hold the master key, verify every object and ignore those that fail. The server logs each object that fails with its key, and the next cleanup cycle reports it as a warning and deletes it (a storage that keeps it under Object Lock leaves it ignored).

**What this prevents.**

- **A planted shard does not steer cleanup.** `supersedes` counts only from attested shards, in garbage collection and in restore. The writer of a backup, whether an agent or `lode backup`, does not apply `supersedes` at all: it cannot verify the signature. The check of a new backup never signs a host's shard that lists `supersedes`, even when its frames open: the frames say nothing about whether that list is honest.
- **Cleanup opens the surviving copy.** Before it deletes or replaces a pack that holds a live blob, the server reads the frame at the place the index names as the surviving copy and opens it: the authentication tag and the keyed blob id must match. If the frame does not open, the pack stays. A pack that cannot be read, or whose live blobs do not all open, is skipped by the rewrite step and left for a later cycle, and the cycle records a warning that names it. This check does not depend on trusting any shard, so it also covers shards signed at the upgrade.
- **A malformed shard is left out.** A shard that does not open, or holds a record outside its pack or with an unknown blob type, is skipped and reported by cleanup, by the deduplication of a backup and by the server's check of a new backup. It does not stop any of them, even when the upgrade signed it.
- **Every read of a bucket object has a size limit.** An agent can put any object under `index/`, `packs/`, `snapshots/` or `locks/`, with any size, and can replace an object after it was listed. Everything this version reads from the bucket (snapshots, index shards, packs, writer markers, attestations, key slots and `config`) is read with a ranged read. With the size from the listing, the read asks for exactly that many bytes; without a listing it asks for the limit for that kind of object plus one byte and refuses a longer body. An object swapped for a larger one after the listing is therefore not downloaded beyond what the listing said, and it fails the check of its name or tag. A writer marker above 1 MiB is not read and counts as an open writer, so it cannot be used to make cleanup fail, and like any open writer it keeps cleanup waiting. A key slot above 64 KiB is skipped, an opening reads at most 1024 key slots, and a `config` above 1 MiB is refused. A pack longer than its listing is read only up to the listed size, and a pack shorter than its listing is reported by the check as a mismatch. A snapshot whose body is not the size the listing gave stops the survey step of cleanup with a store error, like any object that changed during the survey, and is neither quarantined nor ignored. An object listed with size zero that has vanished is reported as gone, not read as empty.
- **An index shard has a size limit that depends on the signature.** No reader loads a shard that the server has not signed if it is larger than 64 MiB, and this holds on every path, a restore included. Cleanup, the writer of a backup (the agent and `lode backup`), the server's check of a new backup and `lode restore` leave such a shard out and report it (`skipped_shards` in the cleanup report) without downloading it, and the rebuild of the index and that check do not read a pack of more than 64 MiB. A shard that the server has signed is read up to 1 GiB, but only after its content, read in pieces of 64 MiB, hashes to the name it carries; a signed shard above 1 GiB is left out and reported on every path, refused before any read when the listing shows its size and, without a listing, once 1 GiB has been hashed. A shard is one authenticated frame: it cannot be opened before all of it has arrived, so the object is first hashed piece by piece and loaded whole only once the hash matches its name, which bounds the memory by the real shard. The honest shards that 0.1 wrote can be larger than 64 MiB; they are signed when the server first opens the repository and are read from then on. A 0.1 repository that no 0.2 server has opened and that holds a shard above 64 MiB, or a signed one above 1 GiB, needs `lode repo rebuild-index` before a restore. Every writer of this version cuts the shards it writes at 32 MiB and at 1024 pack records, and the first cleanup cycle after the update rewrites each signed shard above 64 MiB into shards under the limit. The limits are fixed by calculation, and a signed shard that is overwritten after the signature costs bandwidth on every read, at most about 1 GiB plus 64 MiB, not memory; see [How we test data safety](/docs/security/how-we-test/#what-we-have-not-verified).
- **Cleanup does not delete what a skipped shard might name.** A shard that cleanup left out can list packs that agents still reuse. The agents of this version do not read an oversized shard either, but an agent from 0.1 has no size limit and does read it. Therefore, while the repository has an enrolled agent that does not announce `shard_limit_v1`, the cycle deletes no pack that a skipped shard names, and fails with a message that names the shards and the hosts, so that you update or revoke the agents older than 0.2 and run cleanup again. Revoked agents do not count. Without such agents a skipped shard does not stop cleanup. `lode` from 0.1 started with `--writer-keys` is not visible to the server and keeps this risk, which is why `lode` is updated together with the server.
- **Reads fall back to other copies.** If the first known location of a blob does not open, runs past the end of its pack or is in a pack of a version the reader does not know, `lode restore` and the reads the server makes itself (browsing, tree reads) try the others, including those listed only by a shard that a newer shard supersedes. Every frame is authenticated by its blob id, so a false copy is rejected and never returned. A false record that claims the wrong size for a chunk does not fail the file either: when the sizes in the index do not add up, the restore reads the chunks and counts what they hold. Every visit of such a file charges its chunks to the budget of the operation, as entries before they are read and, for every reference to a chunk, a repeated one too, their bytes as directory data as they are read, so reaching the file through many parents is not free. On each visit each distinct chunk of the file is read once. Charging and reading stop once the chunks hold more than the file says: the references after that are neither read nor charged, and the error then says that the chunks hold more than the size of the file without naming a sum. Every frame fetched for such a chunk is charged too: a copy that does not open costs its frame, and the pack prefix when that pack's key has not opened yet, so a planted shard that lists a chunk first at many copies that do not open pays for each of them; copies at one place in a pack that differ only in the size they claim share one fetch. A charge that does not fit spends the rest of the budget, a chunk none of whose copies opens is not read again in that operation, and no frame is fetched once the budget is spent, so the reading stops at most one frame and one pack prefix past the budget. Below the budget, what is read and not charged is the 41 bytes of framing of each chunk that opens and the prefix of each pack the first time its key opens. The chunks are read once per operation for the first 65,536 such files and again on each visit beyond that; up to 65,536 chunks that do not read are remembered the same way. The integrity check counts the same charge and reports a snapshot that passes the budget with the text of one of the errors a restore gives. It reads the chunks of such a file at most once for each directory it is written in, and over the whole run within the walk budget of one restore, 2^30 references to chunks and 512 GiB, reading at most one frame and one pack prefix past it however many such files come after. A file it can no longer read is the finding `unreadable_tree` (`was not checked`) for every snapshot that reaches its directory, so no snapshot with such a file unread is reported healthy. For the trees an honest backup writes the check reads no chunks; a planted tree or index shard can make it read them, within the budget above. A restore run by an agent does not fall back yet: it reads file data from the first known location only. A download as an archive reads file data with the fallback but takes the size of each chunk from its first known location. In both, a false first copy makes that file fail there while `lode restore` still recovers it.
- **A backup that cannot be restored does not end as a success.** After every backup the server opens every new frame the snapshot depends on and checks that all its trees and data blobs resolve through shards whose frames it has opened itself. This costs egress: the server downloads every new byte once. If the check fails, the job is set to `failed` with the error code `verification_failed`, the snapshot is marked with `unverified_reason` in the snapshot list of the API, and the usual alert for a failed backup fires when that job is still the latest finished job of its policy on that host; a job without a policy, such as a stdin backup, raises no alert yet. A job can therefore turn from succeeded to failed after the agent reported it finished. If the server cannot run the check (the storage is unreachable, or the server refuses to sign the repository, see below), it retries for at most one hour from the first failed attempt, measured on the server's clock; after that the job also becomes `failed` with `verification_failed`. A job that reports a snapshot the catalog already links to another job fails the check, and the other job's snapshot is left as it was. This check covers backups made by agents. `lode backup` run directly against a repository that a 0.2 server has upgraded checks itself: it deduplicates only against signed shards (and shards this machine opened itself), opens the frames its snapshot depends on the way the server does before it exits with 0, and signs the snapshot with the repository password. The first run on a machine reads the frames of every shard the snapshot depends on; later runs keep what they checked in `$XDG_CACHE_HOME/lode/` (see [the command line](/docs/reference/cli/#backup-and-restore-without-the-server)). `lode backup --writer-keys` cannot check anything and refuses to run in such a repository. In a repository that no 0.2 server has opened, `lode backup` is not checked at all: it deduplicates against every shard in `index/`, so a planted shard can make such a backup unrestorable without an error. Back up through an agent, or open the repository with a 0.2 server first, when the bucket is shared with hosts you do not fully trust.
- **The agent's deduplication filter is not a boundary.** Once the server has upgraded a repository, an agent deduplicates only against its own shards and the attested ones. The agent cannot verify a signature, so this narrows what a planted shard can influence and nothing more. The boundary is the server's check above: a shard that passes the filter but lacks the data it claims produces a failed job, not a silent gap.

**What the upgrade trusts.** When the server first opens a repository (it creates one, you connect an existing one, or a repository written by 0.1 meets a newer server) it signs the shards that are in `index/` at that moment. The signature means "present at the upgrade", not "contents verified". The server relies on such a shard only for `supersedes` and for cleanup. The check of a new backup does not rely on it: the first time a backup refers to the shard, the server opens its frames, and it remembers the result. A shard planted before the upgrade is therefore signed too, and a backup that depends on it becomes a failed job. The upgrade also signs who made the snapshots the catalog already ties to a host and a job; see [Snapshot provenance and `latest`](#snapshot-provenance-and-latest). A forgery made before the upgrade is found across the whole repository by `lode check --level packs`; run it once after upgrading.

**Where the state lives, and a folder repository.** The list of shards whose frames the server opened is in the server database. The fact that a repository was upgraded is in the bucket, as a marker in `locks/attest-*`, so a new database does not sign the shards again. On S3 the agent key is read-only on `locks/`, which rules out everything below. On a local or network folder the agent has file permissions and can write and delete in `locks/`:

- It cannot forge a MAC. An object that does not verify is ignored, logged by the server and deleted by the next cleanup cycle.
- A planted or deleted list of shards affects only the agents' deduplication filter. Agents cannot check the MAC, so a planted list steers the deduplication of every host on the repository until the next cleanup cycle deletes it. The outcome is failed jobs on those hosts, not a successful backup that cannot be restored.
- Deleting attestations withdraws the trust in `supersedes` (the index still holds the other copies, and `lode restore` falls back to them) and in deduplication against verified data. It does not turn the backup check off, because the list of verified shards is in the database.
- Deleting attestations also deletes the signed records of who made each snapshot. The server keeps its own marks in the database and is not affected; `lode` on a machine that has not seen the signatures falls back to the legacy choice of `latest`. See [Snapshot provenance and `latest`](#snapshot-provenance-and-latest).
- If the marker is deleted while other attestations remain and the database is lost as well, the server refuses to sign the repository again and says so. Cleanup of that repository then fails with that error before it deletes anything, and a new backup becomes a failed job with `verification_failed` one hour after its first failed check.
- If an agent deletes the marker together with every attestation and the database is lost as well, nothing in the bucket shows it. This is an accepted residual risk. The next upgrade signs the current index, including a shard planted in the meantime. Such a shard still cannot cause a deletion, because cleanup opens the surviving copy, and a backup that depends on it becomes a failed job with `verification_failed`: the upgrade signature does not replace opening the frames.
- Do not use a folder repository for hosts you do not trust.

**What stays open.**

- An agent from 0.1 that is enrolled after a cycle has finished is not covered by the hold-back above: it reads a skipped shard whole and can deduplicate against a pack that the cycle has deleted. This happens with an old package, a downgrade, or the re-enrolment of a host that was revoked to get past the hold-back. The server's check of the new backup finds the missing data and fails that job with `verification_failed`, so no backup ends as a success that cannot be restored. Only an administrator can enroll an agent, which is why the risk is accepted; do not enroll agents older than 0.2 after an update.
- When `index/` is lost, agents deduplicate only against their own shards and the attested ones, so they upload again data that the server has not yet verified. `rebuild-index` accepts every shard of a repository that has not been upgraded, and only attested shards after the upgrade. This costs bandwidth and space, not data.
- Who made a snapshot, and which snapshot is the latest, are covered separately; see [Snapshot provenance and `latest`](#snapshot-provenance-and-latest) for what that covers and where it stops.

## Snapshot provenance and `latest`

A snapshot manifest is written by the host being backed up. Its `time`, `hostname` and `agent_id` are claims of that host. Whoever holds the writer keys can plant a snapshot that names another host and carries any time, even one far in the future. If `latest` followed the manifest, that snapshot is what `lode restore latest` and "restore to the original host" would offer after an incident. This section says how Lodestore avoids that and where the protection stops. The design is in [ADR 0006](/docs/adr/0006-snapshot-provenance/).

**Who signs a snapshot.** A snapshot is signed when a record in a `locks/attest-*` object names it. The record is sealed with a key derived from the repository master key, so an agent cannot write or alter one, and on S3 its key cannot write `locks/` at all.

- **The server** writes the record after it has checked a finished backup (see above). The host in the record comes from the agent's client certificate and the job from the server's own catalog, never from the manifest. A snapshot whose manifest does not name the host that reported it fails the check. A `lode backup --stdin` stream that goes through the agent is reported on the agent's own session, so it is signed for the host of that certificate, and host A cannot pass a snapshot off as host B's.
- **`lode backup` with the repository password or recovery key**, in a repository a 0.2 server has upgraded, signs its own snapshot after it has checked it. The record has no host and no job, which means "signed by the holder of the password": `lode snapshots` marks it `owner` and the web interface shows "Signed with password". The holder of the password can write anything to the bucket anyway; the signature only lets such a snapshot take part in `latest`.
- **At the upgrade**, the first time a 0.2 server opens a repository, it signs the snapshots that its catalog already ties to a host and a job, that is, those a host reported as finished on its authenticated session, including those whose job record the server has since pruned. A job still on record must have ended as succeeded or with warnings. A repository created by a 0.2 server has nothing to sign this way. Every other snapshot in the bucket stays unsigned. The server trusts the state of the repository at that moment: a snapshot that a compromised host reported as its own before the upgrade is signed as that host's.

**What the server does with signed and unsigned snapshots.**

- The lists of a host, the timeline, the host picker, the restore page and the fleet-wide find order snapshots by the time the server received them, never by the manifest; the find lists signed versions of a file first and, within a version, signed snapshots first, so Restore, Download and Show in snapshot of a signed version open a signed snapshot even when a planted snapshot claims the same content (the content id its tree records, or the size and modification time of an empty file or symlink). The time of the last backup (the fleet overview, the "no backup" alert, metrics) and the baseline of the anomaly detector use signed snapshots only, so a planted snapshot cannot hide an overdue backup. The host picker and the restore page open the newest signed snapshot.
- Retention counts only signed snapshots and never forgets an unsigned one (see [Retention and forgetting snapshots](#retention-and-forgetting-snapshots)).
- The interface marks an unsigned snapshot "Unverified". A restore of it needs a confirmation, and the server refuses to restore it in place (`restore_unverified_in_place`) or without the confirmation (`restore_unverified_not_confirmed`). An unsigned snapshot stays restorable to another folder and by its id.

**How `lode` chooses `latest`.** `lode restore`, `lode ls` and `lode dump` use the same rule as the server, because it lives in the format library.

- **Strict**, when the repository holds at least one attestation that passes the MAC. Only signed snapshots compete, ordered by the time the storage reports for the snapshot object (`LastModified`), not by the manifest. A signed snapshot stored more than ten minutes ahead of the clock is skipped with a warning. If none is left, the command fails and asks for an id. If the attestations change while `lode` reads them, as during a cleanup cycle, it reads them again and fails rather than decide on a partial set. It warns about unsigned snapshots stored after the chosen one and about manifests that claim a time in the future.
- **Legacy**, when the repository holds no valid attestation. This is a 0.1 repository that no 0.2 server has opened, and nothing there can be signed yet. `latest` is the snapshot the storage wrote last, and the command warns that it could have been written by a host with writer credentials. A snapshot stored more than ten minutes ahead of the clock is never chosen; if every snapshot is, the command fails and asks for an id. **In legacy mode the protection does not exist**: a compromised host that wrote last wins. Open the repository with a 0.2 server before you need an emergency restore, or name the snapshot by its id.

**Folder repositories.** On a local or network folder, `LastModified` is the file's modification time, which whoever can write the file can set. In strict mode the modification time does not decide who is signed: an agent cannot create a signed snapshot. A writer with file permissions can still change the order of `lode`'s choice among signed snapshots by touching their files; it cannot add a snapshot to the set. The server orders by its own clock and is not affected. The modification time is the only evidence in legacy mode, and in this case:

- `lode` keeps a mark per repository on the machine where it has seen signatures (`$XDG_CACHE_HOME/lode/<repository id>/upgraded`). With the mark, if `latest` finds no readable attestation, it refuses and asks for an id instead of falling back to legacy mode, so deleting `locks/attest-*` from a folder repository does not silently change the answer. `lode backup` on that machine refuses to run in that state as well.
- A machine without the mark, such as a new one used for an emergency restore, cannot tell a repository whose attestations were deleted from a 0.1 repository. It falls back to legacy mode, and the holder of the writer keys, who on a folder has file permissions, can delete the attestations and give a planted snapshot an old modification time so that it is the newest one that is not "in the future". This is not prevented. On S3 the agent key cannot delete or write in `locks/`, so the signatures survive. Do not use a folder repository for hosts you do not trust.

**A lying shard costs one backup.** A host can plant an index shard, or a hint in a forged attestation list, that names blobs it did not upload, hoping a later backup deduplicates against it. When the server's check of a new backup finds shards that do not hold what they claim, it records every one of them in its database as distrusted, up to 64 per backup, and the job fails once. The cap keeps one hostile snapshot from flooding the list; a hint naming more lying shards costs one more backup per 64. The server sends the list to agents with every job and on every connection, and an agent never uses a listed shard for deduplication, so the next backup of that host does not rely on it. Agents receive the newest 65 536 revocations; cleanup reads all of them. A shard the server catches lying again moves back to the front of that list, so a host that floods the list with junk shards to push an old revocation out costs its victim one more failed backup per 64 evicted shards that backup relies on. The next cleanup cycle leaves the shard out of the consolidated attestation, and compaction never signs its records again under a new shard. The revocation lives in the server database, not in the bucket, because the repository format does not change. A lost database loses the list, and the next failing check records it again. `lode backup` keeps its own list of shards it has caught lying, and of those it has opened, in its cache folder.

**After the database is lost.** The rebuild of the catalog restores from the bucket which snapshots are signed and by whom (server or password), and the time of the signature. A server signature is restored only on a snapshot whose rebuilt host is the host the record names; any other snapshot stays unsigned. It does not restore which host and which job made a snapshot, because only the database held that.

**What this does not cover.**

- Provenance says who produced a snapshot, not that its contents are honest. A compromised host can still make real backups that are signed as its own, with any contents, and make enough of them to push its own older history out of a retention window. Limiting what a host may write is planned. `lode restore latest` chooses across all hosts of the repository; to restore one host, find its snapshot with `lode snapshots` and name it by id.
- Legacy mode, a folder repository and a machine without the mark, as described above.
- A `lode backup --writer-keys` backup in a repository that no 0.2 server has upgraded is not checked by anything. In an upgraded repository the command refuses to run, because writer keys cannot check the backup.
- A server that is taken over signs what it likes. The signature is the server's, so it proves what the server saw, not that the host was honest.

## The server and the schedule

The server is a single point of failure for schedules. Policies, schedules, catch-up and retention live on it, and the agent starts no policy job by itself: while the server is down or unreachable no planned backup runs. What a policy's catch-up setting allows is made up after the agent reconnects. `lode backup --stdin` through the agent keeps working, because the agent writes to the bucket with its own key. It keeps the job and its result locally and reports them when the server is back, and the server signs the snapshot only after it has checked it, so until then the snapshot shows as "Unverified". Restoring needs no server at all: the bucket and the repository password or recovery key are enough.

The catalog, the signatures and the retention decisions are the server's too. What a compromised agent can make the server believe, through index shards and snapshot metadata, is covered in [Index metadata from a compromised agent](#index-metadata-from-a-compromised-agent) and [Snapshot provenance and `latest`](#snapshot-provenance-and-latest).

## Demo mode

`demo_mode` turns a server into a public, read-only demonstration. It is meant for a throwaway instance filled with synthetic data and never for real backups: it hands every anonymous visitor an administrator session, and that session can read every snapshot and download it, decrypted by the server. The server logs a warning on every start with the flag on. Do not put it in a Helm values file or a quickstart.

**Sign-in.** `POST /api/v1/auth/demo` signs a visitor in as the administrator without a password. The session lasts one hour and is not extended. The endpoint exists only with the flag on and answers 404 otherwise. Sign-ins are rate limited per client address, so behind a reverse proxy `trusted_proxies` must be set, or every visitor shares one bucket.

**What is open.** A default-deny allowlist of (method, route template) pairs, `ALLOWED` in [`demo.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/src/demo.rs), which is the full list:

- Reading hosts, snapshots, entries, jobs, alerts, policies, repositories and their reports, agent updates, the agent policy and the notification thresholds.
- Reading the list of API tokens and the administrator account. A visitor sees token names and the administrator's name and address, never a token secret. This is why the stand's account must be synthetic.
- The search, `POST /api/v1/find` and `DELETE /api/v1/find/{id}`, and creating and fetching an archive download.
- `POST /api/v1/snapshots/{id}/summary`, which counts what a selection holds.
- `POST /api/v1/auth/logout`, which ends the visitor's own session.
- The two policy checks that the policy editor needs, `POST /api/v1/policies/validate` and `POST /api/v1/policies/{name}/retention-preview`. Both only read the catalog and answer with a result, and a test compares the database before and after.

Saving, running or deleting a policy stays closed. Any other route under `/api/v1` is refused with 403 `demo_mode`, and the web interface turns that answer into one notice, "Not available in the demo." A path that matches no route gets 404. The allowlist is checked by a test against the OpenAPI document, so a new route is closed until someone lists it on purpose. The API reference, `/api/docs` and `/api/v1/openapi.json`, sits outside the allowlist and is served to any session, so a demo visitor can read it.

**What is closed, and why.**

- Every write not listed above: tokens, settings, policies and their hooks (a hook runs a command on a host), restore to a host, agent registration, agent updates, garbage collection and checks.
- Requests that carry an address from the client, such as testing a repository or a notification channel. They would turn the server into a way to reach other services on its network.
- Bearer tokens. A request with `Authorization: Bearer` is refused before the route is looked at. Other schemes are not treated specially here: they carry no credential the server accepts, so the session and the allowlist still decide.
- HEAD, OPTIONS and any method not in the list.
- The notification channel page. The list of channels answers with an empty list in the demo, so webhook addresses, chat ids and SMTP hosts never leave the server. The server test walks the schema of every allowed response for secret-looking field names and seeds secrets to check that no allowed read returns them.
- `/metrics` is not mounted.
- Archive downloads are limited to two at a time, and each stops after two minutes. A slow download would otherwise hold a thread and keep garbage collection waiting.

**What stays open.** `/install.sh` and `/install/agent/{name}` serve the public installer and the agent binaries and their signatures, and the archive download serves whatever the demo repository holds. All three are fine only because the data is synthetic.

**Switching the mode.** Sessions of one mode must not outlive the other. When the server starts with a different `demo_mode` than the one stored, it deletes every session before it listens. Fill the demo with data and maintain it only with the flag off, and close the reverse proxy for that time.

**What the server does not provide.** Isolation of the host. A flaw in the allowlist or in the server would put the process under the control of a stranger, so the deployment has to keep the demo away from everything else: rootless containers or user-namespace remapping, no host directories and no container socket mounted, a separate network without a route to other services, CPU, memory and disk limits, a read-only root filesystem, `cap_drop: ALL`, `no-new-privileges`, and only the HTTP port published, behind a reverse proxy with its own rate limit. The gRPC and object storage ports stay unpublished, and the demo uses secrets of its own.
