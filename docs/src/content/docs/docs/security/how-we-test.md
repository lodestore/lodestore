---
title: How we test data safety
description: Which automated checks protect your backups, when they run, and what they do not cover.
---
A backup tool is trusted for one thing: the data comes back. This page lists the checks that exist in the repository and in CI today, what each one proves, and where the gaps are. Every file named here is in the repository; if a check is not listed, assume it does not exist. The section [What we have not verified](#what-we-have-not-verified) is part of the page, not a footnote.

The latest release is 0.2.0, and this page lists the checks it came out with. They are the ones built and kept green so far, not an external audit. No external audit of the format or the cryptography has been done.

## What counts as losing data

A test is written to catch one of these:

- A snapshot in the bucket cannot be restored, or restores different bytes, with only the bucket and the repository password or recovery key.
- An object a snapshot needs is deleted by anything other than the server's cleanup, or overwritten by Lodestore's own writer. A stolen agent key is a different case: see [`s3_write_only.rs`](#what-the-bucket-looks-like-from-outside) below.
- Cleanup deletes something that a snapshot, finished or still being written, needs.
- The bucket holds readable file names or contents.
- A change to the format silently breaks old repositories or deduplication.

## Frozen format fixtures

The repository format is frozen by committed data, so a dependency bump or a refactor cannot change it unnoticed.

- [`crates/lodestore-format/tests/it/golden.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/golden.rs) reads a repository written by an earlier build (`tests/fixtures/v1`): it lists the snapshots, restores the contents, and re-encodes them to the same bytes. Any change to the encoding, the chunker, the ciphers or the compression that old repositories would not survive makes it fail.
- [`crates/lodestore-format/tests/it/vectors.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/vectors.rs) holds frozen outputs of the primitives for fixed inputs: the chunk boundaries, key derivation, key slots, the AEAD, the key exchange, packs, index shards and the cleanup records. zstd output is left out on purpose because it is not guaranteed between versions; decompressing the committed frames is covered by the golden test.
- [`crates/lodestore-format/tests/fixtures/v1/attest-vectors.json`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/fixtures/v1/attest-vectors.json) freezes the server key derivation, the MAC of a server attestation and its frame, and the sealed provenance bytes for fixed inputs. It is a new file next to the older vectors, which did not change.
- [`crates/lodestore-format/tests/fixtures/v1/source-vectors.json`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/fixtures/v1/source-vectors.json) freezes the canonical keys of source instances (the encoded bytes of a guest and a database source, the labels, and the keys a reader must refuse), checked by `source_vectors_match` in `vectors.rs`. It is a new file; the vectors that existed did not change.
- [`crates/lodestore-format/tests/fixtures/v1/image-vectors.json`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/fixtures/v1/image-vectors.json) freezes the layout of a disk image: the key of an image, the metadata of a snapshot and of a disk, the canonical node of a segment and the layouts a reader must refuse (`image_vectors*` in `vectors.rs`). It is a new file; the vectors that existed did not change.
- [`crates/lodestore-format/tests/fixtures/v1/image-binding-vectors.json`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/fixtures/v1/image-binding-vectors.json) freezes what binds a dirty bitmap to a snapshot of an image: the metadata keys (`disk_{h}_bitmap_name`, `disk_{h}_bitmap_gen`, `disk_{h}_full_reason`), the codes of `full_reason` in the order they are checked, three encoded sources, and the form of the bitmap name, `lode-{repo16}-{inst16}-g{N}`, with the names a reader accepts and the ones it must refuse (`image_binding_vectors*` in `vectors.rs`). It is a new file; the vectors that existed did not change.
- [`crates/lodestore-policy/tests/fixtures/v0.2`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-policy/tests/fixtures/v0.2) holds the policy files of 0.2 (the ones the quickstart, the guides and the scripts use). They must read as before and export to the bytes that the 0.2 code (commit 83884fdf) exports; the expected exports were produced by running that commit, and the fixtures were committed before the export code changed. `lode policy validate` is tested on them and on invalid sources (`source_blocks_reject_unknown_fields`).
- [`crates/lodestore-server/tests/fixtures/secrets-v1.json`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/fixtures/secrets-v1.json) holds secrets sealed by the 0.1 server, written by the 0.1 code before the sealing changed. [`secrets_upgrade.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/secrets_upgrade.rs) opens a database with those rows after the update, checks that the one-transaction migration is repeatable, that a wrong unlock key changes no row, and that a failure in the middle leaves every row as it was. It is a new file; no existing fixture changed in this release.
- The CI job `fixtures-append-only` in [`ci.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/ci.yml) runs [`scripts/check-fixtures-append-only.sh`](https://github.com/lodestore/lodestore/blob/main/scripts/check-fixtures-append-only.sh). It fails when a change modifies, deletes or renames a file under `fixtures/v1`; new files are allowed. A format change has to ship as `format_version` 2 with its own fixtures next to the old ones.

The frozen repository `fixtures/v1/repo` is also opened by the other layers, not only by the format library: the `*_v1_fixture` tests of [`provenance_cli.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lode-cli/tests/it/provenance_cli.rs) run `lode` on it, and `repo_open_v1_fixture_connects` in [`repo_open.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/repo_open.rs) connects it to the server and checks that the server opens it and lists the snapshots recorded in the fixture.

Limit: the fixtures prove that old data stays readable. They do not prove that the format is secure; see the cryptography notes in the [threat model](/docs/security/threat-model/) and the [ADRs](/docs/adr/0002-key-model-and-envelope/).

## Rules the compiler enforces

- Every crate except the agent carries `#![forbid(unsafe_code)]`. The agent is the one crate that calls the operating system directly and keeps `unsafe` where it needs it.
- The call that replaces the random number generator of the writer with a fixed one exists only in test builds and under the `test-hooks` feature, which no production binary enables. A release build cannot produce repeatable keys or nonces through it. The job `check` of [`ci.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/ci.yml) fails a pull request that turns `test-hooks` on for `lodestore-format` anywhere except in a dev-dependency (`cargo tree --workspace -e features,no-dev -i lodestore-format` must not show the feature).

## Fuzzing

The parsers and decoders that read bytes from a bucket, a host or a download are fuzzed with libFuzzer through `cargo fuzz`. There are 25 targets in [`fuzz/fuzz_targets/`](https://github.com/lodestore/lodestore/tree/main/fuzz/fuzz_targets); the code each one runs is in the stable crate [`crates/lodestore-fuzzkit`](https://github.com/lodestore/lodestore/tree/main/crates/lodestore-fuzzkit), so that it also builds and runs without nightly.

- The targets by group: packs (`pack_prefix`, `pack_trailer`, `pack_entries`), index shards (`index_shard`, `verify_shard`), trees (`tree_decode`, `tree_count`, `tree_cursor`), key slots and keys (`key_slot`, `writer_keys`, `recovery_key`), cleanup records and writer markers (`gc_manifest`, `writer_marker`), attestations and provenance (`attest_open`, `attest_peek`, `provenance_open`), the source of a snapshot (`source_decode`, which decodes a claimed source and checks that its canonical key is the one it re-encodes to), the layout of a disk image (`image_layout`, which decodes the segments of an image and checks that an accepted segment is the one the writer would build again), the state file and the bitmap names of an image backup (`image_state`, which parses the state and checks that what it accepts encodes back to the same bytes, and that a bitmap name it accepts is the one it builds again), the NBD client (`nbd_client`, which runs a handshake, a read and a block status request against a scripted stream of server bytes) and the NBD test server (`nbd_server`, which runs it against scripted client bytes), snapshots (`snapshot_open`, `snapshot_resolves`), the minisign signature of an agent update (`minisign_signature`) and the plan of a restore that the agent executes (`restore_plan`).
- Authenticated formats would reject random bytes at the first check, so a target seals the bytes the fuzzer produced with fixed test keys and then opens them, and requires that what comes out is what went in. The raw bytes also go to the opening function, so the rejection path is exercised too.
- Memory is bounded. libFuzzer runs with `-malloc_limit_mb=256`, `-rss_limit_mb=2048` and `-max_len=1048576`, so one allocation above 256 MB is a crash. [`regressions.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-fuzzkit/tests/regressions.rs) holds every target to a ceiling of 64 times the input plus 64 MiB of allocation, measured with a counting allocator.
- What every pull request runs, besides the smoke fuzz below, is `seeds_and_regressions_never_panic`, which replays the seeds of every target on stable. The seeds of `image_layout` are built from `image-vectors.json` and those of `image_state` from the binding vectors. The seeds of `nbd_client` and `nbd_server` are the bytes of a real exchange between the client and the test server of the repository, whole and cut in half; they are not recorded from qemu.
- The corpus starts from the frozen fixtures of `tests/fixtures/v1`. `restore_plan` also gets hand-built plans with unsafe names (`..`, empty, `../../outside`) and checks after each run that nothing was written outside the restore folder.
- [`fuzz.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/fuzz.yml) runs every target for 5 minutes each night, with the corpus kept between runs, at most six targets at once. A crash uploads the input as an artifact and opens an issue named `fuzz crash: <target>` unless one is open.
- A crash is fixed together with a regression: the minimized input goes into `fuzz/regressions/<target>/`, and `seeds_and_regressions_never_panic` in `regressions.rs` replays it on stable with the normal tests of every pull request. There are no such inputs yet.
- On a pull request that changes a parser, a decoder, the cleanup code, the NBD client or the image code, or `fuzz/`, six targets (`index_shard`, `tree_decode`, `image_layout`, `image_state`, `nbd_client` and `nbd_server`) run for 30 seconds each. That is a smoke test, not the nightly run.

Limit: fuzzing finds what it reaches in the time it has. Five minutes a night per target is not exhaustive, three targets (`verify_shard`, `snapshot_resolves`, `snapshot_open`) run an order of magnitude fewer inputs per second than the others because each one reads and decrypts a real pack, and `restore_plan` does not get valid encrypted frames, so the writing of file contents is not fuzzed, only the plan, the names, the tree and the metadata.

## Property tests

Property tests generate inputs and check a statement about all of them. They use `proptest` and run with the normal tests; each property runs 256 cases unless the case is heavy (then 16), and a failing case is saved next to the test and replayed first from then on.

- [`index_props.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/index_props.rs): the place the index chooses for a blob does not depend on the order in which the index shards are loaded (`index_location_does_not_depend_on_shard_order`), a blob that is in at least one shard outside an excluded pack is never lost, `supersedes` from a shard that is not attested is ignored, and excluded packs stay excluded. The generator includes `supersedes` that points at itself, in a cycle or at a shard that does not exist.
- [`codec_props.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/codec_props.rs): what is sealed opens to the same value, for snapshots, trees (also trees cut into several pieces), index shards, packs, key slots (a wrong password or recovery key gives no key), locks and writer markers, attestations and provenance.
- `roundtrip_generated_tree_restores_identically` in [`roundtrip.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/roundtrip.rs): a generated tree (empty and sparse files, symlinks, hardlinks, modes, nanosecond times, extended attributes on Linux) is backed up and restored, and the restored tree must match. Then files are rewritten, removed and added, a second backup is made against the first, and that restores to a match too.
- Source instances, in [`provenance.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/provenance.rs) and [`source.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/source.rs): generated keys round-trip through the canonical form and two different identities never share a key; `files_latest_picks_like_before` compares `latest` for a repository of `files` snapshots with a frozen copy of `pick_latest` from commit 83884fdf (0.2) over generated repositories, and `latest_is_per_source_instance` and `latest_separates_forty_instances` check that `latest` of one instance is not moved by the others, among forty instances.
- Retention and alerts per instance, in [`differential.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/src/catalog/retention/differential.rs) and [`evaluate/differential.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/src/alerts/evaluate/differential.rs): `files_only_catalogs_decide_like_before` and `files_pairs_alert_like_before` run the current retention `decide` and the alert candidates of `evaluate` against frozen copies from commit 83884fdf on generated catalogs of `files`, and the decisions and alert keys must be identical; `other_instances_do_not_change_files_decisions` checks that snapshots of other instances change nothing for `files`.
- The choice of `latest` by the server and by `lode`, in [`attest_verify.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/attest_verify.rs): `attest_verify_latest_agrees_with_lode_on_hostile_repositories` generates repositories with several hosts that share one instance key, a name shared by two hosts, a host whose name is another host's id (also in UUID form, which `--host` must read as an id only), renamed hosts, snapshots with a skewed manifest time, ties and snapshots stored ahead of the clock. The server verifies them for real, and `latest_verified_id` must equal what `lode latest@KEY` (and `--host`) chooses; where `lode` refuses because the key comes from several hosts, the test checks the refusal. Counters of each class of case must stay above zero, or the test fails. The reads are counted too: for one choice only `snapshots/` and `locks/attest-` are read, each object once, and no more bytes than their listed size. The test does not cover retention or forgetting, and the storage supplies the time of an object. It runs on SQLite and on PostgreSQL.
- [`gc_props.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/gc_props.rs) holds a differential test of cleanup, `gc_hostile_repository_restores_after_cycle`. It generates repositories with planted index shards of the kinds an attacker holding the writer keys can write (forged offsets, `supersedes` over real shards, a chain of shards that replace each other, a record for a pack that does not exist), makes backups between the steps of the cycle, runs a whole cycle and then restores every snapshot, also one made in the middle. The data of a forgotten snapshot must be gone, the bytes left in `packs/` and `index/` stay within a bound, and the listing is shuffled. The test counts how many cases deleted a pack, repacked, planted a shard and interleaved a backup, and fails when the generator stops producing them. Three pure properties cover the plan: it never deletes a live blob (`gc_plan_never_deletes_live`), it does not depend on the order of the listing, and compaction keeps every location (`gc_compact_keeps_every_location`).

The tests of this phase found two defects in the product, both fixed: see [Cleanup](#cleanup-garbage-collection) and the changelog.
- Disk images, in [`image.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/image.rs): a generated layout of an image round-trips through the segments and back (`image_layout_round_trips`), merging the segments gives the bytes of the image (`image_merge_matches_concatenation`), two names never share a key and the metadata of a disk round-trips (`image_keys_are_injective`, `image_meta_round_trips`), and a table of hostile segment lists is refused (`image_layout_rejects_hostile_segments`). The image of 16 TiB, the largest one, is accepted (`image_layout_accepts_the_largest_image`), and the worst segment fits a tree blob. The round trip with holes across segments cuts the image into segments of two chunks, not of 256 GiB.
- Incremental backups of disk images, in [`image_props.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-nbd/tests/it/image_props.rs) with the model in [`image_model.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-nbd/tests/it/image_model.rs): `image_props_incremental_equals_full_read` drives the steps a user's script performs, with the real `decide`, the real writer and the real NBD client, on a model of a disk, and requires that every backup has the same tree as a full read of the same disk at that moment and restores to the bytes of the disk. The model rotates the bitmaps as the [recipe](/docs/recipes/disk-image-backup/) does, for granularities from 512 B to 64 MiB, below, equal to and above the chunk, and runs directly on the source and through the NBD client and server. The generated steps are writes, backups, a resize (growing, shrinking, shrinking and growing back to the same size, each with the bitmaps dropped and the next generation used, as qemu requires), a backup of the same instance from another machine, a state file that is an older copy, a failure in the middle of a read, a rejected snapshot, a bitmap that is created after the read began, a skipped generation, an export without the bitmap and a clock that goes back. A run after any of these events must not be an increment, and a clean run on an export with a bitmap must be one, so the test cannot become empty. For every increment it also requires that the source was not read outside the dirty ranges (counted at the source and at the export), that no more bytes were read than the dirty ones, and that no more parent chunks were read than are partly dirty. A second test, `image_props_hostile_repository_equals_full_read`, damages and swaps the pack files of the parent between steps and requires the same result, and that restore of the increment and of the full read either both succeed with the disk's bytes or both fail with the same error. Both run with 16 cases in the tests of every pull request (about 25 seconds each in a debug build) and with 512 cases every night, in the job `image-props` of `fuzz.yml`. The generators count the runs of each kind and the tests fail when a kind stops being produced.
- Negative controls for the same test, in `image_props.rs`: the test is shown to fail when the contract is broken. A bitmap that is reset after a backup loses a write made during the read (`image_props_clear_after_backup_loses_a_window_write`), a bitmap that is recreated under its old name after a resize leaves an old tail in the result (`image_props_reused_name_after_a_resize_is_detected`), a bitmap that was reset without a backup loses a write (`image_props_stale_bitmap_is_detected`), a `g{N+1}` that is disabled loses a write made during the read (`image_props_disabled_next_bitmap_loses_a_window_write`), and a disk replaced or reverted behind the same socket, its bitmaps kept, leaves bytes of the old disk in the increment (`image_props_replaced_or_reverted_disk_is_missed`). The same sequences with the rotation, or with the next generation after the resize, equal a full read. These controls state what the protection is: the rotation contract, not a check that `lode` can make.
- The rule that decides between a full read and an increment, in [`image_binding.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/image_binding.rs): a table of 23 rows that checks every reason of `full_reason` and the order in which they apply, the forked chain of generations, and a property: a run is an increment exactly when every condition holds. The names, the state file and the metadata round-trip on generated inputs, and tables of damaged state files, names and metadata are refused.

Limit: the generated repositories are small (two to four backups, files of a few tens of KiB), and shards are planted before the cycle starts, not during it.

## Mutation testing

A test suite can pass because it checks little. [`cargo-mutants`](https://mutants.rs/) changes the code one small step at a time (a `>` becomes `>=`, a function returns a default) and runs the tests; a change that no test notices is a surviving mutant, and means that a test is missing or too weak. It is run on the code whose mistakes lose data.

- Three groups, set in [`mutants.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/mutants.yml): the whole of `lodestore-format`, the cleanup code of the server (`crates/lodestore-server/src/maintenance/gc/`, with the `gc_` and `adv_gc_` test files), and the retention rules (`crates/lodestore-policy/src/retention.rs`). Each is split into shards that run in parallel, at most six at once.
- The full run is weekly (Saturday) and by hand. It does not run on pull requests: it takes hours.
- [`.github/mutants-baseline.json`](https://github.com/lodestore/lodestore/blob/main/.github/mutants-baseline.json) is where the result is pinned: per group, the number of mutants and the names of the survivors. [`scripts/mutants-ratchet.sh`](https://github.com/lodestore/lodestore/blob/main/scripts/mutants-ratchet.sh) fails the weekly run for a survivor that is not in the baseline, for fewer mutants than the baseline (a lost shard or a narrowed run), and for any survivor in the code that decides what is deleted (cleanup and retention). The baseline has not been filled in yet: all three groups are `null`, so the weekly run prints its results and fails nothing. The first baseline comes from a full run.
- Two checks do run on every pull request, in the job `check` of `ci.yml`: every `#[mutants::skip]` in `crates/*/src` must have a reason in a `//` comment on the line above, `.cargo/mutants.toml` may not use `exclude_` options, and once the baseline has a number of skips it cannot grow; and a pull request cannot loosen the baseline of its base branch (a number back to `null`, a new survivor, a survivor in the deletion code, more skips).
- [`mutants-diff.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/mutants-diff.yml) runs on a pull request that changes `lodestore-format`, the cleanup code or the retention rules. It mutates only the lines the pull request changed, split over four parallel jobs; for `lodestore-format` it leaves out the slow S3 and shard-size tests, which the weekly run covers. It is advisory and goes red when a changed line has a survivor. It does not run on a pull request that changes none of those sources (for example only the `tests/` folders), so a test weakened in such a change is found by the weekly run, after the merge.

Limit: a surviving mutant is a hint, not proof. Some mutants change nothing that can be observed, and the baseline records them as they are. The groups cover three parts of the code, not the whole repository.

## What the bucket looks like from outside

- [`no_plaintext.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/no_plaintext.rs) backs up files whose names and contents are recognizable and then searches every object, names included, for them. Nothing may appear.
- [`s3_write_only.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/s3_write_only.rs) uses an S3 user with a write-only policy from the test kit, close to what an agent key gets. It checks that this user can back up and deduplicate, and cannot delete or read packs. Lodestore's own writer refuses to replace an object (`If-None-Match: *`), but that is the client behaving, not a limit on the key: with the policy generated for MinIO an agent key can overwrite, and `wizard_s3_write_only_key_can_overwrite_on_minio` in [`repos_s3.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/repos_s3.rs) records it. Versioning or Object Lock is what protects the data there. On MinIO the key holder sends a plain `PutObject`, and nothing in the policy refuses it.
- [`restore_hostile.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/restore_hostile.rs) feeds the restore snapshots that someone holding the writer keys could forge (names such as `..`, duplicate or unsorted entries, size lies, decompression bombs) and a target with planted symlinks. The restore must refuse or stay inside the target. It also builds directory trees that reach one shared subdirectory from many parents and checks that the walk of a restore stops at the budget with an error that names the limit; the budget is shrunk in the test, so no 2^30 entries are built. The server tests of the listing, the search and the restore plan check how that error reaches the caller. The same file builds directories whose pieces add up to more than 1 GiB of tree data, and paths whose open directories hold more than 2 GiB, with the real limits and no real data (`restore_hostile_wide_directory_stops_by_byte_limit`, `restore_hostile_held_bytes_stop_by_limit`): the restore, the listing and the summary stop with the limit named before the pieces are downloaded, also when the index did not list a piece (`restore_hostile_byte_limit_counts_pieces_the_index_did_not_list`) and when the bytes are the lists of pieces of subdirectories (`restore_hostile_held_bytes_count_subtree_lists`). A file whose size in the index is a lie, reached through a tree of directories that share a subdirectory, has its chunks read once and not once per visit (`restore_hostile_diamond_size_lie_reads_chunks_once`), and every visit of it charges its chunks to the budget of the walk whatever the size of the cache of lengths (`restore_hostile_size_lie_counts_against_the_walk`); the structure check gives the finding with the text of the restore's error on the same boundary and reads the chunks once (`check_hostile_size_lie_counts_against_the_walk_like_restore`). A file that names one chunk many times and does not add up makes a restore and the structure check read that chunk exactly once with 4, 64 and 1024 references (`restore_hostile_repeated_chunk_reads_do_not_grow`, `check_hostile_repeated_chunk_reads_do_not_grow`); when the reads of such chunks pass the budget of the run, the structure check reports the file as not checked for every snapshot of its directory and goes on (`check_hostile_chunk_read_limit_is_a_finding`), and after the budget is spent it reads the chunk of none of the 4, 64 or 1024 files that follow (`check_hostile_spent_budget_reads_no_more_chunks`); a damaged chunk that 4, 64 or 1024 such files name is read once, with the default budget and with one its first read spends (`check_hostile_unreadable_chunk_reads_do_not_grow`); a planted shard that lists 64 one-byte chunks first at 8 copies of 64 KiB that do not open makes the check stop at a budget of four such frames, read no more than the budget and one frame past it, and report the files as not checked (`check_hostile_failed_copies_count_against_the_budget`). A planted shard that lists the root tree first at a 1 MiB frame of another blob leaves a restore and the check at the same walk budget, to the byte (`check_hostile_failed_tree_copy_counts_like_restore`). A directory that lists one empty tree as its piece 64 or 2000 times costs the check the reads of one (`check_hostile_repeated_piece_reads_do_not_grow`). A tree of no nodes and 1 KiB of a field the schema does not have, listed ten times as a piece, is charged for every listing: the check reports the snapshot exactly when a restore stops on the bytes held at once, the bytes of one directory or the bytes of the walk (`check_hostile_repeated_blank_piece_counts_like_restore`), and listing it 2000 times costs the reads of one (`check_hostile_repeated_blank_piece_reads_do_not_grow`). A directory that lists a piece with entries twice is reported for the order of its names without a second read (`check_hostile_repeated_piece_with_entries_is_a_finding`). A copy of an honest snapshot that names only a planted shard listing every tree larger, or every chunk one byte short in a shard listed after the real one, is refused by a restore with a tight limit, and the structure check reports the copy and not the original (`check_hostile_snapshot_shard_lists_trees_larger_like_restore`, `check_hostile_snapshot_shard_lists_chunks_wrong_like_restore`). The parent snapshot that `lode backup` reads is held to the limits of a path (`parent_tree_held_entries_stop_by_limit`, `parent_tree_held_bytes_stop_by_limit`). `tree_limits.rs` in the server tests plants a directory of 65 pieces of about 16 MiB in the bucket and checks that a listing, a summary and the preparation of an archive answer `400` `tree_too_large` with the limit named, that an archive download is cut off and not completed, and that a search ends as incomplete with `walk_limit` and still finds the files of an ordinary snapshot (`tree_limits_wide_directory_is_refused_on_every_http_path`); `restore_plan.rs` checks that the plan of a restore job for an agent refuses the same directory (`restore_plan_refuses_wide_directory_by_byte_limit`).

## Cleanup (garbage collection)

Cleanup is the only code that deletes data, so it gets the most scrutiny. Its design is described in [Cleanup](/docs/guides/gc/).

- [`gc_interleave.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/gc_interleave.rs) runs backups and the cleanup steps in every order the protocol allows, with one or two backups, and after each order restores every snapshot in the bucket. The model assumes the rule the design relies on: a backup that opened before the cleanup manifest was published finishes before the verification step, which the time limit of an agent job guarantees. A backup that goes past that limit is outside what this test shows.
- [`gc_chaos.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/gc_chaos.rs) runs two real agents against a real server. Backups run while a cleanup cycle marks, verifies and sweeps, and in one variant the server restarts in the middle of the cycle. Afterwards every kept snapshot must restore and no backup job may have failed.
- [`attest_verify.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/attest_verify.rs) checks the server's verification of each new backup. A backup still waiting for verification when a cleanup cycle compacts and sweeps the index is verified, not failed; a sweep waits for a verification that is reading; a backup that deduplicated against a shard naming a missing pack fails at once with `verification_failed`; a job that reports another job's snapshot fails; and a host's shard that lists `supersedes` is never attested. [`gc_cycle.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/gc_cycle.rs) also shows that a cycle resumed after the upgrade signs the index before it compacts, that it deletes attestations failing the MAC while keeping a valid one, and that it reports packs it could not repack.
- `gc_s3_week_long_backup_keeps_its_data` in [`gc_s3.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/gc_s3.rs) runs on MinIO with the server clock moved forward. A backup with a time limit of 7 days is opened before the cleanup manifest is published and committed at the very end of its limit. Cleanup must wait through the pause without deleting a pack, the backup must deduplicate against packs that were marked, and afterwards every snapshot restores. The test fails when the pause stops covering the running backup: with that protection removed, the restore of the week-long backup fails on a missing blob.
- [`gc_props.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/gc_props.rs), described under [Property tests](#property-tests), found two defects here. An index shard planted with the writer keys that names blobs in packs that do not exist stopped every cleanup cycle (`gc_survey_places_blobs_in_packs_that_exist`), and then made cleanup rewrite the same pack in every cycle without freeing it (`gc_repack_moves_blobs_a_planted_shard_misplaces`). Data was not lost either way. Cleanup now places a live blob in a pack that exists, and planning and repack read the same index.
- [`gc_mark.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/gc_mark.rs) shows that the survey step only reads and stops on anything it cannot follow. [`gc_repack.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/gc_repack.rs) runs repack, verify, compact and sweep on a real repository in a folder. [`gc_locks.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/gc_locks.rs) shows that a writer does not trust candidate packs that cleanup has published for deduplication, and stops on a manifest it cannot read.

## Compromised-agent suite

This suite models a host whose agent is controlled by an attacker: someone who holds the writer keys and can put shards and packs of their own in the bucket. It also models a stolen API token with too few scopes, a local user who talks to an agent's socket, and a server that is taken over. Every test in it is named with the prefix `adv_` and runs on a local folder, so it needs no MinIO. The question each one asks is the same: after the attack, does every snapshot still restore, and does a backup that cannot be restored never end as a success? See [Index metadata from a compromised agent](/docs/security/threat-model/#index-metadata-from-a-compromised-agent) for what is claimed.

- Run it with [`scripts/test-adversarial.sh`](https://github.com/lodestore/lodestore/blob/main/scripts/test-adversarial.sh), which is `cargo nextest run --workspace --profile adversarial`. CI runs the same command in the step "Run the compromised-agent suite" of [`ci.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/ci.yml), after the normal tests.
- The scenarios in `crates/lodestore-format/tests/it` (`adv_gc_mark.rs`, `adv_gc.rs`, `adv_restore.rs`): a shard that supersedes real shards does not stop the survey step of cleanup; forged offsets and a forged `supersedes` do not make cleanup lose a snapshot, also through compaction and sweep; a pack whose surviving copy does not open is kept; a planted pack that cannot be opened does not stop cleanup, nor does a shard with a malformed record; and a restore reads the real copy of a blob when a false record is listed first, whether it names wrong offsets, a pack of an unknown version or a wrong size. An index shard planted in the listing with a size of 5 GiB is read neither by cleanup (`adv_gc_skips_planted_oversized_shard`) nor by the writer of a backup (`adv_writer_skips_planted_oversized_shard`), and a pack planted with a size of 5 GiB is not read by the index rebuild (`adv_rebuild_skips_planted_oversized_pack`): each is left out, reported, and the object is never downloaded. A writer marker planted with a size of 5 GiB is not read and counts as an open writer, so cleanup waits for it instead of failing (`adv_planted_oversized_writer_marker_is_not_read_and_holds_gc`, in `adv_gc.rs`): the store in that test fails any whole-object read. [`shard_limits.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-format/tests/it/shard_limits.rs) and `shard_split.rs` in the same folder check the limits on honest data: the edge of the size limit, a signed shard above it, up to 1 GiB, that is read and restored once its content matches its name (`shard_limit_attested_shard_is_read_up_to_the_signed_cap`), one above 1 GiB that is left out whether or not the listing shows its size (`shard_limit_attested_shard_over_the_signed_cap_is_skipped`, `shard_limit_attested_shard_without_listing_stops_at_the_signed_cap`), an unsigned shard above 64 MiB that is left out on every path, a signed shard overwritten afterwards that is not loaded, a failed read of the attestations that is read again on the next load (`shard_limit_failed_attestation_read_is_retried`), and the writers cutting shards under the limit. `bounded_reads.rs` checks that snapshots, the writer's `config`, packs, attestations and the checks read objects with a ranged read and refuse an object swapped for a larger one after the listing, and `restore_hostile.rs` checks that a directory above 2^23 entries, and an operation that would hold more than 2^24 entries, stop with an error that names the limit, also when the entries are those of directories already walked (`restore_hostile_held_entries_count_consumed_directories`). The same file checks that the structure check reports such snapshots as `unreadable_tree` and checks the next one, stops reading a directory at the piece that passes the limit of one directory, and counts the directories above it at full length (`check_hostile_wide_directory_is_a_finding`, `check_hostile_held_entries_are_a_finding`, `check_hostile_held_entries_count_consumed_directories`), and the same for the limits on bytes (`check_hostile_wide_directory_over_byte_limit_is_a_finding`, `check_hostile_held_bytes_are_a_finding`, `check_hostile_held_bytes_count_subtree_lists`), and that a directory shared by a shallow and a deep snapshot is a finding only for the deep one, whichever the check reads first (`check_hostile_held_shared_dir_shallow_then_deep`, `check_hostile_held_shared_dir_deep_then_shallow`). A finding in or below a directory that two snapshots share is reported for both, whichever the check reads first (`check_hostile_finding_below_shared_dir_reaches_every_snapshot`), a tree whose pack is missing from the bucket is a finding for each snapshot and the check goes on (`check_hostile_missing_tree_pack_is_a_snapshot_finding`), and a path over the limit that many snapshots share is read once, down to the leaf (`check_hostile_shared_cut_path_is_walked_once`). Each directory is read once on a diamond whose paths are incomparable in entries and bytes, and under snapshots whose roots are incomparable, so the reads equal the trees checked (`check_hostile_incomparable_paths_read_each_tree_once`). A directory whose subtree alone passes the limit of a path or of nesting is a finding for the snapshot that reaches it and the rest of that directory is not walked, while a snapshot that reaches only the rest still gets its findings (`check_hostile_directory_over_path_limit_alone_skips_the_rest`, `check_hostile_directory_too_deep_alone_skips_the_rest`). A directory that is deep for one snapshot and shallow for another is a finding for the deep one only, in either order (`check_hostile_depth_cut_shared_dir_shallow_first`, `check_hostile_depth_cut_shared_dir_deep_first`). A hardlink group whose members differ is a finding for the snapshot that has both members and not for one that shares only a directory, in either order (`check_hostile_hardlink_conflict_stays_with_its_snapshot`), and a conflict inside a shared directory reaches every snapshot that reaches the directory (`check_hostile_hardlink_conflict_inside_shared_dir_reaches_every_snapshot`). A subdirectory id that is not 32 bytes is a finding (`check_hostile_short_subtree_id_is_a_finding`). A snapshot that would pass the walk budget of a restore is a finding with the text of the restore's error (`check_hostile_fan_out_over_walk_budget_matches_restore`), and a tree of forty levels of two directories that name the same one below, which is 2^40 visits, is reported without being expanded (`check_hostile_huge_diamond_is_not_expanded`). `backup_behavior.rs` checks that the writer refuses a tree a restore could not hold and writes no snapshot (`backup_refuses_tree_over_held_limit`, and for the bytes `backup_refuses_directory_over_byte_limit` and `backup_refuses_tree_over_held_byte_limit`, which find the edge by number and check that the writer and the reader agree on it), and `restore_modes.rs` in `lode-cli` that `lode restore` names `--allow-large-directories` and that the flag restores such a snapshot, also when the limit is the bytes (`restore_large_directory_by_bytes_needs_the_flag`). `gc_mark.rs` checks that a snapshot read in a size other than the listed one stops the survey (`gc_mark_snapshot_body_not_of_listed_size_stops_mark`), and that a snapshot whose tree packs are gone is quarantined and does not stop the survey (`gc_mark_quarantine_missing_tree_pack`), `gc_repack.rs` that repack names a pack longer than its listing, `bounded_reads.rs` that an object listed as empty that has vanished is reported as gone, and `check.rs` that an oversized `config` is the finding `unreadable_config` and not an abort.

## Disk image increments against qemu-nbd

The property tests above use a model of a disk and the NBD server of the repository. [`image_qemu.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lode-cli/tests/it/image_qemu.rs) runs `lode backup --bitmap` against a real `qemu-nbd -r -f qcow2 -B g{N} -B g{N+1}` on a qcow2 disk with the same rotation as the [recipe](/docs/recipes/disk-image-backup/). The tests are marked `#[ignore]`; `ci.yml` installs `qemu-utils` from the distribution and runs them in a step of its own on every pull request. In CI a missing or too old tool fails the step instead of skipping the test.

- `qemu_incremental_matches_the_disk_at_every_granularity`: four granularities of the bitmap (512 B, 64 KiB, 4 MiB and 16 MiB) on a disk of 40 MiB in three segments, one full read and five rounds each. The writes land inside a chunk (unaligned), across a chunk boundary, across both segment boundaries, as a zeroed range, and at the end of the disk, and one write is made after the export stops and before `g{N}` is deleted. After every round the restored image equals the disk as `qemu-img convert -O raw` writes it. qemu lets a client read outside the dirty ranges, so a proxy on the socket records every read of `lode`, and the test requires every read to lie inside the dirty granules of `g{N}` (the test keeps its own set for every live bitmap), the sum of the reads to be at most the dirty bytes, and the list not to be empty.
- `qemu_export_without_the_bitmap_reads_in_full`: an export without `-B` under `--bitmap` is a full read (`bitmap_missing`), the next run with both bitmaps is a full read (`no_state`), and the one after is an increment.
- `qemu_resize_forces_a_full_read`: growing, shrinking, and shrinking and growing back to the old size. The test removes every bitmap before the resize and continues with the next generation, as the recipe says; it does not depend on what qemu does with a bitmap on resize. The run after it is a full read with `gen_mismatch` (the generation is checked before the size), its restore equals the disk, and the run after that is an increment again. `size_changed` itself is covered by the model tests and by the tests of `lode` below, not by qemu.

Tested with qemu 10.1.3 (macOS, Homebrew) and qemu 10.2.1 (Linux, Ubuntu `qemu-utils`). CI runs the version that `ubuntu-latest` ships, and the step prints it. Older versions are listed under [What we have not verified](#what-we-have-not-verified).

[`image_bitmap.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lode-cli/tests/it/image_bitmap.rs) runs `lode backup --image nbd+unix://...` against the test NBD server in 15 tests: the first increment after a full read, the refusals of a wrong bitmap name and of flags that do not go together, a changed export without `--name`, the order of consuming and writing the state, the lock, an unconfirmed next bitmap, the restart of a chain, a run that is aborted, and the events that must give a full read and a restore equal to the disk: a rejected snapshot, a lost cache (which still stores nothing new for an unchanged disk), a newer snapshot from another machine, a resized disk, a tampered state file and two different exports under one explicit `--name`.

## The quickstart check

[`scripts/quickstart-ci.sh`](https://github.com/lodestore/lodestore/blob/main/scripts/quickstart-ci.sh) takes the marked command blocks from the [Quickstart](/docs/quickstart/) page: starting the server, the setup link, the agent install and the restore without the server. It starts MinIO and the server image, goes through the setup wizard and the host enrollment with the install script, makes a backup, and restores it through the API. It then compares the restored tree with the original using `diff -r` and a list of sha256 sums. Finally it stops the server container and restores again with only `lode`, the bucket and the password, and compares again. The whole run has a budget of 600 seconds, which is the "first backup in ten minutes" promise.

Limit: the script drives the API where the page describes clicks in the interface (wizard, adding a host, restore). It proves the mechanics, not the screens; the screens are covered by the browser test below. The policy of the first backup is set in the script and does not come from the page. The check after publishing adds `--from-github` to the install command, so it installs the agent from GitHub Releases and does not test the download from your server. It installs `minisign` first. It checks the release signature with the project key only for a release whose image already carries this installer, because that mode runs the `install.sh` of the published image; in a pull request the `--from-github` checks are the `install_verify_` tests. Three parts of the page are not run: the local folder section, the "With HTTPS" section (Caddy and a public DNS name) and the download of `lode` from a release (the script installs the `lode` it just built). Without Docker, [`docs/scripts/quickstart-doc.test.mjs`](https://github.com/lodestore/lodestore/blob/main/docs/scripts/quickstart-doc.test.mjs) checks the page itself on every build of the docs: every variable is set before it is used, container and volume names do not repeat, the minisign key is the second line of `project.pub`, `lode` is installed only in the same `&&` chain as its signature check, the CI markers are the known four, and the HTTPS command has no `--insecure`. It reads the text; it does not run these commands.

The job `e2e` of the same workflow (`scripts/quickstart-ci.sh <image> --e2e`) drives the interface itself. [`web/e2e/first-backup.e2e.ts`](https://github.com/lodestore/lodestore/blob/main/web/e2e/first-backup.e2e.ts) runs a Playwright browser against the server image and MinIO: the setup, the repository wizard with an S3 bucket and the recovery key, adding a host (the test installs the agent with the install command of the quickstart page and the token the interface produced, and waits for the host to come online), a policy, a backup run from the interface and a restore of the data folder from the interface. On the screens it passes (setup, choose storage, check access, recovery key, add host, new policy, the backup job, restore) [axe](https://github.com/dequelabs/axe-core) checks WCAG 2 level A and AA, and a violation fails the run. The script then compares the restored tree with the original by `diff -r` and sha256 sums. It runs for pull requests, not for the post-publish check.

Limit: this is one path in one browser at one window size. It compares no screenshots, does not try other widths or the dark theme, and the automated accessibility rules find only the part of the problems that a rule can express. The restore without the server is checked by the first job, not by this one.

| `mutants-diff` | [`mutants-diff.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/mutants-diff.yml) | pull requests that change `lodestore-format`, the cleanup code or the retention rules | mutation of the changed lines only; advisory |

A push to `main` also uploads the built site to the host. |
| `release` | [`release.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/release.yml) | on a `v*` tag; by hand from a branch as a dry run into separate `-dryrun` packages, with no release | runs `ci`, `build` (without the build cache) and `linux-root`, signs the binaries with minisign, builds the images and the chart, signs the image and the chart with cosign and attests provenance and an SBOM by digest, smoke-tests both architectures, runs the quickstart on the candidate image, then a job `verify` runs the commands of the release notes on the staged files; only then it publishes. After publishing it runs the quickstart again against the published image and opens an issue if that fails |

`scripts/adversarial-vs-release.sh` is not in any workflow: it is run by hand before a release.

The long runs are kept off the pull request, so that a pull request does not wait hours for them: the full fuzz run is nightly and the full mutation run is weekly. What a pull request gets is the smoke fuzz of six targets and the mutation of its own changed lines, and only when it changes the source of the checked code.

Two consequences. The PostgreSQL run is not part of every pull request; it runs weekly and before a release. And the post-publish quickstart cannot stop a release that is already public, it can only report.

The `docs` workflow does not exercise the deploy or the nginx config: the upload runs only on `main` once deploys are switched on, and [`deploy/site/test-config.sh`](https://github.com/lodestore/lodestore/blob/main/deploy/site/test-config.sh) (headers, cache, gzip, redirects against a built site) is run by hand.

The nextest `ci` profile in [`.config/nextest.toml`](https://github.com/lodestore/lodestore/blob/main/.config/nextest.toml) retries one test, `reenroll_keeps_agent_id_and_rebinds_snapshots`, up to three times. That is a known flaky test and it is not about stored data, and it is the only retry in that profile. A web test sets its own retry in its options, `{ retry: n }`, so search `web/src` for those.

## What we have not verified

- **Object Lock on real AWS S3.** All Object Lock behavior is checked against MinIO. MinIO and AWS can differ in details such as how retention is reported, how long a lock lasts and how delete markers behave. Until a run against AWS exists, treat Object Lock support on AWS as expected, not demonstrated.
- **The refusal of overwrites in the AWS policy.** No test covers the `Deny` on `s3:if-none-match` that the generated AWS policy ends with. The tests that touch overwriting use the MinIO policy, which leaves it out.
- **`#[ignore]`d tests outside the filters.** The `linux-root` workflow starts only the filters in [`linux-root.yml`](https://github.com/lodestore/lodestore/blob/main/.github/workflows/linux-root.yml). An ignored test that matches none of them does not run in CI. Check that file for `hooks_rejects_foreign_owner`, which guards the [hook ownership rule](/docs/security/threat-model/#backup-hooks), `special_files_warn_devices` and `download_archive_zip64_large`.
- **A segment of 256 GiB.** The tests cut an image into segments of two chunks (8 MiB), so the logic of segments is checked, not the memory and the time of a real segment. The largest image is checked as a layout of 64 segments that are all holes.
- **The head limit of a restore through the server, end to end.** An image with more than about 350 thousand extents cannot be built in a test. The limit is checked on a synthetic node, and the wiring by the fact that both the queue and the planner call the same check.
- **Zeros for holes on a device.** `lode restore --to-device` writes the holes as zeros in blocks of 64 KiB and does not use `fallocate`, so an image with holes of hundreds of GiB takes as long as writing them. The tests use small images. The check that a device is not in use was tried on a loop device with ext4; it was not tried on a disk with partitions, and it cannot see a process that holds the device open without an exclusive lock.
- **Incremental image backups on a real Proxmox node.** The shape of the NBD export of Proxmox, the granularity of its bitmaps and its speed are not tested; that is phase 25. Bitmap managers that reset a bitmap when a client connects, as the Proxmox provider does, are not supported and not tested (phase 26): with such a manager a reset bitmap looks like a good one to `lode`.
- **A bitmap that was recreated under the same name.** Over NBD `lode` sees only that `g{N}` and `g{N+1}` exist. A bitmap that was recreated or reset behind its back is not visible, and an increment made from it misses writes. The negative controls of the property test show that the test would catch it; nothing in `lode` does. The protection is the rotation contract of the recipe.
- **Versions of qemu other than 10.1 and 10.2.** The helper of the tests accepts qemu 8.2 and newer, but no run was made on a version older than 10.1, and the claim that two `-B` options and bitmaps on a resized disk work on 8.2 is not checked. The version that the CI runner has is in the log of its step, not here.
- **A disk that is written during the read.** An increment reads the source once, without a snapshot of its own, like a full read; a consistent result needs a quiet disk or a snapshot of the volume that the snapshot manager takes. The qemu test writes in the window between the end of the export and the deletion of `g{N}`, not during the read.
- **Large disks.** The qemu tests use a disk of 40 MiB and the model one of up to 22 MiB. The time and memory of the block status of a large disk with a fine bitmap are not measured.
- **Discovery on a real Proxmox node.** The scan of `/etc/pve` is tested against a directory that imitates it, with sparse and oversized files, links and a hung read. It has not run on a live Proxmox node, and whether `.vmlist` and `.members` are regular files there, and how a stopped `pmxcfs` looks to the agent, is taken from the documentation of Proxmox. The PostgreSQL and MySQL scans run against the real servers only by hand, on one Linux distribution. A PostgreSQL refusal is recognised by its English text, and nothing tests another `lc_messages`.
- **Alert delivery to real services.** Alerts to Telegram, Slack, a webhook and SMTP run through the server's whole pipeline against local stand-ins, with retries, the failed state, the reminder and the resolved message checked on a moved clock ([`notify.rs`](https://github.com/lodestore/lodestore/blob/main/crates/lodestore-server/tests/it/notify.rs)). The stand-ins check the request and the error handling. No test sends a message through the real Telegram or Slack, or a real mail server, so a change in what those services accept is not caught.
- **The limits themselves are estimates.** The ceilings on index shards (64 MiB for a shard the server has not signed, on every path including a restore; 1 GiB for a signed shard, which is read once its content hashes to its name), on the walk of a directory tree (2^30 entries and 512 GiB of directory data per operation, 2^23 entries and 1 GiB of tree data in one directory, 2^24 entries and 2 GiB of tree data held at once) and on Argon2 work per opening (`m × t` of at most 2^24, counted over the slots of the kind the secret opens) and on the key slots read per opening (1024) were chosen by calculation, not measured on large real repositories. The tests show that each limit is enforced, not that no honest repository will ever reach it.
- **The Argon2 budget cannot tell a planted slot from the real one.** A host with the writer keys can add valid password slots that cost less than the real one. The opening tries the cheapest slots first, so enough of them use up the budget before the real slot is tried, and opening with the password then refuses and asks you to remove the slots that are not needed. The recovery key starts no Argon2 and the server opens the repository with the master key in its database, so neither is affected by the budget. The count is different: an opening reads the first 1024 key slots in the order of the listing, so more than 1024 planted slots listed before the real one block the recovery key for that opening too, with the same error. That needs write access to `keys/`, which agent keys do not have, and the server opening with its master key is unaffected. The tests show that an opening reads at most 1024 slots and names the ones it did not try (`open_reads_at_most_max_key_slots`, `open_names_the_slots_past_the_cap`, in `repo.rs`); no test makes the budget or the count distinguish a planted slot from the real one, because the format cannot without the password (T-14-69).
- **A signed shard has a high size limit, not a low one.** A signed shard is read up to 1 GiB. Before it is loaded whole, its content is read in pieces of 64 MiB and hashed against its name, so the memory a reader needs is bounded by the real shard, and above 1 GiB it is left out. An object that was overwritten under a signed name on a storage that does not refuse overwrites (no `If-None-Match`) is read in pieces on every read and then not loaded: that costs traffic, not memory, at most about 1 GiB plus 64 MiB per read (T-14-74). The tests cover the signed shard above 64 MiB, the one above 1 GiB, the one with no listing and the overwritten one; the bound on the traffic is asserted with a store that counts bytes, not measured on a real bucket.
- **The gRPC limits at their real values.** The cap of 4096 connections, and the share of 1024 for one client address (IPv6 by its /56), are tested with small caps in unit tests of the connection wrapper, and there is no test of the limit of 32 streams per connection. The timeouts of 10 seconds are tested at their real value for REST and for the TLS handshake of gRPC.
- **Mail with TLS from the first byte.** `smtp_connects_to_the_checked_address` shows that the server connects to the address it has checked, and not to the name. The timeline tests deliver mail through a stand-in that speaks STARTTLS (`security: starttls`), with a certificate from a test authority. The stand-in does not speak the other mode, `security: tls`, where the connection is encrypted from the start, usually on port 465: that mode shares the way the certificate is checked, but no test completes a delivery with it.
- **A renewal during a restore is tested by chance of timing.** `adv_restore_survives_certificate_renew` restarts restores of a 64 MiB file, up to forty times, until a renewal falls inside one and the restore read packs both before and after it. It cannot pass without that, and fails with a message that lists the reads per serial when none of the runs did.
- **The session conflict alert behind a proxy.** The conflict rule is tested with two addresses that the test connects from; no test puts a load balancer or a NAT pool in between.
- **Fuzzing and mutation testing are scheduled runs, not gates.** The fuzzers get 5 minutes per target per night, and a pull request gets 30 seconds on six targets. The full mutation run is weekly, and [`.github/mutants-baseline.json`](https://github.com/lodestore/lodestore/blob/main/.github/mutants-baseline.json) has no baseline yet, so until it is filled in a surviving mutant is reported and fails nothing. The mutation of a pull request covers its changed lines of source only; a change that weakens a test and touches no source is found by the weekly run, after the merge. The hostile-restore tests and the compromised-agent suite are still hand-written cases that find what someone thought of; the fuzzers and generators widen that, and do not close it.
- **The browser test covers one path.** The interface is driven through setup, adding a host, a policy, a backup and a restore, with an accessibility scan of each screen. There are no screenshot comparisons, no other window sizes or the dark theme, and no browser other than Chromium.
- **Test storage rests on an archived project.** The upstream MinIO repository is archived, and the tests use one pinned release. If that download disappears or stops working on a new platform, the S3 tests need another S3 server. The choice of a replacement is open.
- **Platforms.** CI runs on Linux x86_64 only, plus an arm64 image smoke test at release. The agent supports Linux on x86_64 and arm64. The tests are not run on macOS or Windows in CI.
- **Scale.** Nothing here measures speed, memory or behavior with hundreds of hosts or billions of objects.
- **Operations.** Restoring from a real disaster in your environment, including your IAM policies and network, is something only you can test. Run a [`restore` check](/docs/guides/checks/) and the quickstart's restore without the server on your own bucket before you depend on it.
