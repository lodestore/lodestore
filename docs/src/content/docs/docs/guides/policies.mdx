A `BackupPolicy` is one strict YAML document shared by the UI, `lode apply` and CI. This page covers the four blocks that make a policy run on its own and tell you when it does not: `spec.schedule`, `spec.retention`, `spec.limits` and `spec.alerts`. All four are optional. A policy without them runs only when started by hand, keeps every snapshot and uploads without limits. The `apiVersion` is `lodestore.io/v1alpha1` for a policy of files; a policy with a `spec.source` uses `lodestore.io/v1alpha2` (see [source](#source-what-a-policy-backs-up)).

```yaml
apiVersion: lodestore.io/v1alpha1
kind: BackupPolicy
metadata:
  name: etc-and-home
spec:
  repository: main
  paths:
  - /etc
  - /home
  schedule:
    cron: 30 2 * * *
    timezone: Europe/Kyiv
    jitter: 15m
    catchUpWindow: 24h
  retention:
    keepLast: 3
    keepDaily: 7
    keepWeekly: 4
    keepMonthly: 6
  limits:
    uploadRate: 50MiB/s
    nice: 10
    ioniceClass: best-effort
    ioniceLevel: 4
    maxRuntime: 12h
  alerts:
    maxAge: 36h
```

Unknown fields are rejected with the line and column of the typo.

## source: what a policy backs up

Without `spec.source` a policy backs up the files in `spec.paths`, and every policy on this page so far does. `spec.source` names another kind of source and needs `apiVersion: lodestore.io/v1alpha2`; a `v1alpha1` document that has a `source` is refused. The `type` selects the block, and the other fields of the block sit next to it:

| `type` | Fields | Selects |
| --- | --- | --- |
| `files` | none | The files in `spec.paths`, as without a source. `paths`, `exclude`, `oneFileSystem` and `excludeCaches` belong to this type only; the other types refuse them. |
| `proxmox-vm`, `proxmox-ct` | `vmids` (100 to 999999999, up to 1000), `pool`, `tags` (up to 20) | Virtual machines or containers of a Proxmox node by id, pool or tag. At least one of the three is required. A guest is selected when it matches any one of the three, and matches `tags` when it carries any one of the tags. |
| `postgres`, `mysql` | `databases`, `excludeDatabases` (names of 1 to 64 bytes, up to 1000 each) | Databases of a server (MySQL: schemas). With no `databases`, every database is selected, including ones created later. `excludeDatabases` is used only when `databases` is empty. |

```yaml
apiVersion: lodestore.io/v1alpha2
kind: BackupPolicy
metadata:
  name: nightly-guests
spec:
  repository: main
  source:
    type: proxmox-vm
    tags: [prod]
```

The server stores a policy of every type, whether it comes from the form, the YAML tab, the API or `lode apply`. The agent decides what it can run: a job of a type the agent cannot back up yet fails before it starts, see [Jobs that do not start](#jobs-that-do-not-start). A policy of `files` is exported in the old form: without `source` and with `apiVersion: lodestore.io/v1alpha1`, the same bytes as before. A policy with another source is exported as `v1alpha2`. A server of 0.2 does not read `v1alpha2`.

For guests, `vmids: [101]` with `tags: [prod]` selects VM 101 and every guest tagged `prod`; it does not require both. The selector of the policy chooses the hosts as for any policy; what the policy backs up on each host comes from what the agent of that host found there.

A policy of containers runs as one job for each selected container of the node that reported it, one at a time on a node. The selector is resolved against the list that the node sent after the job was queued, so a container created just before the run is included, and a container that already has a job in progress from this policy is skipped. The job waits in the queue for such a list for up to 30 minutes, and then fails with `source_unknown`. A container that moved to another node since the last list fails on the old node with `guest_not_local`, and the policy is run at once for it on the other host of the policy that now lists it, as a new job of that host. A node without the Lodestore plugin fails the job with `guest_plugin_missing`.

`lode policy validate FILE...` checks policy files offline, with the same rules as the server, and prints the path, line and column of each problem. It exits 0 when every file is valid and 3 when one is not; it needs no server and no token.

## What to back up in the policy form

The field **What to back up** is at the top of the policy form. It offers **Files** and the types that an agent has found on a host of the repository: **Virtual machines** and **Containers** when an agent found at least one guest of that kind, **PostgreSQL** and **MySQL** when an agent found a server. A card shows on how many of the selected hosts the type was found, for example "On 2 of 3 hosts", and how many of those agents are too old to back it up. A type that none of the selected hosts has is disabled with "Not found on the selected hosts". Choosing a type other than Files hides the path fields, which belong to Files only.

For guests the form shows **Guests**: pick them from a searchable list (25 rows at a time), take every guest of a pool, or take every guest with any of up to 20 tags. For PostgreSQL and MySQL it shows **Databases** or **Schemas** with three modes: all (including ones created later), pick, or all except the names you tick. The list is what the agents of the selected hosts reported in their last scan. A guest or database that is ticked in the policy but no longer reported stays in the list marked "Not found on the selected hosts", so it can be unticked. A pick with nothing ticked cannot be saved ("Pick at least one guest."), because an empty pick would otherwise mean everything. A selection that combines `vmids`, `pool` and `tags`, or `databases` and `excludeDatabases`, is kept as it is and shown with a note to edit it in the YAML tab. The YAML tab shows the same `spec.source` that `lode apply` takes.

**Matching hosts** shows, for a policy of guests or databases, how many instances the policy selects on each host, and marks a host whose jobs will fail, with the reason: the agent is too old to back up the type, the host has no Proxmox, PostgreSQL or MySQL, or none of the selected guests or databases are on it. When the agent has no recent list, or its list was cut short or could not be read, the host has no count and no mark of the last two kinds: the server does not guess, and the agent decides when the job comes. Jobs of containers are the exception: they wait for a list, see [Jobs that do not start](#jobs-that-do-not-start).

## Sources found on a host

The agent of each host scans for sources when it starts and every five minutes, and sends the last result with each heartbeat. A host page shows a **Sources** tab as soon as an agent has found a guest or a database. It lists:

- **Guests**: VM or CT, the id, name, pool and tags.
- **Databases**: grouped under their server with its port and version, one row per database. A server that the agent found but could not list shows a note instead of rows.
- **Files**: a row for the paths that a files policy covers.

Each row has a **Protection**: the policies that select it, **Not protected** when none does, or **Agent too old** when the agent finds the type but cannot back it up yet; an agent version that backs up the type clears it (see [Agent updates](/docs/guides/agent-updates/)). The filter **Not protected** shows what no policy covers. The table has 25 rows per page. A note names a list that the agent cut short, and a guest or database that another host also reports, such as a clone or a standby: both hosts report the same key, so `lode latest@<key>` needs `--host` (see [Which snapshot is `latest`](/docs/reference/cli/#which-snapshot-is-latest)).

What the agent finds, and where it stops:

| Source | Found from | Reported |
| --- | --- | --- |
| Proxmox | `/etc/pve`, read only and without starting a process: the guests of the node the agent runs on, and the cluster name from corosync, or the node name outside a cluster | VMID, VM or CT, name, tags, pool, UUID |
| PostgreSQL | A running cluster: a socket `.s.PGSQL.<port>` in `/run/postgresql`, `/var/run/postgresql` or `/tmp`, owned by `postgres`. The agent runs `psql` as `postgres` over the socket | System identifier, port, version, databases (not templates) |
| MySQL | A running `mysqld`: a socket in `/run/mysqld`, `/var/run/mysqld` or `/var/lib/mysql`, owned by `mysql`. The agent runs `mysql` as `root` over the socket (`auth_socket`) with `--local-infile=0` | Server UUID, port, version, schemas (not `information_schema`, `performance_schema`, `sys`) |

- A VM is identified by the UUID in its configuration. A VM whose UUID is zero, invalid or the same as another VM's on the node (a restored copy), and a VM whose configuration cannot be read, is not listed. A container has no UUID in Proxmox, so the agent generates one and keeps it in `/var/lib/lodestore/source-ids.json`; it never writes to the Proxmox configuration. A reinstalled node, a container migrated to another node and a reused VMID are therefore new instances. A container recreated with the same VMID between two scans is not told apart.
- The databases are read with constant queries over a local socket, with no password and no credentials in the agent configuration. If the agent cannot connect (no `psql` or `mysql` client in `/usr/bin`, a refused login, a timeout), the server is shown with its databases unknown, not empty. After a refused login, which includes a locked account, the agent does not try again for a day, or until the database server restarts. A PostgreSQL refusal is recognised from its English message only. A PostgreSQL database whose name is longer than 64 bytes or is not valid UTF-8 is not listed, and the list is marked as cut short. MariaDB is not listed as MySQL. A `mysqld` started with `skip_networking` has port 0.
- Only a running server is found: a stopped cluster leaves no socket and disappears from the list. If a policy expected one of its databases, [Source no longer selected](/docs/guides/alerts/#source-no-longer-selected) is raised an hour later.
- Limits: 1000 guests, 20 tags per guest, 16 database servers, 1000 databases per server, 64 bytes per name, 256 KiB per list. A tag or pool longer than 64 bytes is left out, and so is a cluster or node name longer than 63 bytes. A list over the size limit is not stored at all and counts as unknown. When anything is dropped, including tags past the twentieth, the list is marked as cut short, and the tab and the form say so.

The agents of this version find guests and databases but back up files only: guest and database backups are not part of them yet.

## Jobs that do not start

A job of a guest or database policy fails at once, before any hook runs, in the cases below. It shows in **Jobs** as a failed job with a message that says what to do, raises the usual **Backup failed** alert and carries its code in `error_code`:

| Code | When | What to do |
| --- | --- | --- |
| `source_agent_outdated` | The agent has not declared the capability `source:<type>` for the type of the policy. Agents of this version declare `source:files` and `source:proxmox-ct`. | Update the agent to a version that backs up the type. |
| `source_not_found` | The host has no source of the type, or the policy selects none of the guests or databases found on it. | Check what the policy backs up and where it runs. |
| `source_unknown` | A job of containers waited 30 minutes and the agent did not list its containers after the job was queued. | Check that the agent is online and up to date. |
| `guest_not_local` | The container is no longer on this node. The agent says which node it is on. | Nothing: the job is queued on the node that lists the container, if it is a host of the policy. Add that host to the policy otherwise. |
| `guest_plugin_missing` | The node reports that the Lodestore plugin is missing or was changed. | Run `lodestore-agent pve install` on the node. |

The server refuses a job for the second reason only on a recent, complete list: under 15 minutes old, collected after the job was queued, not cut short, and with no database server that could not be read. If the agent is offline, or its list is old, older than the job (a guest created while the job waited) or incomplete, a job of a virtual machine or a database goes to the agent, which checks its own scan and refuses with the same code. A job of containers waits for a list instead. What an agent reports never widens what it may do: it only narrows what the form offers and which jobs are handed out.

## Durations and rates

A duration is a whole number and one unit: `s`, `m`, `h`, `d` (24 hours), `w` (7 days) or `y` (365 days). Fractions and signs are not accepted.

A rate is a whole number, a binary unit (`B`, `KiB`, `MiB`, `GiB`) and `/s`, for example `800KiB/s` or `50MiB/s`. The minimum is `1KiB/s`.

## schedule

| Field | Meaning | Default |
| --- | --- | --- |
| `cron` | Required. Five fields (minute hour day month weekday) or one of `@hourly`, `@daily`, `@weekly`, `@monthly`. Seconds and years are not accepted. | |
| `timezone` | IANA name such as `Europe/Kyiv`. | `UTC` |
| `jitter` | Each host starts up to this much later than the slot. The offset is stable per host and policy, so a fleet does not start at the same second. `0s` to `24h`. | `15m` |
| `catchUpWindow` | A host that missed slots (offline, agent stopped) runs one backup when it returns, if the last missed slot is not older than this. `1m` to `30d`. | `24h` |

Missed slots are never replayed one by one: after an outage the host runs a single catch-up backup, or nothing if the window has passed.

A slot that comes while a manual run of the same policy is queued or running on the host waits for it. The scheduled backup starts when the manual run ends (as a catch-up backup when that is more than two minutes after the slot), so a run-now does not take the scheduled snapshot's place. Past `catchUpWindow` the slot is skipped like any missed slot. A slot that comes while a scheduled backup of the policy is still running is merged into it.

### Daylight saving time

The cron expression is evaluated on the wall clock of `timezone`. Every slot runs exactly once:

- A local time that does not exist (the clock jumps forward) runs once, at the first minute that exists after the gap. In `Europe/Kyiv` on 2026-03-29, `30 3 * * *` runs at 04:00. In `Australia/Lord_Howe`, where the shift is 30 minutes, `15 2 * * *` runs at 02:30 on 2026-10-04.
- A local time that happens twice (the clock goes back) runs only the first time. In `Europe/Kyiv` on 2026-10-25, `30 3 * * *` runs at the first 03:30 only. This holds for wildcard schedules too: `@hourly` in `America/New_York` on 2026-11-01 runs at 00:00 EDT, 01:00 EDT and 02:00 EST, and skips the second 01:00.

Schedules that are not a single fixed time of day, such as `*/30 * * * *` or `0,30 3 * * *`, skip local times that do not exist and rely on the next slot that does. The UI shows a note on days where a slot is skipped or repeated.

## retention

Retention follows `restic forget`. It runs per host and per source instance (a source instance is one guest, one database or the files of the host), on the snapshots of this policy only, after each successful backup. Snapshots made by `lode` or by other policies are never touched. For a policy of files there is one instance on each host, so nothing changes; for a policy of guests, each guest has its own history, and a guest backed up often does not push out the history of another.

| Field | Keeps |
| --- | --- |
| `keepLast` | The N newest snapshots. |
| `keepWithin` | Every snapshot received no earlier than the newest snapshot minus this duration (at least `1m`). The window is counted from the newest snapshot, not from the current time, so a host that stopped backing up does not lose its history. |
| `keepDaily` | The newest snapshot of each of the last N days that have snapshots. |
| `keepWeekly` | The newest snapshot of each of the last N ISO weeks (Monday first) that have snapshots. |
| `keepMonthly` | The newest snapshot of each of the last N months that have snapshots. |

Counts are whole numbers of 1 or more. A snapshot is kept if any rule keeps it. With no rules at all, nothing is forgotten.

### Scheduled and manual snapshots

The snapshots of a policy on a host form, for each source instance, up to three kinds of pool, and the rules above apply to each pool on its own:

- **Scheduled**: backups started by the schedule, including catch-up backups.
- **Manual**: backups started by hand, from the web interface, `lode server policies run`, `lode server jobs run` or the API.
- **Stdin**: snapshots of `lode backup --stdin --policy NAME` through the agent, only when the policy sets `includeStdin` (see below). Each stream name (`--name`) has its own pool.

A series of manual runs therefore rotates only the manual snapshots and never touches the scheduled history. A manual backup taken before a risky change stays until later manual backups push it out of the rules. Snapshots that were made before the server recorded how they started, and whose job records the server had already deleted (jobs are kept for 90 days), count as scheduled.

### Stdin snapshots

A snapshot made with `lode backup --stdin --policy NAME` is outside retention by default: it takes no slot in any rule and is never forgotten, like a stdin snapshot without a policy. It also does not count as the last successful backup of the policy for alerts and metrics. The name `NAME` must be a policy that selects the host, both when the stream starts and when it ends; otherwise the job fails on the server with `snapshot_policy_mismatch` and the snapshot is not counted under that policy. To let retention rotate them, set `includeStdin: true` under `retention`; they then form a pool for each stream name and push out neither manual nor scheduled snapshots, nor the snapshots of a stream of another name: a weekly `etcd.snap` is not rotated by an hourly `pg.dump`. Setting it needs the `snapshots:delete` scope for a token, like any other retention change. Clearing every retention rule in the policy form also turns `includeStdin` off, so rules added again in the same session do not bring it back.

```yaml
  retention:
    keepLast: 7
    includeStdin: true
```

Details that matter:

- Days, weeks and months are counted in the schedule's `timezone`, or in UTC when the policy has no schedule. Changing the time zone of a policy with retention moves the boundaries, so it needs `snapshots:delete` for a token.
- The time of a snapshot is the time the server received it (the storage object's modification time), not the time the backup started. This survives a catalog rebuild. S3 keeps this time in whole seconds, so snapshots stored within the same second are ordered by when the server catalogued them, and never by the time the host wrote into the snapshot.
- Two snapshots with the same time are ordered by id.
- The two newest good snapshots of each pool of each source instance on a host are always kept, whatever the rules say, so a bad rule or a run of failed backups cannot empty a host. A good snapshot is one that is neither suspicious nor incomplete. Incomplete snapshots take part in the rules like any other, but do not count towards these two.
- Suspicious snapshots (flagged by the anomaly detector or by an administrator) take no slot in any rule and are never forgotten. The good snapshots around them are counted as if they were not there.
- An instance that stops getting snapshots (a deleted guest, a reused VMID, a recreated database) keeps its two newest good snapshots for good; the other rules apply to it as always. A guest that moves to another node is a new instance on that node, with its own retention, and the old one keeps its two snapshots. Remove them by hand with `snapshots:delete` when you no longer need them. A policy that stops selecting an instance raises one alert, [Source no longer selected](/docs/guides/alerts/#source-no-longer-selected).
- The anomaly detector compares a snapshot with the history of its own source instance only.
- If a policy is deleted, its snapshots stay. A new policy with the same name in the same repository takes them into its pool.
- Forgetting removes only the snapshot manifest. The data it referenced stays in the repository until garbage collection frees the space.

### Retention preview

Before you save a tighter rule, the policy page shows what it would forget. When the policy has more than one source instance on its hosts, the page has two tabs, **Policy** and **Retention preview**. The Policy tab keeps a summary (for example "Would forget 46 of 412 snapshots in 40 sources on 2 hosts") and an **Open preview** button. The preview tab lists the sources that have something to forget with the columns Source, Host, Forget and Keep, a filter by host and 25 sources per page; a row opens the list of snapshots to forget, and the floor of two and the snapshots that are suspicious are noted above the table. A policy with one instance shows the list inside the form, as before. The API answers with the same data (see [the API reference](/docs/reference/api/#retention-preview)), and `lode server policies retention` prints the preview per host.

## limits

| Field | Meaning |
| --- | --- |
| `uploadRate` | Caps the upload speed to storage, for example `20MiB/s` or `500KiB/s`. |
| `nice` | CPU priority of the backup, `0` to `19`. Higher means lower priority. |
| `ioniceClass` | `best-effort` or `idle`. Leave it out for the system default. |
| `ioniceLevel` | `0` (highest) to `7`. Only valid with `ioniceClass: best-effort`. |
| `maxRuntime` | Time limit of one backup, from `1h` to `7d`. The default is `12h`. |

A backup that does not finish within `maxRuntime` is stopped and does not create a snapshot. The server marks a backup that is still active an hour after its limit as failed with the error `time_limit`. The limit is also what lets garbage collection prove that no running backup still references data it is about to delete, so a lower value shortens the pause before deletion.

`nice` and the I/O priority apply to the backup on the host and are inherited by hooks. The I/O priority is best effort: the kernel honours it only with an I/O scheduler that supports priorities, such as BFQ (or CFQ on old kernels). With `none` or `mq-deadline`, common on NVMe disks, it has little or no effect. `idle` can make backups much slower on a busy disk.

## alerts

| Field | Meaning |
| --- | --- |
| `maxAge` | How old the last successful backup of this policy may get on a host before the alert **No recent backup** fires and the host shows as overdue. `1h` to `365d`. |

Lodestore always watches for a policy that goes silent, whether or not it reports an error. Without `maxAge` the limit comes from the schedule: twice the longest gap between the next scheduled runs, plus the schedule's `jitter`. For a daily policy with the default `15m` jitter that is about 48 hours and 15 minutes, so one missed night is tolerated and two are not. Set `maxAge` when that is too loose, for example `maxAge: 36h` for a daily policy you cannot miss, or too strict, for example `maxAge: 10d` for a weekly policy that is often skipped on purpose.

A policy with no schedule and no `maxAge` has no limit: it runs only by hand, so being old is not a fault. The limit is counted for each host the policy applies to. The age starts at the last successful backup, or, when the host has none yet, at the later of the time the host enrolled and the time the policy was created. See [Alerts and notifications](/docs/guides/alerts/#no-recent-backup-the-dead-man-rule).

## What an API token may change

A web session may change everything on this page. An API token, for example in a CI job that runs `lode apply`, needs `policies:write` to change a policy and more when the change reaches further than the policy itself:

| Change | Extra scope |
| --- | --- |
| Add, change or remove `retention`, or `includeStdin` | `snapshots:delete`, because retention makes the server delete snapshots |
| Run a policy with retention more often | `snapshots:delete`. The server compares the shortest gap between two runs of the schedule over the next 366 days, in the time zone of the policy, before and after the change. That also catches `0 3 * 12 *`, which runs daily but only in December, in place of a weekly schedule, and a schedule with no two runs in that year, such as `* * 29 2 *`, in place of a daily one. A schedule that runs less often, or at another time of day, needs only `policies:write` |
| Add, change or remove `hooks`, or widen a policy that has hooks: change its `repository`, or its selector in any way other than a shorter `hosts` list or more `matchLabels` added (an empty selector, a changed or removed label and a host id that is not enrolled yet all count as wider), or change host labels so that a host joins it | `hooks:write`, because hooks run commands as root on the hosts. It does not matter which hosts are enrolled at that moment. Deleting a whole policy without retention needs only `policies:write` |
| Change `paths`, `exclude`, `oneFileSystem`, `excludeCaches`, `source`, `schedule.timezone` or `repository` of a policy with retention (before or after the edit) | `snapshots:delete`, because narrower paths, another source, another time zone or another repository make the next backups hold less or sit in another pool, or move the day and week boundaries, and retention then forgets real snapshots. A missing time zone is UTC, and the name of the zone is compared as written. Paths compare as a set, so reordering them needs only `policies:write`; excludes compare as an ordered list, because a later `!` pattern can bring back what an earlier one excluded, so reordering or repeating one counts as a change; `/etc` and `/etc/` count as different paths. A policy without retention needs only `policies:write` |
| Delete a policy with retention, also with `lode apply --prune` | `snapshots:delete`, because a new policy with the same name and repository takes over its snapshots |

The server answers 403 and names the scope; for hooks it also lists the policies. `lode apply` refuses the whole run in these cases, and `--dry-run` shows the refusal beforehand.

A token can start the same policy on the same host at most 6 times per hour. The seventh request gets a 429 with `Retry-After`. Sessions are not limited, and scheduled runs do not count.
