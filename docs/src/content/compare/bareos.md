Bareos is a backup system for networks of computers, a fork of Bacula 5.2 started in 2010. Lodestore is a newer system built around S3-compatible object storage.

## Why teams pick Lodestore

- **Few moving parts.** The Lodestore server is one binary with a SQLite catalog by default, or PostgreSQL for production, and the agent on each host writes straight to the bucket. In Bareos, data goes from the File Daemon through a Storage Daemon, which holds the object-store credentials.
- **Restore depends only on the bucket.** A password or recovery key and the bucket are enough for `lode` to restore, even if the server is gone.
- **No Storage Daemon on the data path, and deletion only by the server.** The agent writes straight to the storage with rights that have no delete: generated by the server for S3 services that can restrict a key, for Google Cloud Storage and for Backblaze B2; on Azure Blob Storage a short-lived access token that the server signs for each agent. Deletion is done by the server alone, with a two-phase cleanup that works with S3 Object Lock. With Object Lock in COMPLIANCE mode, not even the server can remove locked data before its retention period ends. See the [threat model](/docs/security/threat-model/#agent-credentials). So far MinIO and SFTP have been tried on the real service; the other backends are tested on emulators, and [Storage backends](/docs/reference/storage/#verification-status) says which.
- **Fleet view and alerts out of the box.** A web interface, schedules and retention as policies, alerts to Telegram, Slack, email and webhooks, and a fleet-wide search for a file across all hosts.
- **A short path to the first backup.** One server image and a one-line install per host; see the [Quickstart](/docs/quickstart/).

## At a glance

| | Bareos | Lodestore 0.2 |
|---|--------|---------------|
| Components | Director, a File Daemon on each client, a Storage Daemon and a PostgreSQL catalog | One server binary and an agent on each host |
| Storage | Tape, File, Fifo, Droplet (object stores, most notably S3), Dplcompat, Dedupable | S3-compatible object storage, local or network folder; Azure Blob Storage, Google Cloud Storage and SFTP from the next release, see [Storage backends](/docs/reference/storage/) |
| Where object-store credentials live | In a profile on the Storage Daemon, not on the File Daemons on the clients | On S3-compatible storage the agent holds a write-only key; the server holds the key that can delete |
| Protection from a compromised host | Tape and WORM media for ransomware-resilient setups | Agent rights without delete, generated by the server for S3 services that can restrict a key, Google Cloud Storage and Backblaze B2, and a short-lived access token that the server signs for each Azure Blob Storage agent; deletion is server-only; so far MinIO and SFTP have been tried on the real service ([Storage backends](/docs/reference/storage/#verification-status)); the server checks every new backup an agent makes, so index metadata forged by a compromised host cannot delete the backups of other hosts or pass off an unrestorable backup as a success; the latest snapshot is picked from signed records of which host and job made each snapshot, not from the time a host writes into it; the agent writes restored files only into folders its own configuration allows, even when the server asks for more |
| Platforms | Linux, Windows, macOS, FreeBSD | Linux, x86_64 and arm64 |
| Sources | Files, plus File Daemon plugins for PostgreSQL, MariaDB, Percona XtraBackup, Microsoft SQL Server, Proxmox VE and VMware | Files and directories; databases through a dump in a pre-backup hook |
| Backup levels | Full, differential, incremental and Always Incremental | Deduplicated snapshots |
