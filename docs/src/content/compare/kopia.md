Kopia is a snapshot backup tool with a command-line interface and an official graphical interface, designed to back up individual machines, with an optional server mode. Lodestore is a self-hosted server with an agent on each host, built for a fleet of Linux hosts.

## Why teams pick Lodestore

- **Built around a fleet.** Schedules and retention are set on one server for every host. A web interface shows which hosts backed up and which did not, alerts cover failed or missing backups, offline hosts and failed checks, and you can find a file across the snapshots of every host.
- **Deletion only by the server.** The agent writes with rights that have no delete: generated by the server for S3 services that can restrict a key, for Google Cloud Storage and for Backblaze B2; on Azure Blob Storage a short-lived access token that the server signs for each agent. Deletion is done by the server alone, with a two-phase cleanup that works with S3 Object Lock, so no host needs a client with full access to the repository for maintenance. With Object Lock in COMPLIANCE mode, not even the server can remove locked data before its retention period ends. See the [threat model](/docs/security/threat-model/#agent-credentials). The setup wizard shows, for each provider, how to create that key (or what to do where a provider cannot limit one) and checks what it can do before the repository is created. So far MinIO and SFTP have been tried on the real service; the other backends are tested on emulators, and [Storage backends](/docs/reference/storage/#verification-status) says which.
- **A short path to the first backup.** One server image and a one-line install per host; see the [Quickstart](/docs/quickstart/).

## At a glance

| | Kopia | Lodestore 0.2 |
|---|-------|---------------|
| What it is | Snapshot backup tool with a command-line interface and a graphical interface, designed to back up individual machines; no server is needed to run it | Self-hosted server with agents, Apache-2.0 |
| Central management | Optional server mode with an API for centrally managing backups of multiple machines; a Repository Server can proxy access to the storage | One server for all hosts: web interface, schedules and retention, alerts, search across the snapshots of every host |
| Protection from a compromised host | Object Lock on S3-API storage, enabled when the repository is created from the command line; a key without delete permission turns deletes into hidden markers; a Repository Server can give clients access that allows reading and writing but not deleting | Agent rights without delete, generated by the server for S3 services that can restrict a key, Google Cloud Storage and Backblaze B2, and a short-lived access token that the server signs for each Azure Blob Storage agent; deletion is server-only; so far MinIO and SFTP have been tried on the real service ([Storage backends](/docs/reference/storage/#verification-status)); the server checks every new backup an agent makes, so index metadata forged by a compromised host cannot delete the backups of other hosts or pass off an unrestorable backup as a success; the latest snapshot is picked from signed records of which host and job made each snapshot, not from the time a host writes into it; the agent writes restored files only into folders its own configuration allows, even when the server asks for more |
| Platforms | Linux (x64, arm64, arm), macOS and Windows; FreeBSD and OpenBSD builds are marked experimental | Linux, x86_64 and arm64 |
| License | Apache-2.0 | Apache-2.0 |

### Storage

| Storage | Kopia | Lodestore 0.2 |
|---------|-------|---------------|
| Amazon S3 and S3-compatible storage | Yes | Yes |
| Local or network folder | Yes | Yes, the agent can delete in it |
| SFTP, Azure Blob Storage, Google Cloud Storage | Yes | Yes from the next release; each backend reports what a host can do to its backups, see [Storage backends](/docs/reference/storage/) |
| WebDAV, Google Drive, Rclone | Yes; Google Drive and Rclone are marked experimental | Not in 0.2 |
