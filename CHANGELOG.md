# Changelog

All notable changes to Lodestore are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- `spec.source` in a backup policy, with `apiVersion: lodestore.io/v1alpha2`: `files`, `proxmox-vm`, `proxmox-ct`, `postgres` and `mysql` blocks. A policy of files is exported without it and as `v1alpha1`, byte for byte as before. The server stores a policy of every type; a job of a type the agent cannot run yet is refused before it starts with `source_agent_outdated`. See [Backup policies](https://lodestore.dev/docs/guides/policies/).
- The agent finds the sources of its host and reports them to the server: the guests of a Proxmox node (VM and container, with id, name, tags, pool and a stable UUID), the PostgreSQL clusters (system identifier, port, version and databases) and the MySQL servers (server UUID, port, version and schemas) that run on it. It reads `/etc/pve` and talks to a database only through its local socket, without a password, and repeats the scan every five minutes. The new agent capability `source:files` is the first of the `source:<type>` capabilities that decide which jobs a host may get.
- A Sources tab on the host page lists the guests and databases found on the host, with the policies that select each one, a "Not protected" filter, "Agent too old" for a type the agent cannot back up yet, a note when the same guest or database is also found on another host, and the point where a list was cut short. The Snapshots table shows the source label under the date on a phone.
- A "What to back up" field in the policy form offers a type only when an agent has found it on the selected hosts, and lets you pick guests (by id, pool or tag) and databases from what the agents found, or take all of them. The YAML tab shows the same `spec.source` that `lode apply` takes. The Matching hosts list shows how many instances the policy selects on each host and marks the hosts where its jobs will fail. `POST /api/v1/policies/validate` answers with `availability`, and `POST /api/v1/policies/source-options` and `GET /api/v1/hosts/{id}/sources` serve the form and the tab.
- `lode ls`, `lode dump` and `lode restore` take `--host HOST` with `latest@<source key>`, to choose among the snapshots one host made.
- The jobs `source_agent_outdated` (the agent has no `source:<type>` capability for the policy) and `source_not_found` (the host has no source the policy selects) fail before any hook runs, with a message that says what to do, and raise the usual "Backup failed" alert.
- `lode policy validate FILE...` checks policy files offline with the rules of the server and exits 3 when a file has problems.
- Snapshots carry a source type and a label. `GET /api/v1/hosts/{id}/snapshots` and `GET /api/v1/restore/snapshots` accept `source_type` (and the latter `source`, a source instance on the host) and report `source_type`, `source_label` and `source_counts`; `lode server snapshots list` takes `--source-type` and `--source`, `lode snapshots` takes `--source-type`. The host page filters its Snapshots tab by source type when a host has more than one.
- `latest@<source key>` in `lode restore`, `lode ls` and `lode dump` selects the newest signed snapshot of one source instance. When snapshots of the key come from more than one host, `lode` refuses and asks for `--host` (see below).
- Four restore scopes, `restore:guest`, `restore:guest-in-place`, `restore:db` and `restore:db-in-place`, independent of `restore:host`, `restore:in-place` and `restore:download`. They are reserved: no endpoint uses them yet. `RestoreSpec` carries a `target` for a guest or a database.
- The alert `source_instance_gone` (`LodestoreSourceInstanceGone` in the Prometheus rules): one warning for 24 hours when a policy stops expecting a source it backed up.
- The retention preview lists every source instance with something to forget, with a Retention preview tab on the policy page when a host has more than one.
- [ADR 0007](https://lodestore.dev/docs/adr/0007-source-model/): the source model, canonical keys of source instances, retention and `latest` per instance, restore scopes and the layout of disk images.
- `lode backup --image SOURCE [--name NAME]` backs up a raw image file or a block device, read whole, as a snapshot of the new source type `image` (key `image/NAME`): fixed chunks of 4 MiB, zero chunks stored as holes, segments of 256 GiB, up to 16 TiB. `--json` reports `image.key`, `image.size` and `image.read_mode`. A source that changed while it was read fails the backup without a snapshot, and a mounted device gets a warning: the image is crash-consistent at best. See [Back up a disk image](https://lodestore.dev/docs/recipes/disk-image-backup/).
- `lode restore` of an image snapshot writes one sparse `NAME.img`; `SNAPSHOT:/disks/NAME` restores the segments as files. `lode restore --to-device DEVICE` writes an image to a block device on Linux, with `--accept-unverified` for a snapshot that nothing signed in a repository with signatures. It refuses a device that is smaller than the image, mounted, in swap or held by another device; a process that holds the device without an exclusive lock is not seen. `latest@image/NAME` refuses when the signed snapshots of the name were made under more than one host name and takes `--host` with the name.
- Restore of an image through the server: a whole-image restore through the API writes `NAME.img` into a restore folder (`restore:host` with `skip_existing` or `stop_if_not_empty`; `restore:in-place` with `overwrite_changed`, as defence in depth). `in_place` is refused for an image, and an image with too many holes for a plan of 4 MiB is refused with 422.
- `image` in the `source_type` filter of the API, in `lode snapshots --source-type` and in `lode server snapshots list`; the web interface labels it "Disk images".
- `lode backup --image nbd+unix:///EXPORT?socket=PATH --bitmap lode-...-g<N>` makes an incremental backup of a disk image by a dirty bitmap of an NBD export (qemu-nbd was tested at 10.1 and 10.2): it reads only the dirty ranges, reuses the chunks of the previous snapshot and merges a chunk that is partly dirty with the bytes of that snapshot. Any doubt about the pair of bitmap and previous snapshot gives a full read with the reason in the output (`image.full_reason`). The bitmaps rotate by generation (`g<N>`, `g<N+1>`), and `lode` says which one to create for the next backup (`image.next_bitmap`, `image.bitmap_to_create`). It has its own NBD client, which accepts only `nbd+unix://`. A bitmap manager that resets the bitmap when a client connects is not supported. See [Back up a disk image](https://lodestore.dev/docs/recipes/disk-image-backup/#incremental-backups-from-a-dirty-bitmap).
- Azure Blob Storage, Google Cloud Storage and SFTP repositories, and a Backblaze B2 preset for S3 (`provider = b2`). Agents write to every new backend only by creating objects: Azure with `If-None-Match: *` in one request, Google with `ifGenerationMatch=0`, SFTP by an exclusive create in `tmp/` followed by a hard link (`publish = hardlink`, the default) or, for servers without a hard link request, an exclusive create under the final name with a comparison of size and bytes (`publish = direct`). A write that was cut off leaves a short or holed file that is never counted as the pack, which is written again under a new name. The SFTP host key is pinned in the settings of the repository (`host_key`), typed in or taken from the key the server shows (see below); a changed key stops the connection. Only ed25519 and ECDSA keys are accepted. The server creates these repositories through the API; the web wizard still offers S3 and a local folder. See [Storage backends and guarantee levels](https://lodestore.dev/docs/reference/storage/).
- `lode -r azblob://CONTAINER[/ROOT]`, `gcs://BUCKET[/ROOT]` and `sftp://USER@HOST[:PORT][/PATH]`, with secrets from `LODE_AZBLOB_*`, `LODE_GCS_*` and `LODE_SFTP_*` environment variables and never from the URL. Restoring without the server works on all three; see [Restore without the server](https://lodestore.dev/docs/recipes/restore-without-server/).
- The storage check reports a measured guarantee level: `create_only_enforced`, `overwrite_keeps_old_version`, `host_can_overwrite_or_delete` or `unchecked`, with the reasons as `guarantee_notes`. It tries to write, overwrite and delete objects in each of `packs/`, `index/` and `snapshots/` with the credentials the agents get, reads the earlier versions of a versioned bucket, and reads the lifecycle rules of an S3 bucket; a rule that deletes objects or their versions, or rules that cannot be read, lower a level that rests on kept versions. Repository summaries and details carry `guarantee_level`, `guarantee_accepted` and `guarantee_checked_at`. The check does not measure rights over the bucket configuration, and a policy that depends on where a request comes from can differ between the server's network and a host's.
- A repository whose measured level is `host_can_overwrite_or_delete` or `unchecked` is created or connected only with consent: `POST /api/v1/repositories/wizard` and `.../connect` answer `409` with `weaker_guarantee` unless the request has `accept_weaker_guarantee: true`, the web wizard asks for a checkbox, and `lode repo init` stops, creating nothing, unless it gets `--accept-weaker-guarantee`. This changes `lode repo init` on a local folder, which always measures `host_can_overwrite_or_delete`, and on S3: a bucket without versioning, or a key that can overwrite or delete, now needs the flag, and a versioned bucket with a create-only key reports `overwrite_keeps_old_version` with a note that `lode` does not read the lifecycle rules.
- `POST /api/v1/repositories/{id}/guarantee/accept` makes the measured level the accepted one. The request names the level the person was shown in `expected_level`, and the server answers `409` without a change when a check has measured another level since. A manual check keeps the measured level and raises the accepted level only when the measured one is higher; the repository page shows when the measured level is below the accepted one and offers to accept the new level. Replacing or verifying the agent key runs the full check.
- Cleanup removes the files of cut-off SFTP uploads from `tmp/` when they are older than the pause and than 24 hours, and on the B2 preset leaves objects that are only hidden, because it cannot tell a hide marker of the server from another one. On B2 a cycle fails, both before it plans a delete and before it deletes, when a snapshot the server did not forget has a hide marker or an older version in its history, so a host that hides a snapshot, even one it puts back and hides again, cannot make cleanup delete its data. See [Cleanup](https://lodestore.dev/docs/guides/gc/#sftp-and-backblaze-b2).
- The server checks the storage guarantee of every repository by itself once a day, with the same probe as **Check storage again**; the first pass runs ten minutes after the server starts. The new alert `guarantee_downgraded` (`LodestoreGuaranteeDowngraded`, warning) is raised for one of five causes: `lower` (the measured level is below the accepted one), `weak_unaccepted` (the accepted level is `unchecked` and the measured one is `host_can_overwrite_or_delete`), `inconclusive` (three probes in a row measured nothing), `recheck_failing` (three checks in a row failed before they recorded a result) and `recheck_not_running` (the daily check has not run for more than two days). One failed check or one inconclusive probe changes nothing. A probe that started before the credentials, the host key or the agent options were replaced, or earlier than a stored result, is discarded, and `POST /api/v1/repositories/{id}/check` answers `409` for it. A changed SFTP host key raises its own critical alert, `host_key_changed` (`LodestoreHostKeyChanged`), with the pinned and the offered fingerprint. Both types are in the notification channels, the metrics and the Prometheus rules, and the web interface shows them on the Overview. See [Alerts and notifications](https://lodestore.dev/docs/guides/alerts/) and [Storage backends and guarantee levels](https://lodestore.dev/docs/reference/storage/#checking-again).
- The SFTP host key can be learned from the server. `POST /api/v1/repositories/check` with an SFTP draft that has no `host_key` makes the SSH handshake only and returns the key and its fingerprint in `host_key`; you compare the fingerprint and send the key back. `POST /api/v1/repositories/{id}/host-key/check` shows the key a server presents now, and `PUT /api/v1/repositories/{id}/host-key` pins a new one after a full check with it (the password entered in the last 15 minutes is needed). The server sends the pinned key to its agents at the start of every session (agent capability `host_key_v1`, message `UpdateHostKey`); an agent of an earlier version cannot take it and is counted in `needs_update`. A server with only an RSA host key is a permanent error.
- `agent_options` in the draft of an Azure Blob Storage, Google Cloud Storage or SFTP repository: the secrets the agents use instead of the server's (`sas_token`; `credential`; `user` and `key`). The level is measured with them, so `shared_credentials` is recorded only for a repository without them. The Azure `account_key` is not accepted as an agent option, and the values are never returned.
- `PUT /api/v1/repositories/{id}/agent-options` replaces the agents' credentials of a repository created with `agent_options`, after a full check with them, with the password entered in the last 15 minutes. A repository created on shared credentials answers `409`: its hosts already hold the server's credentials, so it moves to separate agent credentials only as a new repository. Online agents get the new location at once (capability `location_v1`, message `UpdateLocation`, which changes only the credentials), the others at their next session, and an agent of an earlier version is counted in `needs_update`. When the last check shows that the agents' credentials cannot write, the alert `guarantee_downgraded` says so.
- `GET /api/v1/agent-policy` takes `preset`, `bucket`, `prefix` and `user` and answers with `rights` for Amazon S3, MinIO, Wasabi, Backblaze B2, Cloudflare R2, Hetzner Object Storage, Hetzner Storage Box, Azure Blob Storage, Google Cloud Storage and SFTP: a policy or commands that create agent credentials without delete, or an instruction where the storage cannot restrict a key (R2, Storage Box). A value outside a short alphabet answers `422`; the server runs nothing and calls no cloud. `GET /api/v1/storage-presets` lists the presets with endpoint template, region, path style, mechanism and whether the text has been tried on the real service (only `minio` and `sftp` have).
- A new Azure Blob Storage repository created through the wizard with the account key gives its agents a container SAS that the server signs itself (read, create and list; 24 hours from a start 15 minutes before it was signed), instead of the account key. The server sends it at enrolment and at every session start, signs a new one every hour for online hosts, and records the expiry of each one it sends. A revoked host gets no new SAS, and its access ends when the last SAS issued to it expires. Agents announce the new capability `sas_refresh_v1` and take a replaced SAS from their location file every five minutes, into the job that is running. Agents of older versions need an update (`hosts_need_agent_update`).
- The check reads the lifecycle rules of a Google Cloud Storage bucket when the server's account may read them (`storage.buckets.get`): a rule that deletes under the repository prefix gives `lifecycle_deletes`, and `lifecycle_unverified` stays only when the rules could not be read. Azure lifecycle is still not read.
- `GET /api/v1/repositories/{id}/storage-access` tells whether revoked hosts still reach the storage of a repository (`after_revoke`, `status`, `rotate_via`, counts of revoked hosts and `access_ends_by`), and says to disable the old key at the provider after a replacement in Lodestore (`rotated_disable_old_key_at_provider`).
- A page for each storage backend in the documentation (Amazon S3, MinIO, Wasabi, Backblaze B2, Cloudflare R2, Hetzner, Azure Blob Storage, Google Cloud Storage, SFTP, local folder) with what a host can do there and what has been tried on the real service, and a matrix of the same in the threat model.

- The setup wizard has five steps and a tile for each storage: Amazon S3, MinIO, Wasabi, Backblaze B2, Cloudflare R2, Hetzner Object Storage, Hetzner Storage Box, Azure Blob Storage, Google Cloud Storage, SFTP and a local path. The new **Agent rights** step shows the commands or the policy that create an agent key without delete rights for the chosen provider, takes the key, checks it and shows what a host can do, with a Bucket group (Object Lock, Versioning, Lifecycle rules) for S3, Google Cloud Storage and Azure. **Skip, use the server key** needs a consent to the weaker level and is not offered for Cloudflare R2 and for Azure with the account key.
- The wizard gets the SFTP host key from the address alone, and shows its fingerprint before it asks for the server's user and private key; the key is sent only after you choose **It matches**. `POST /api/v1/repositories/check` with an SFTP draft that has no `host_key` now needs only `endpoint`. **Check host key again** on the repository page shows the key the server presents now and offers to keep or trust it.
- A **Guarantee** column in the repository list with the measured level and the time of the last check (a warning after 48 hours, when never checked, and below the accepted level), and a card **What a host can do to backups** on the repository page with **Check now**.
- **Limit agent rights** on the repository page: the panel shows the commands of the wizard, asks for your password, checks the new key and switches the agents to it (`PUT …/agent-key` for S3 and Backblaze B2, `PUT …/agent-options` for Google Cloud Storage, SFTP and an Azure SAS). The dialog that revokes a host says whether the host can still write and offers **Replace agent key** where that closes its access.
- A page for each storage in the documentation has a section "In the web interface" that says which tile to choose, what to enter and what the Agent rights step shows.

### Changed

- The wizard step Access is split into **Connection** and **Agent rights**, and the dialog and the policy panel for replacing the agent key are replaced by the **Limit agent rights** panel.
- `PUT /api/v1/repositories/{id}/agent-key` needs a session that entered its password in the last 15 minutes and answers `403` `step_up_required` otherwise.
- The first contact with an SFTP server needs only its address; it no longer asks for a user or a key.
- The storage check creates the folders it writes into (`packs`, `index`, `snapshots`, on SFTP also `tmp`) with the server's own key on SFTP and in a local folder, so it works on an empty directory; the agent's key needs no right to create a directory. A failed check on SFTP or a local folder shows the storage's own message; S3, Azure and Google Cloud Storage keep a general message with the detail in the server log.
- Retention, the floor of two newest good snapshots, `latest` and the missing-backup alert work per source instance (a guest, a database, or the files of a host) instead of per host. A policy of files has one instance per host and behaves as before, which tests check against the previous code. A guest that migrates to another node, or a database that fails over to another host, is a new instance on the new host.
- `latest` in `lode` and the server chooses among `files` snapshots; a snapshot of another source is chosen only by `latest@<source key>`, and a WAL batch never. A repository without signatures skips snapshots whose manifest claims a source other than `files`.
- The anomaly baseline of a snapshot is the history of its own source instance.
- A files restore of a snapshot of a guest or a database is refused with 422; a disk image restored whole is the one exception.
- `lode backup --name` is no longer limited to `--stdin`: it also names a disk image with `--image`. `lode restore --target` is not needed with `--to-device`.
- `lode restore --verify` and `lode check --level restore` verify the files of a disk image by fixed slices of 4 MiB, besides the content-defined chunks they used before.
- `lode ls`, `lode dump` and `lode restore` with `latest@<source key>` exit with code 1 when the signed snapshots of the key come from more than one host, as with a cloned guest or a database and its standby, and name the hosts with the id and age of the newest snapshot of each; `--host` chooses one. A value of `--host` in the form of a UUID is a host id and is never looked up as a name. A key held by one host behaves as before.
- A job for a source other than `files` is refused when the agent has no `source:<type>` capability, and when the agent has reported a complete, recent list of sources, collected after the job was queued, that holds none the policy selects. An agent that is offline or has no recent list is sent the job and decides itself.
- The missing-backup alert of a policy for guests or databases waits for the instances the agents found, plus any instance whose latest job failed. When nothing is known about a host it waits for one placeholder instance, so a failing job still raises an alert.
- `source_instance_gone` opens an hour after an instance stops being expected and not before, and does not open again within 24 hours of the last event, so a guest that disappears from one scan does not raise an alert.

- The comparison pages show the date the facts about each competitor were checked and a list of sources with their versions.
- `lode backup --stdin --policy X` through the agent, where `X` does not select the host or does not exist, now ends on the server as a `failed` job with `snapshot_policy_mismatch` instead of a snapshot under policy `X`.
- With `includeStdin: true`, the stdin snapshots of a policy are counted in a retention pool of their own, not in the manual pool, and each stdin stream name has its own pool, so a weekly `etcd.snap` is not rotated by an hourly `pg.dump`.

- The repository `experimental` flag and its badge are gone from the API and the web interface: Azure Blob Storage, Google Cloud Storage and SFTP are built into the server, the agent and `lode` without a feature switch, and the repository page shows the guarantee level instead. WebDAV is no longer accepted as a backend.
- After the update an existing repository shows Unchecked (`unchecked`) as its measured level until its first check, and keeps the level it had before as its accepted level (a verified agent key as `create_only_enforced`, a key that can delete or overwrite, or a folder, as `host_can_overwrite_or_delete`). A check that settles nothing changes neither level.
- A location on Backblaze B2 (an endpoint at `backblazeb2.com`) needs `provider = b2` and is refused with `422` without it: B2 does not apply `If-None-Match`, and a delete there hides the file instead of removing it.
- The quickstart enables versioning on the MinIO bucket before the wizard, so that the first repository measures `overwrite_keeps_old_version` and needs no consent. A bucket without versioning asks for the consent.
- The checks of an Azure Blob Storage repository always carry `lifecycle_unverified`, because the server does not read its lifecycle rules, and those of a Google Cloud Storage repository carry it when the server cannot read them; `overwrite_keeps_old_version` is lowered there as it is for an S3 bucket whose rules cannot be read. The error texts of the checks hide the signature of an Azure SAS.
- Replacing an SFTP host key or the agents' credentials needs the password entered in the last 15 minutes. Replacing the S3 agent key does not.
- **Updating.** The first daily check after the update can raise `guarantee_downgraded` for repositories that existed before: when the accepted level, taken over from the state of the agent key, is `unchecked` and the check measures `host_can_overwrite_or_delete`, the cause is `weak_unaccepted`; accept the level on the repository page or fix the storage. `recheck_failing` appears only after three failed checks in a row, as for a new repository. Each check writes and removes a few small objects named `probe-<random>`; under Object Lock, or where the server may not delete versions, they stay (a few per repository a day). Agents need the new version to take a new SFTP host key and new agent credentials from the server, or they stay in `needs_update`.
- `PUT /api/v1/repositories/{id}/agent-options` answers `409` on a repository whose agents get a SAS from the server. `POST /api/v1/repositories/wizard/{id}/commit` answers `409` with the code `storage_changed` when another repository took the container after the check.
- A repeat write that the storage refuses (`409` `ObjectLockedByBucketPolicy` on a Cloudflare R2 bucket lock, `403` on Google Cloud Storage or Azure) counts as already written only when the stored object has the same bytes; the same length and other bytes is an error.
- The level of an Azure Blob Storage repository with a SAS of its own, or with a SAS from the server, drops to `host_can_overwrite_or_delete` with `shared_credentials` when the agents of another repository of the same account hold the account key, an account SAS or a SAS wider than read, create and list, or another repository uses the same container. The account is told by its name; a name that cannot be read counts as the same account. The drop happens when such a repository is registered or widened, at creation, and in the daily check, so it can show on the first recheck after the update.

### Fixed

- Retention could forget a newer snapshot and keep an older one when several backups were stored within the same second on S3, which keeps object times in whole seconds. Such snapshots are now ordered by when the server catalogued them.
- A snapshot that the storage stored ahead of the server clock is skipped when the server picks the latest snapshot of a source, as `lode` already did; the two no longer disagree.
- A job whose snapshot claims a malformed source fails at once, with `verification_failed` or `snapshot_policy_mismatch`, instead of being retried by the verification forever.
- An instance that is no longer expected does not make a host healthy, and its old success no longer sets the last success of the fleet overview.
- A scan that fails is not read as "nothing found": an unknown list never silences the missing-backup alert and never raises `source_instance_gone`. A guest that drops out of a list that was cut short keeps raising "No recent backup".
- The sources tab ignores a snapshot stored ahead of the server clock when it shows the last snapshot of a source.
- The server no longer refuses a job with `source_not_found` for a guest created while the job waited in the queue: only a list collected after the job was queued can refuse it there. The agent still checks the job against its own latest discovery.
- A list of sources that is over the size limit is not stored and counts as unknown; tags past the limit and over-long cluster or node names mark the list as cut short.
- The agent runs `mysql` with `--local-infile=0` and treats a locked account like a refused login, so it does not retry at every scan. A PostgreSQL database whose name is longer than 64 bytes or is not valid UTF-8 is no longer reported under a cut name, and the saved ids of containers past the report limit are kept.

### Security

- A new repository location takes only the options listed for its backend, spelled exactly; any other option name answers `422` ("azblob location does not support the option `sas_key`; ..."). Before, a secret under another spelling or an alias of the storage library (`sas_key`, `azure_storage_account_key`, `Token`) was stored unsealed, returned by `GET /api/v1/repositories/{id}` and sent to agents. Repositories already stored open as before. `lode` no longer repeats an `s3:` URL with a query, a fragment or `user@` in its error. See [Storage backends and guarantee levels](https://lodestore.dev/docs/reference/storage/#backends).
- On Azure Blob Storage, Google Cloud Storage and SFTP, hosts of a repository without `agent_options` write with the server's own credentials, which can delete and overwrite, so a compromised host can destroy the backups in such a repository. The level there is at most `host_can_overwrite_or_delete`, with the reason `shared_credentials` ("Hosts use the server's own credentials for this storage, so they can do anything the server can."), and the repository is created only with explicit consent. This departs from the rule that an agent cannot delete, which holds on S3-compatible storage; a repository with `agent_options` (see below) is measured with its agents' own credentials. An SFTP repository is never reported above `host_can_overwrite_or_delete`, because an agent can keep a published file open and write to it. Google Cloud Storage and Azure Blob Storage agents use only the credentials the server sent, never those of their host. The protection that a service enforces on Azure Blob Storage, Google Cloud Storage, Backblaze B2 and hosted SFTP has not been verified on the real services; see [Storage backends and guarantee levels](https://lodestore.dev/docs/reference/storage/#verification-status).
- The server compares the source a snapshot claims in its manifest with the source of its job when it checks the job. A mismatch, an invalid claim or a claim in a job of another type fails the check with `verification_failed`: no signature and no place in retention. The signed record names the source the server took from the job, and a record with an invalid source does not open. A files restore refuses snapshots of guests and databases.
- A token needs `snapshots:delete` in addition to `policies:write` to change `spec.paths`, `spec.exclude`, `spec.oneFileSystem`, `spec.excludeCaches`, `spec.source`, the effective `spec.schedule.timezone` or `spec.repository` of a policy that has retention before or after the edit, and to delete a policy with retention (`DELETE /api/v1/policies/{name}`, `lode server policies delete`, `lode apply --prune`), dry runs included. Without it the server answers 403 and `lode` exits with code 13; a session needs its password entered in the last 15 minutes. Reordering paths is not a change, reordering or repeating an exclude is. See [API tokens and scopes](https://lodestore.dev/docs/security/threat-model/).
- The server takes the policy and the stdin name of a snapshot from the job that created it, not from the tags of the manifest. A snapshot tagged for another policy, also one that a catalog sync had already found, is refused and the job fails with `snapshot_policy_mismatch`, so a compromised agent cannot put a snapshot into the retention pool of another policy. A stream job is refused a snapshot that is not a stream of its name, so it cannot pull an older backup of its host into the stdin pool. Binding a snapshot the catalog already knows checks the host of the manifest as binding a new one does; a signature of the repository password does not mark a snapshot that the job of another host claimed, and the server's signature at the upgrade from 0.1 is not given to a snapshot whose manifest does not name the host of its job. A CLI job keeps its policy only when the policy selects the host, at creation and at completion, and a CLI job without a stream is not recorded. On upgrade the server takes out of the pools the snapshots whose policy, stdin name or manifest host disagrees with their job, moves the snapshots of CLI jobs to the stdin pool and logs the number of rows it changed. See [Retention and forgetting snapshots](https://lodestore.dev/docs/security/threat-model/#retention-and-forgetting-snapshots).

### Security

- An API token can no longer get root on a host, change hooks or make the server forget scheduled history without the scope for it: restore needs `restore:host` or `restore:in-place`, the agent confines restores to its own restore folders and turns in-place off by default, hooks and the hosts they run on need `hooks:write`, and run-now, a more frequent cron and `includeStdin` cannot push scheduled snapshots out of retention. A token with `restore:host` cannot restore setuid files. A server that is taken over can still write under the restore folders of every host, and anywhere on a host where in-place restore is on or the agent is from 0.1. See [API tokens](https://lodestore.dev/docs/security/threat-model/#api-tokens).
- Index shards from a compromised host no longer influence cleanup or the backups of other hosts. The first time a 0.2 server opens a repository (created, connected or upgraded) it signs the shards that exist at that moment, and trusts them only for `supersedes` and cleanup; the data a new backup depends on is opened and checked by the server once, so a shard planted before the upgrade makes such a backup fail instead of succeed. After upgrading, run `lode check --level packs` to find a forgery made earlier across the whole repository. See [index metadata from a compromised agent](https://lodestore.dev/docs/security/threat-model/#index-metadata-from-a-compromised-agent).
- A host with writer credentials can no longer make `latest`, "restore to the original host", the time of the last backup or the retention window follow a snapshot it planted: planting a snapshot with a date far in the future, or a hundred snapshots, changes none of them. Open a repository with a 0.2 server before you need an emergency restore; until then `lode restore latest` runs in the legacy mode described above, which a host that wrote last can still win, and a new machine reading a folder repository whose signatures were deleted cannot tell. The first strict `lode backup` on a machine costs a read of the data its snapshot depends on. See [snapshot provenance and `latest`](https://lodestore.dev/docs/security/threat-model/#snapshot-provenance-and-latest).
- An old or copied agent certificate no longer opens a session, renews or reads packs: the server accepts only the serial it issued last, and the one before it for two minutes after the first session with the new one, for at most 24 hours; a session that was opened with the previous certificate is closed when that window ends, and the agent reconnects with the current one. The refusal is `certificate_stale`; the agent logs how to enrol the host again and keeps retrying. **Upgrade:** a host whose renewal answer was lost before the update, so that its certificate on disk is older than the one in the database, has no grace window and is refused; enrol it again with `install.sh --force` and a new join token. See [agent credentials](https://lodestore.dev/docs/security/threat-model/#agent-credentials).
- A session that someone else holds can no longer create a token, a join token or a root-owned restore without the password, and a password change can revoke every token. See [signing in and sensitive actions](https://lodestore.dev/docs/security/threat-model/#signing-in-and-sensitive-actions).
- Notifications cannot be pointed at what the server can reach and the administrator cannot: an environment proxy no longer bypasses the address filter, more ranges and embedded IPv4 addresses are refused, and the SMTP connection goes to the checked address. See [notifications and outbound requests](https://lodestore.dev/docs/security/threat-model/#notifications-and-outbound-requests).
- A slow or silent client can no longer hold REST, metrics or gRPC connections open without limit, and a local user or a compromised agent cannot fill the job table with CLI jobs. A database URL, the unlock key and the administrator password given on the command line are no longer printed by the server's debug output. See [limits against a flood](https://lodestore.dev/docs/security/threat-model/#limits-against-a-flood).
- An object planted in the bucket can no longer exhaust the memory of the server, of the agents or of cleanup: the size of an index shard is taken from the listing before the shard is read, a shard above 64 MiB that the server has not signed is not loaded, writers cut shards at 32 MiB, and every other object the format reads (writer markers, key slots, `config`) is read with a bounded read. See [cleanup](https://lodestore.dev/docs/guides/gc/#what-a-cycle-does).
- A snapshot that cleanup cannot open and that belongs to no backup job no longer stops cleanup for good or goes unnoticed: it is quarantined and raises the alert `snapshot_quarantined`, cleanup deletes nothing while it waits, and an administrator with `snapshots:delete` excludes the snapshot so that cleanup goes on. See [quarantined snapshots](https://lodestore.dev/docs/guides/gc/#quarantined-snapshots).
- Smaller hardening of the repository format: a build that does not know a feature in `incompat_features` refuses to read the repository, the server does not open a repository whose `config` differs from the one recorded when it was added, opening with a password spends at most `16777216` of Argon2 work, and the server seals its secrets with associated data that carries the length of the kind and of the id. The first start of 0.2 re-seals the stored secrets; back up the server database before upgrading.
- Signing in cannot be used to exhaust the processor of the server or to lock the administrator out: the hashing of passwords runs through a gate and answers `503` `busy` with `Retry-After` when it is full, without counting the attempt; a password over 4096 bytes is refused before it is hashed; IPv6 clients are limited by their /56 prefix, and a user by 60 failed attempts an hour that spare the addresses it has signed in from. See [signing in and sensitive actions](https://lodestore.dev/docs/security/threat-model/#signing-in-and-sensitive-actions).
- A restore without `restore_owners` no longer sets POSIX ACLs or the `security.*` and `trusted.*` attributes, which can widen access or carry file capabilities; `user.*` attributes are restored as before.

### Fixed

- Blog clips pause and resume on a click, Enter or Space.
- Copying the heading of the home page no longer copies the words of the rotating text.
- Cleanup no longer stops, or rewrites the same pack in every cycle, when an index shard planted by a compromised host names blobs in packs that do not exist. Data was not lost, but one such shard could keep cleanup from freeing space.
- The index chooses the same copy of a blob whatever the order in which its shards are loaded.
- A file whose chunk sizes in the index do not add up made a restore read every chunk it names before charging them to the walk budget, and the structure check read them without any limit, so one planted file naming one chunk many times could make the nightly check read terabytes. Now each distinct chunk of such a file is read once per visit, every reference to a chunk is charged as it is read, and charging and reading stop once the chunks hold more than the file says. The structure check reads such chunks within the walk budget of one restore per run, reads no other chunk once that budget is spent, and reports a file it could not read for every snapshot that reaches it. Every copy of such a chunk that is fetched is charged to that budget, also the copies before the real one that do not open, and a chunk none of whose copies opens is not read again for the next file that names it.
- The structure check read a piece of a directory once for every time the directory listed it, so a directory listing one empty tree thousands of times cost as many reads, none of them charged. Now a piece is read once per directory, and its bytes count every time the directory lists it, as in a restore.
- The structure check sized directories and files by all index shards, while a restore takes the sizes of the shards its snapshot names, so a snapshot naming only a planted shard with larger tree sizes or wrong chunk sizes passed the check and then stopped `lode restore` at a limit. Now a snapshot that names a shard listing a tree larger than the check read it, or a chunk at another size than the one its file added up with, is the finding `unreadable_index`.
- The structure check kept the lists of subdirectories and the hardlink members of a directory whose subtree had taken the path over a limit while it walked below; it now lets go of them.
- The size of the repository the structure check counts no longer overflows on a listing with impossible object sizes.
- `lode backup` held the chain of directories of its parent snapshot without the limits of a path, so a planted parent could make it hold a gigabyte of tree data per level; the parent now stops at 2^24 entries and 2 GiB of tree data held at once, and the backup goes on without it.
- A file whose chunk sizes in the index do not add up charges its chunks and their bytes to the walk budget on every visit, and its chunks are read once per operation for up to 65,536 such files; the structure check counts the same charge.
- The structure check reported a finding in a directory shared by several snapshots for the first snapshot only and called the others ok; every snapshot that reaches the directory now gets it.
- The structure check could read a tree again for every new path to a directory several snapshots share, and a planted tree made that number grow exponentially; it now reads each directory once and judges each snapshot by its own path, in whichever order the snapshots are read.
- The structure check gave a conflict between hardlink members of a shared directory and another directory to every snapshot that shares the directory, and could leave without a finding a snapshot that was checked after another with the same directory; only the snapshot in which the members of a group differ now gets the finding.
- The structure check gave no finding for a snapshot whose tree pack is missing from the bucket; it now reports `unreadable_tree` for each snapshot that needs it and goes on.
- A restore counted only the entries left to hand out of a directory it had already walked into, so a tree of nested directories could pass the limit of 2^24 entries held at once; every open directory now counts at its full length, and `lode backup` refuses a tree a restore could not hold.
- A failed or incomplete read of the attestations is no longer remembered for the life of the reader: the next load reads them again.
- Cleanup stops with a store error when a snapshot body is not the size the listing gave, instead of ignoring it or quarantining it, and reports the real reason when a repack skips a pack longer than its listing.
- An object listed with size zero that has vanished is reported as gone, not read as empty.
- An oversized `config` is the finding `unreadable_config` of `lode check` and the server's checks and no longer aborts the check.
- An exclusion confirmed while a cleanup survey is running is kept; a dry run or a cleanup lifts an exclusion only when its survey started after the confirmation.
- The catalog sync of an unavailable repository answers `503` `repository_unavailable`, and enrolling a host and planning a restore answer `failed_precondition`, instead of an internal error.
- Replacing the agent key of a repository the server cannot open no longer pushes the key to agents; they get it at their next hello after the repository opens again.
- A search that the user cancels ends as `cancelled` even when a snapshot was skipped at the walk limit.
- The Free up space card refreshes the quarantine after a `409` from an exclusion, and the alerts after an exclusion.
- The restore dialog of the web interface keeps Start off and says the restore will be refused for a folder outside the host's restore folders, or when the host allows no new folder; restore errors that retrying cannot fix no longer ask to try again.
- Closing the Create API token dialog without creating a token returns focus to the Create token button.
- `lode server restore --host <name>` with a token that cannot read the host list says to pass the host id when the server does not know the name.
- The demo stand template `deploy/demo/env.example` pins 0.2.0. The proxy steps in `deploy/demo/README.md` get the certificate first, install the site file without editing the working copy and keep it through the maintenance window, and the update steps restart the rootless Docker daemon after a Docker or containerd package upgrade.
- `install.sh` tells a failed download of a signature from a missing one: only an answer of HTTP 404 says the release has no signature, any other failure names the URL, the exit code of curl and the HTTP status, and when minisign refuses a signature its own output is printed.

## [0.1.0] - 2026-11-02

First release.

### Added

- Backup server in a single binary, shipped as a Docker image and a Helm chart. It keeps its catalog in SQLite by default and in PostgreSQL for production.
- Host agent for Linux on x86_64 and arm64. It registers with a one-time join token, receives its own client certificate, keeps an outbound connection to the server and needs no inbound ports.
- Encrypted, deduplicated repository format v1. Agents write straight to S3-compatible object storage (AWS S3, MinIO, Ceph and others), or to a local or network folder. On S3-compatible storage the agent key has no delete rights; overwrite is refused only where the storage enforces `If-None-Match`, so use versioning or Object Lock elsewhere. In a local folder the agent can delete. Restoring needs only the bucket and a password or recovery key, even if the server is gone.
- Backups of files and directories with exclusions and pre/post hooks that run named scripts from a host-side allowlist.
- Restore from the web interface and the command line: in place, to another host, or as a downloadable archive. Search for a file across the snapshots of all hosts.
- Backup policies written as YAML or edited in a form, with cron schedules in an IANA time zone, jitter and catch-up of missed runs, and retention by daily, weekly, monthly, last-N and within-period rules. `lode apply -f` applies policies from CI, with `--dry-run` and `--prune`.
- Two-phase cleanup that runs only on the server: a dry-run report, marking, a pause longer than the longest backup, a second check, then deletion, with pack rewriting and index compaction. It works with S3 Object Lock and versioning.
- Scheduled integrity checks: repository structure, pack reads and a test restore, with a report in the interface.
- Alerts for failed backups, missing backups, offline hosts, failed checks and expiring certificates, delivered to Telegram, Slack, email and webhooks. Prometheus metrics, alert rules and a Grafana dashboard.
- Web interface with fleet overview, hosts, policies, jobs, restore and settings; the `lode` command line client with API tokens and scopes.
- Signed agent updates. The agent installs an update only after checking its signature against the project key or a key trusted on the host. The server does not verify the signature, it only reads the signature's trusted comment.
- Detection of suspicious snapshots: a snapshot marked by the anomaly detector or an administrator counts toward no retention rule and is never forgotten.
- `demo_mode`, a public read-only demonstration for a throwaway server with synthetic data, never for real backups. A demo stand is in `deploy/demo`.
