# Changelog

All notable changes to Lodestore are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- `install.sh` verifies the agent's minisign signature with the project key built into it, and with any key given by `--trust-key`: always with `--from-github` (the signature of `SHA256SUMS`), and on the server path when `minisign` is installed on the host. Without `minisign` the server path keeps the checksum check and prints a `note:`. The server serves the signature at `/install/agent/<arch>.minisig`, `GET /api/v1/server/info` has a new `project_key` field, and Add host warns about plain HTTP and shows the commands to check the agent by hand.
- A check of the `Signed-off-by` trailer on every commit of a pull request (job `dco`): each commit needs a sign-off with the name and email of its author, added by `git commit -s`. See [CONTRIBUTING](CONTRIBUTING.md).
- Server-side verification of every new backup an agent makes. After a job finishes, the server opens the new frames the snapshot depends on and checks that the snapshot resolves through shards it has checked. It downloads every new byte once, so expect that much extra egress. A job can turn `failed` with `verification_failed` after it was reported as finished, also when the server could not check the backup within one hour; its snapshot then carries `unverified_reason` in the snapshot list of the API, and the alert for a failed backup fires when that job is still the latest finished job of its policy on that host (a job without a policy, such as a stdin backup, raises no alert yet). A job that reports a snapshot already linked to another job fails the check, and the server never signs a host's shard that lists `supersedes`.
- A compromised-agent test suite, the tests named `adv_*`. Run it with `scripts/test-adversarial.sh`. `scripts/adversarial-vs-release.sh` checks that every scenario fails on 0.1.0. New scenarios: an index shard or a pack planted with a size of 5 GiB is not read by cleanup, the writer of a backup or the rebuild of the index, a writer marker planted with a size of 5 GiB does not stop cleanup, and a snapshot that does not open, or whose root tree is missing, puts cleanup into quarantine instead of stopping it for good. See [how we test data safety](https://lodestore.dev/docs/security/how-we-test/#compromised-agent-suite).
- Signed provenance of snapshots. After it has checked a backup, the server writes a record into `locks/attest-*` that names the host (from the agent's certificate) and the job, and `lode backup` with the repository password signs its own snapshot the same way, without a host. The first start of a 0.2 server on a repository signs the snapshots its catalog already ties to a host and a job, including those whose job record was already pruned; a job still on record must have succeeded. See [snapshot provenance and `latest`](https://lodestore.dev/docs/security/threat-model/#snapshot-provenance-and-latest).
- `verified_by` (`server`, `owner` or `null`) on every snapshot of the REST API and in `lode snapshots --json`. In the restore host list, `latest_verified_id` and `unverified_count`. The web interface marks a snapshot nothing signed as "Unverified" and one signed with the repository password as "Signed with password".
- `accept_unverified` in `POST /api/v1/restores` and `lode server restore --accept-unverified`: a snapshot that nothing signed is restored into another folder only after this confirmation, and never in place. The restore and download dialogs ask for it.
- The agent and the server revoke an index shard that lied: the server records it in its database, sends the list with every job and on every connection (`distrusted_shards` in the agent protocol), and the next cleanup leaves it out of the signed list. See [cleanup](https://lodestore.dev/docs/guides/gc/#attestations-and-cleanup).
- Find orders and dates its results by when the server received each snapshot, not by the time in the snapshot's manifest, and every version has `verified_by`. A version that nothing signed is listed after the signed ones, and the web interface marks it "Unverified". `lode server find` and the web interface restore a signed snapshot of the first (signed) version, even when a newer unsigned snapshot holds the same content.
- A public read-only demo at <https://demo.lodestore.dev>: three hosts back up synthetic data, and you can browse their snapshots and download one as an archive without signing in.
- Restore folders on the agent: `restore.allowed_restore_roots` (a list of absolute paths, `/var/lib/lodestore/restore` when the key is not set) and `restore.allow_in_place` (off by default) in `/etc/lodestore/agent.yaml`. `install.sh --allow-in-place-restore` turns in-place restore on. The agent reports both to the server, and the restore host list of the API has `restore_roots` (`null` when the agent has not reported them, `[]` when it allows no restore into a new folder) and `allow_in_place`; the new errors are `restore_outside_roots`, `restore_in_place_disabled` and, for tokens, `restore_agent_outdated`.
- `lode restore --allow-large-directories`, for a snapshot with a directory above 2^23 entries or 1 GiB of tree data, or with more than 2^24 entries or 2 GiB of tree data held at once; each such directory is held in memory whole.
- The API token scope `hooks:write`, and the retention option `spec.retention.includeStdin` that lets the stdin snapshots of a policy take part in retention.
- A token can start a policy on a host at most 6 times an hour per pair of policy and host; the next request answers `429` with `Retry-After`.
- A restore into a new folder never leaves setuid/setgid bits or file capabilities, even with `restore_owners`: the agent restores the owners and drops them. Only a restore in place keeps them.
- The server checks the capability `restore_roots_v1` again when it hands a token's restore job to an agent, and fails the job with `restore_agent_outdated` if the agent no longer reports it.
- `PUT /api/v1/policies/{name}` answers `409` `policy_conflict` before any scope check when `base_revision` is stale, and `PUT /api/v1/hosts/{id}/labels` answers `409` when the labels changed while the request ran.
- A size limit on index shards: cleanup, the writer of a backup and the server's check of a new backup do not load a shard above 64 MiB that the server has not signed, a restore included, and a shard the server signed is read up to 1 GiB once its content, hashed in pieces of 64 MiB, matches its name; a signed shard above 1 GiB is left out and reported, refused before any read when the listing shows its size. A 0.1 repository that no 0.2 server has opened and that holds a larger shard, or a signed one above 1 GiB, needs `lode repo rebuild-index` before a restore. Every object the format reads from the bucket is read with a bounded ranged read: a writer marker above 1 MiB is not read and counts as an open writer, a key slot above 64 KiB is skipped, an opening reads at most 1024 key slots, and a `config` above 1 MiB makes the repository unavailable. Every writer cuts the shards it writes at 32 MiB and 1024 pack records. A signed shard above 64 MiB written by 0.1 is rewritten into shards under the limit by the first cleanup cycle after the update, which therefore goes through the pause even when there is nothing to delete. See [cleanup](https://lodestore.dev/docs/guides/gc/#what-a-cycle-does).
- Quarantine of snapshots that cleanup cannot follow. Such a snapshot no longer stops cleanup for good: the cycle collects them, deletes nothing and waits, and an administrator with `snapshots:delete` excludes each one with **Exclude from cleanup** or `POST /api/v1/repositories/{id}/gc/quarantine/{snapshot_id}/exclude`. A snapshot that belongs to a backup job cannot be excluded; one that retention has forgotten but the storage keeps can. An exclusion made while a cycle runs is kept, and an excluded snapshot that reads again or is gone loses its exclusion, and is quarantined again if it breaks later. The cleanup report has the new lists `skipped_shards` and `quarantined`. See [quarantined snapshots](https://lodestore.dev/docs/guides/gc/#quarantined-snapshots).
- The alerts `snapshot_quarantined` and `repository_unavailable`, on by default for notification channels, and the Prometheus rules `LodestoreSnapshotQuarantined` and `LodestoreRepositoryUnavailable`. Channels created in the interface before 0.2 with every alert type get the two new types when the server updates; channels with a chosen list do not.
- A budget for the walk of a snapshot's directory tree: 2^30 entries and 512 GiB of directory data per operation, counting every visit. One directory may have at most 2^23 entries and 1 GiB of tree data, and one operation may hold at most 2^24 entries and 2 GiB of tree data at once, each open directory counted at its full length (`entries in one directory`, `bytes in one directory`, `entries held at once`, `bytes held at once`); a directory whose pieces already add up to more than the limit is refused before any piece is read. A backup refuses a larger directory and a path whose open directories hold more, and writes no snapshot. `lode restore --allow-large-directories` restores a snapshot written before that. A restore, a listing, an archive download and a restore plan stop with an error that names the limit. The integrity check (`lode check` and the server's) reports a snapshot that passes one of the four limits of a directory and a path, or the budget of the whole walk, as `unreadable_tree` with the limit named, and goes on with the others. The API answers `400` `tree_too_large` for a listing, a summary and preparing an archive, an archive download that passes the limit after it started ends without the end of the archive, and a search ends as incomplete with `stop_reason` `walk_limit`. Cleanup is not subject to it.

- Step-up for dangerous actions of a session: creating an API token, creating a join token, and starting a restore that writes in place, restores owners or targets an agent that does not report `restore_roots_v1` need the password to have been entered in the last 15 minutes. Otherwise the API answers `403` `step_up_required` before anything is created. `POST /api/v1/auth/step-up` opens the next 15 minutes, and five wrong passwords in a row end the session; a wrong current password when changing the password and a failed sign-in that carries the session cookie count towards the same five. The web interface asks for the password in a dialog and carries on. API tokens are not affected and still cannot create tokens or join tokens.
- Step-up now also covers what an API token needs `hooks:write`, `snapshots:delete` or `agents:update` for: a session must have entered its password in the last 15 minutes to create or update a policy so that it sets or changes hooks or retention (or runs retention more often), to apply such policies, to change host labels so that a policy with hooks reaches the host, to delete a snapshot or mark it suspicious, to start a cleanup, close its backup markers, exclude a quarantined snapshot or save the cleanup settings, and to start or continue an agent update. Otherwise the API answers `403` `step_up_required` and changes nothing. API tokens are not affected; their scopes still decide.
- `revoke_tokens` on `POST /api/v1/account/password`: with `true` the change also revokes every API token and expires every join token that nobody used, and the password form offers it as an option. Without it the tokens stay valid. Changing the password still ends the other sessions.
- The alerts `agent_session_conflict` (a live agent session replaced from another address, or five replacements in ten minutes) and `agent_certificate_rejected` (a certificate the server did not issue last), on by default for notification channels, the Prometheus rules `LodestoreAgentSessionConflict` and `LodestoreAgentCertificateRejected`, and the metric `lodestore_unknown_agent_refusals`. Channels created in the interface with every alert type get the two new types when the server updates; channels with a chosen list do not. See [alerts](https://lodestore.dev/docs/guides/alerts/#alert-types).
- `notifications.proxy` in `server.yaml`: an `http://` or `https://` proxy for webhook, Slack and Telegram requests. The proxy resolves the target name, so the server checks only addresses written as numbers. See [sending through a proxy](https://lodestore.dev/docs/guides/alerts/#sending-through-a-proxy).
- Helm chart: a ServiceAccount of its own without a mounted token (`serviceAccount.create`, `serviceAccount.name`), a NetworkPolicy for ingress (`networkPolicy.enabled`, `networkPolicy.metricsFrom`, `networkPolicy.egress`), and a separate Service for metrics. See [Deploying with Helm](https://lodestore.dev/docs/install/helm/#pod-security-defaults).

### Changed

- `Trees checked` of the structure check (`trees_checked` in the API) counts the different trees read, not every read, so a directory shared by many snapshots counts once.
- **Upgrade:** Back up the server database before upgrading to 0.2: the first start re-seals the stored secrets, and a 0.1 server cannot read them afterwards: started on the migrated database it stops with `unlock key does not match`, and the only way back is to restore the database backup.
- The server seals its secrets with associated data that carries the length of the kind and of the id, and migrates the secrets of 0.1 once at start, in one transaction.
- A build that does not know a feature in `incompat_features` of a repository refuses to read it as well as to write it.
- The server does not open a repository whose `config` differs from the one recorded when the repository was added. The repository page shows the reason in Storage checks and the alert `repository_unavailable` is raised; other repositories are not affected. The server hands no writer keys or storage key to agents, assigns no restore job and no backup job it queued, manual, scheduled or catch-up (they fail with `repository_unavailable`), signs no URLs for reading packs, and browsing, downloads and the catalog sync answer `503` `repository_unavailable`, enrolling a host and planning a restore fail with `failed_precondition`, and the new agent key of such a repository is sent to no agent until it opens again (agents get it at their next hello); **Check storage again** reopens the repository.
- Opening a repository with a password spends at most `16777216` of Argon2 work (`m × t`), the work of one slot with the largest allowed parameters, summed over the slots the secret actually tries; slots of another kind or with parameters out of range cost nothing. One opening also reads at most 1024 key slots, in the order of the listing. When the budget or the count stops the opening, the error says the secret is wrong or its slot was not tried and names both limits, and `lode` exits with 12.
- Cleanup deletes no pack named by an index shard it skipped while agents older than 0.2 are enrolled: update the agents and `lode` together with the server, otherwise cleanup waits and the cycle fails with a message that names the hosts.
- **Breaking:** `install.sh --from-github` requires `minisign` on the host and stops before downloading anything without it. On a host with `minisign`, an agent without a matching signature, such as one from an image built from source, is not installed unless it is signed with a key given by `--trust-key`.
- The server refuses to start when `public_url` has a user name, a quote or any character other than letters, digits and `. : - _ [ ]` in its host, because the value is written into the install script.
- The server is relicensed from AGPL-3.0 to Apache-2.0; every crate in the repository is now Apache-2.0.
- **Breaking for CI:** the API token scope `restore` is split into `restore:download` (archive downloads), `restore:host` (restore into a new folder) and `restore:in-place` (restore in place). Tokens issued before the update keep only `restore:download`. A CI job that started restore jobs gets `403`, with the name of the scope it needs, until you issue a new token with `restore:host` or `restore:in-place`.
- A token needs `restore:in-place` to restore file owners, setuid/setgid bits and file capabilities (`restore_owners`). `lode server restore` restores owners by default, so with a token that holds only `restore:host` run it with `--no-owners`. Sessions are not affected.
- A token needs `hooks:write`, besides `policies:write` or `hosts:write`, to create a policy with hooks, change or remove hooks, change the `repository` of a policy with hooks, change its selector in any way other than a shorter `hosts` list or more `matchLabels`, or bring a host under a policy with hooks by its labels, also in `lode apply --dry-run`. This does not depend on which hosts are enrolled. Hooks a policy already has stay as they are.
- The default restore folder is `/var/lib/lodestore/restore/<date>-<id8>` (the old default lacked the `lib` part: `/var/lodestore/` instead of `/var/lib/lodestore/`) in `lode server restore`, the web interface and the quickstart; both use the first restore folder the host reports when it reports one. After the update an agent restores only into its `allowed_restore_roots`, and without that key only into `/var/lib/lodestore/restore`; a restore into another folder, from the web interface too, is refused with `restore_outside_roots` until you add the folder. Restore in place is off on the agent until `allow_in_place: true` is set.
- Setting or changing retention, `includeStdin` or making the schedule of a policy with retention more frequent needs `snapshots:delete` of a token. The server compares the smallest gap between runs over the next 366 days, so a cron limited to some months is caught too. A new schedule with no two runs in that period, such as `* * 29 2 *`, or one with more than 100000 runs in it, counts as more frequent.
- Retention counts scheduled and manual (run-now) snapshots of a policy and host in two pools; rules and the floor of two apply to each. A run-now that is queued or running when a scheduled slot comes no longer takes the slot: the scheduled backup runs after it. Snapshots from `lode backup --stdin --policy` take no retention slot and are not the last backup of the policy, unless `includeStdin` is set.
- Cleanup opens the surviving copy of every live blob before it deletes or replaces a pack, and skips a pack it cannot read instead of failing; the cycle records a warning naming each skipped pack. `supersedes` of an index shard counts only when the server has signed the shard. `lode restore` and the server's own reads try the other known copies of a blob when the first one does not open; a restore run by an agent and an archive download read only the first copy for now. Cleanup, backups and the server's check of a new backup skip an index shard with a malformed record instead of failing.
- Once a 0.2 server has opened a repository, agents deduplicate only against their own shards and shards the server signed. The repository format stays version 1. The server signs shards with new `locks/attest-*` objects, which 0.1 ignores. An object there that fails the server's MAC is logged and deleted by the next cleanup cycle.
- `latest` in `lode restore`, `lode ls` and `lode dump`, and in the restore page of the web interface, is the newest snapshot that carries a signature, ordered by the time the storage or the server recorded, not by the time written in the snapshot. A repository that no 0.2 server has opened has no signatures: `latest` then follows the storage's time with a warning, never takes a snapshot stored in the future, and refuses and asks for an id when `lode` has seen signatures there before and they are gone. Without a signed snapshot `latest` fails and asks for an id.
- Snapshot lists are ordered by the time the server received the snapshot. Retention, the time of the last backup (the fleet overview, the missing-backup alert, metrics) and the baseline of the anomaly detector count only signed snapshots. Retention never forgets an unsigned snapshot.
- `lode backup` with a password or recovery key in a repository the server has upgraded deduplicates only against signed shards, opens its snapshot's data the way the server does and exits with 1 if it does not check out, signs the snapshot when it does, and picks an incremental parent only among snapshots signed for its host name. The first run on a machine reads much of the data, and it keeps what it checked in `$XDG_CACHE_HOME/lode/`. `lode backup --writer-keys` exits with an error in such a repository. See [the command line](https://lodestore.dev/docs/reference/cli/#backup-and-restore-without-the-server).
- Every verified backup and every strict `lode backup` adds one `locks/attest-*` object, and only a cleanup cycle merges them. With cleanup turned off they accumulate, and every open for writing and every `latest` reads all of them.
- The documentation moved to <https://lodestore.dev/docs/>. The old addresses under `https://lodestore.github.io/lodestore/` redirect to the new pages.
- The project site with comparisons and a blog is at <https://lodestore.dev>.
- The `lode` message about access to `locks/` links to the new address of the cleanup guide.

- Sign-in limits: IPv6 clients are grouped by their /56 prefix (was /64), a user has a limit of 60 failed attempts an hour that spares addresses it has signed in from (kept in memory, empty after a restart), and passwords are measured in bytes: a new one may have up to 1024 bytes, and a submitted one over 4096 bytes is refused before it is hashed. The hashing of passwords runs through a gate, and when it is full sign-in, creating the administrator, changing the password and the step-up answer `503` `busy` with `Retry-After` without counting the attempt. Behind a reverse proxy without `trusted_proxies` the limit for a user name does not hold.
- REST and the metrics port close a connection that does not send a complete request head within 10 seconds, an idle keep-alive connection included. gRPC allows 10 seconds for the TLS handshake and for the first `Hello`, 32 streams per connection and 4096 connections, 256 of them per client address (IPv6 by its /56).
- A host has at most 8 open CLI jobs; the next ones from the agent's socket are refused. Results of jobs the agent finished offline are still recorded.
- Without `restore_owners` (`lode server restore --no-owners`, or an agent with `restore_owners` off) a restore skips every `system.*` attribute (all ACLs), `security.*` and `trusted.*`; `user.*` is restored as before. A `tar` download still carries every attribute as `SCHILY.xattr.*`, and `--xattrs` and `--acls` of the one who unpacks it decide whether they are applied.
- Notification clients now also refuse `0.0.0.0/8` and `240.0.0.0/4` always, `192.0.0.0/24`, `198.18.0.0/15`, `fec0::/10` and `64:ff9b:1::/48` unless `allow_private_targets` is set, and the metadata addresses `100.100.100.200`, `192.0.0.192` and `fd00:ec2::254` even with it. An IPv6 address that holds an IPv4 address (mapped, compatible, SIIT, NAT64 including `64:ff9b:1::/48`, 6to4, Teredo) is judged by the IPv4 address in it. Email connects to the address it checked.
- **Breaking:** the server no longer uses `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` for notifications. A deployment that reached Slack, Telegram or a webhook through an environment proxy has to set `notifications.proxy` in `server.yaml`, or deliveries fail.
- **Breaking:** in the Helm chart, metrics (`metrics.port`) moved from the shared Service to `<release>-lodestore-metrics`, a Service of its own. Point Prometheus at it. A NetworkPolicy now closes the metrics port to every pod until the scraper is listed in `networkPolicy.metricsFrom`.
- **Breaking:** the Helm pod now runs with a read-only root filesystem (a 64 MiB `/tmp` is mounted), the seccomp profile `RuntimeDefault`, no privilege escalation and no capabilities, under a ServiceAccount of its own without a token, and `networkPolicy.enabled` is on. Set `networkPolicy.enabled=false` if your cluster has its own policy, or `networkPolicy.egress` to restrict outgoing traffic.
- **Breaking:** sessions that were open before the update have no password time and ask for the password at the first token, join token or restore that needs it. Sign in again or enter the password in the dialog.
- **Breaking:** `lode server restore --no-owners`, and an agent without `restore_owners`, no longer set POSIX ACLs, `security.*` or `trusted.*` attributes; a restore that relied on them without owners has to ask for owners (`restore:in-place` for a token).

### Security

- An API token can no longer get root on a host, change hooks or make the server forget scheduled history without the scope for it: restore needs `restore:host` or `restore:in-place`, the agent confines restores to its own restore folders and turns in-place off by default, hooks and the hosts they run on need `hooks:write`, and run-now, a more frequent cron and `includeStdin` cannot push scheduled snapshots out of retention. A token with `restore:host` cannot restore setuid files. A server that is taken over can still write under the restore folders of every host, and anywhere on a host where in-place restore is on or the agent is from 0.1. See [API tokens](https://lodestore.dev/docs/security/threat-model/#api-tokens).
- Index shards from a compromised host no longer influence cleanup or the backups of other hosts. The first time a 0.2 server opens a repository (created, connected or upgraded) it signs the shards that exist at that moment, and trusts them only for `supersedes` and cleanup; the data a new backup depends on is opened and checked by the server once, so a shard planted before the upgrade makes such a backup fail instead of succeed. After upgrading, run `lode check --level packs` to find a forgery made earlier across the whole repository. See [index metadata from a compromised agent](https://lodestore.dev/docs/security/threat-model/#index-metadata-from-a-compromised-agent).

- A host with writer credentials can no longer make `latest`, "restore to the original host", the time of the last backup or the retention window follow a snapshot it planted: planting a snapshot with a date far in the future, or a hundred snapshots, changes none of them. Open a repository with a 0.2 server before you need an emergency restore; until then `lode restore latest` runs in the legacy mode described above, which a host that wrote last can still win, and a new machine reading a folder repository whose signatures were deleted cannot tell. The first strict `lode backup` on a machine costs a read of the data its snapshot depends on. See [snapshot provenance and `latest`](https://lodestore.dev/docs/security/threat-model/#snapshot-provenance-and-latest).

- An old or copied agent certificate no longer opens a session, renews or reads packs: the server accepts only the serial it issued last, and the one before it for two minutes after the first session with the new one, for at most 24 hours; a session that was opened with the previous certificate is closed when that window ends, and the agent reconnects with the current one. The refusal is `certificate_stale`; the agent logs how to enrol the host again and keeps retrying. **Upgrade:** a host whose renewal answer was lost before the update, so that its certificate on disk is older than the one in the database, has no grace window and is refused; enrol it again with `install.sh --force` and a new join token. See [agent credentials](https://lodestore.dev/docs/security/threat-model/#agent-credentials).
- A session that someone else holds can no longer create a token, a join token or a root-owned restore without the password, and a password change can revoke every token. Guessing is bounded by the limits above, and a flood of sign-ins cannot lock the administrator out or make the server hash without bound. See [signing in and sensitive actions](https://lodestore.dev/docs/security/threat-model/#signing-in-and-sensitive-actions).
- Notifications cannot be pointed at what the server can reach and the administrator cannot: an environment proxy no longer bypasses the address filter, more ranges and embedded IPv4 addresses are refused, and the SMTP connection goes to the checked address. See [notifications and outbound requests](https://lodestore.dev/docs/security/threat-model/#notifications-and-outbound-requests).
- A slow or silent client can no longer hold REST, metrics or gRPC connections open without limit, and a local user or a compromised agent cannot fill the job table with CLI jobs. A database URL, the unlock key and the administrator password given on the command line are no longer printed by the server's debug output. See [limits against a flood](https://lodestore.dev/docs/security/threat-model/#limits-against-a-flood).

### Fixed

- A file whose chunk sizes in the index do not add up made a restore read every chunk it names before charging them to the walk budget, and the structure check read them without any limit, so one planted file naming one chunk many times could make the nightly check read terabytes. Now each distinct chunk of such a file is read once per visit, every reference to a chunk is charged as it is read, and charging and reading stop once the chunks hold more than the file says. The structure check reads such chunks within the walk budget of one restore per run, reads no other chunk once that budget is spent, and reports a file it could not read for every snapshot that reaches it. Every copy of such a chunk that is fetched is charged to that budget, also the copies before the real one that do not open, and a chunk none of whose copies opens is not read again for the next file that names it.
- The structure check read a piece of a directory once for every time the directory listed it, so a directory listing one empty tree thousands of times cost as many reads, none of them charged. Now a piece is read once per directory, and its bytes count every time the directory lists it, as in a restore.
- The structure check sized directories and files by all index shards, while a restore takes the sizes of the shards its snapshot names, so a snapshot naming only a planted shard with larger tree sizes or wrong chunk sizes passed the check and then stopped `lode restore` at a limit. Now a snapshot that names a shard listing a tree larger than the check read it, or a chunk at another size than the one its file added up with, is the finding `unreadable_index`.
- The structure check kept the lists of subdirectories and the hardlink members of a directory whose subtree had taken the path over a limit while it walked below; it now lets go of them.
- The size of the repository the structure check counts no longer overflows on a listing with impossible object sizes.
- `lode backup` held the chain of directories of its parent snapshot without the limits of a path, so a planted parent could make it hold a gigabyte of tree data per level; the parent now stops at 2^24 entries and 2 GiB of tree data held at once, and the backup goes on without it.
- A file whose chunk sizes in the index do not add up charges its chunks and their bytes to the walk budget on every visit, and its chunks are read once per operation for up to 65,536 such files; the structure check counts the same charge.
- The structure check reported a finding in a directory shared by several snapshots for the first snapshot only and called the others ok; every snapshot that reaches the directory now gets it.
- The structure check could read a tree again for every new path to a directory several snapshots share, and a planted tree made that number grow exponentially; it now reads each directory once and judges each snapshot by its own path, in whichever order the snapshots are read.
- The structure check gave a conflict between hardlink members of a shared directory and another directory to every snapshot that shares the directory, and could leave without a finding a snapshot that was checked after another with the same directory; only the snapshot in which the members of a group differ now gets the finding.
- The structure check gave no finding for a snapshot whose tree pack is missing from the bucket; it now reports `unreadable_tree` for each snapshot that needs it and goes on.
- A restore counted only the entries left to hand out of a directory it had already walked into, so a tree of nested directories could pass the limit of 2^24 entries held at once; every open directory now counts at its full length, and `lode backup` refuses a tree a restore could not hold.
- A failed or incomplete read of the attestations is no longer remembered for the life of the reader: the next load reads them again.
- Cleanup stops with a store error when a snapshot body is not the size the listing gave, instead of ignoring it or quarantining it, and reports the real reason when a repack skips a pack longer than its listing.
- An object listed with size zero that has vanished is reported as gone, not read as empty.
- An oversized `config` is the finding `unreadable_config` of `lode check` and the server's checks and no longer aborts the check.
- An exclusion confirmed while a cleanup survey is running is kept; a dry run or a cleanup lifts an exclusion only when its survey started after the confirmation.
- The catalog sync of an unavailable repository answers `503` `repository_unavailable`, and enrolling a host and planning a restore answer `failed_precondition`, instead of an internal error.
- Replacing the agent key of a repository the server cannot open no longer pushes the key to agents; they get it at their next hello after the repository opens again.
- A search that the user cancels ends as `cancelled` even when a snapshot was skipped at the walk limit.
- The Free up space card refreshes the quarantine after a `409` from an exclusion, and the alerts after an exclusion.
- The restore dialog of the web interface keeps Start off and says the restore will be refused for a folder outside the host's restore folders, or when the host allows no new folder; restore errors that retrying cannot fix no longer ask to try again.
- Closing the Create API token dialog without creating a token returns focus to the Create token button.
- `lode server restore --host <name>` with a token that cannot read the host list says to pass the host id when the server does not know the name.
- The demo stand template `deploy/demo/env.example` starts from 0.1.0. The proxy steps in `deploy/demo/README.md` get the certificate first, install the site file without editing the working copy and keep it through the maintenance window, and the update steps restart the rootless Docker daemon after a Docker or containerd package upgrade.

## [0.1.0] - 2026-11-02

First release.

### Added

- Backup server in a single binary, shipped as a Docker image and a Helm chart. It keeps its catalog in SQLite by default and in PostgreSQL for production.
- Host agent for Linux on x86_64 and arm64. It registers with a one-time join token, receives its own client certificate, keeps an outbound connection to the server and needs no inbound ports.
- Encrypted, deduplicated repository format v1. Agents write straight to S3-compatible object storage (AWS S3, MinIO, Ceph and others), or to a local or network folder. On S3-compatible storage the agent key has no delete rights; overwrite is refused only where the storage enforces `If-None-Match`, so use versioning or Object Lock elsewhere. In a local folder the agent can delete. Restoring needs only the bucket and a password or recovery key, even if the server is gone.
- Backups of files and directories with exclusions and pre/post hooks that run named scripts from a host-side allowlist.
- Restore from the web interface and the command line: in place, to another host, or as a downloadable archive. Search for a file across the snapshots of all hosts.
- Backup policies written as YAML or edited in a form, with cron schedules in an IANA time zone, jitter and catch-up of missed runs, and retention by daily, weekly, monthly, last-N and within-period rules. `lode apply -f` applies policies from CI, with `--dry-run` and `--prune`.
- Two-phase cleanup that runs only on the server: a dry-run report, marking, a pause longer than the longest backup, a second check, then deletion, with pack rewriting and index compaction. It works with S3 Object Lock and versioning.
- Scheduled integrity checks: repository structure, pack reads and a test restore, with a report in the interface.
- Alerts for failed backups, missing backups, offline hosts, failed checks and expiring certificates, delivered to Telegram, Slack, email and webhooks. Prometheus metrics, alert rules and a Grafana dashboard.
- Web interface with fleet overview, hosts, policies, jobs, restore and settings; the `lode` command line client with API tokens and scopes.
- Signed agent updates. The agent installs an update only after checking its signature against the project key or a key trusted on the host. The server does not verify the signature, it only reads the signature's trusted comment.
- Detection of suspicious snapshots: a snapshot marked by the anomaly detector or an administrator counts toward no retention rule and is never forgotten.
- `demo_mode`, a public read-only demonstration for a throwaway server with synthetic data, never for real backups. A demo stand is in `deploy/demo`.
